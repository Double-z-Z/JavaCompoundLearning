# 标签治理

> **触发时机**
> - 用户说"整理标签"
> - 用户说"标签健康度"
> - 用户说"tags治理"
> - 用户说"治理标签"
> - 用户说"标签检查"
>
> **核心原则**: 标签是用户查询的主要阵地，只用于原子笔记的概念关联。系统属性用 frontmatter，AI 属性不用标签。

## 执行阶段

### Phase 1: 数据采集（3 分钟）

**执行**:
```bash
obsidian tags sort=count counts
```

**补充扫描**:
```bash
# 扫描 frontmatter tags（学习笔记范围）
grep -rn "^tags:" 02-Knowledge 03-Practice 01-Projects 04-Maps 05-Templates wiki --include="*.md"

# 扫描 inline #tags（同上范围）
grep -rn "#[一-龥a-zA-Z]" 02-Knowledge 03-Practice 01-Projects 04-Maps 05-Templates wiki --include="*.md" | grep -v "^.*:# " | grep -v "##"
```

**记录**:
- 标签总数、单标签计数、出现文件数
- 区分 frontmatter tags vs inline tags

---

### Phase 2: 问题诊断（5 分钟）

将问题分为 6 类，按处理优先级排序：

| 类别 | 问题描述 | 判断标准 | 处理策略 |
|------|---------|---------|---------|
| **A. 同义词重复** | 同一概念中英文并存 | `并发`+`concurrency`、`算法`+`algorithm` | **可直接处理**（用户历史偏好） |
| **B. 系统标签混入** | 笔记类型/状态误用为标签 | `drill`、`project`、`mistake`、`MOC`、`practice` | **建议直接处理**（转为 frontmatter `type`） |
| **C. 高度相关可合并** | 子概念与父概念并存 | `selector`/`epoll`/`buffer` 与 `IO模型` | **建议确认后处理**（分批呈现） |
| **D. 英文可中文化** | 普通英文词有中文对应 | `performance`→`性能`、`scenario-analysis`→`场景分析` | **建议确认后处理**（专有名词保留） |
| **E. 伪标签污染** | 非笔记文件中的 `#章节引用` | Skill/设计文档中的 `#当前快照`、`#拒绝清单` | **建议确认后处理**（改为「章节名」） |
| **F. 过于细分/宽泛** | 标签粒度不当 | 仅出现 1 次且过度具体，或过于宽泛如 `tech` | **建议确认后处理**（用户可能拒绝） |

**诊断时注意**:
- 专有英文名词（`NIO`、`Redis`、`Netty`、`WebFlux`、`Caffeine`、`Lua`、`JVM`）**不**建议中文化
- `type`/`status`/`mastery` 等系统元数据**应**在 frontmatter 中管理，不在 tags 中
- 不纠结 kebab-case/snake_case/空格等格式问题，**只关注语义正确**

---

### Phase 3: 输出报告（5 分钟）

**报告格式**:
```
🏷️ 标签健康度诊断报告

📊 基础数据
- 总标签数: X
- 单标签最高出现: #redis (25)
- 疑似问题标签: Y 个

┌─────────────────────────────────────────────────────────┐
│ A. 同义词重复（可直接处理）                                │
├─────────────────────────────────────────────────────────┤
│ 违规标签        │ 规范形式    │ 涉及文件数 │ 建议操作     │
│ `concurrency`   │ `并发`      │ 1          │ 合并         │
│ `algorithm`     │ `算法`      │ 1          │ 合并         │
└─────────────────────────────────────────────────────────┘
> 此类问题历史授权直接处理，是否执行？ [Y/n]

┌─────────────────────────────────────────────────────────┐
│ B. 系统标签混入（建议直接处理）                            │
├─────────────────────────────────────────────────────────┤
│ 违规标签   │ 应转 frontmatter │ 涉及文件数 │ 建议操作      │
│ `drill`    │ `type: drill`    │ 9          │ 删除tag加属性 │
│ `MOC`      │ `type: moc`      │ 2          │ 删除tag加属性 │
└─────────────────────────────────────────────────────────┘
> 此类问题影响标签纯洁性，建议直接处理，是否执行？ [Y/n]

┌─────────────────────────────────────────────────────────┐
│ C. 高度相关可合并（建议确认）                              │
├─────────────────────────────────────────────────────────┤
│ 父标签      │ 建议合并的子标签              │ 涉及文件数 │
│ `IO模型`    │ `selector`, `epoll`, `buffer` │ 6          │
│ `cache`     │ `local-cache`, `hot-cold-tiering`│ 3       │
└─────────────────────────────────────────────────────────┘
> 建议按批次逐步处理，是否执行本批次？ [Y/n/跳过]

...（D/E/F 类同理，每类单独呈现，用户逐类决策）
```

**呈现规则**:
1. A/B 类合并呈现，询问一次确认
2. C/D/E/F 类**分别呈现**，每类独立询问
3. 用户说"跳过"或"不要执行 X" → 记录到报告中并跳过
4. 用户说"X 类直接处理" → 执行该批次全部操作
5. 用户对某一批次中的个别条目有异议 → 只处理同意的条目，异议条目记录为"用户保留"

---

### Phase 4: 执行整改（按确认批次）

**执行规则**:
- 优先修改 `02-Knowledge/`、`03-Practice/`、`04-Maps/`、`05-Templates/` 中的学习笔记
- `wiki/` 文件中的示例标签也需同步修正
- Skill 文件中的伪标签（E类）需同时修改 `.claude/skills/` 和 `.trae/skills/` 镜像
- 修改 dataview 查询中的标签引用时，同步更新查询语句
- 用户**未明确同意**的条目，绝不执行

**每批次执行后**:
```bash
obsidian tags sort=count counts
```
对比验证该批次标签是否已消失/合并。

---

### Phase 5: 归档与预防

**更新整理笔记 Skill**:
如发现标签问题源于笔记生成规范未遵守，在 `.claude/skills/整理笔记/SKILL.md` 和 `.trae/skills/整理笔记/SKILL.md` 中补充约束。

