# 领域术语表（Ubiquitous Language）

> **用途**: 消除跨上下文词汇歧义，作为所有设计文档、接口契约、代码实现的权威命名参考。
> **原则**: 同一词汇在同一 Bounded Context 内只能有一个含义；跨上下文引用时必须带上下文前缀。

---

## 1. Host Context（主机上下文）

| 术语 | 语义 | 类型 | 合法值 |
|------|------|------|--------|
| **hostType** | 主机的物理形态 | 枚举 | `PVE_HYPERVISOR`, `VM`, `BARE_METAL`, `LOCAL` |
| **hostRole** | 主机在 MCP 体系中的功能角色 | 枚举集合 | `MCP_HOST`, `TARGET`, `LOADGEN` |
| **capability** | 主机声明的可执行能力 | 枚举集合 | `DOCKER`, `NATIVE`, `VM` |
| **networkZone** | 主机所属的网络区域标识 | 字符串 | 如 `lan-10.0.0` |

### 命名约束

- `hostType` 在 hosts.yml 中字段名为 `type`，在代码中映射为 `HostType` 枚举。**禁止**在其他上下文中简称 `type` 来表达此概念。
- `capability` 中的 `DOCKER` / `NATIVE` 表示"这台机器能否运行 Docker/原生进程"，与 Environment 的隔离技术选型是不同层级的概念。

## 2. Environment Context（环境上下文）

| 术语 | 语义 | 类型 | 合法值 / 示例 |
|------|------|------|--------------|
| **environmentType** | 环境的业务用途分类 | 枚举 | `DEV`, `TEST`, `STAGING`, `PROD`, `EXPERIMENT` |
| **isolationType** | 运行时隔离技术选型 | 枚举 | `DOCKER`, `NATIVE` |
| **runtimeConstraint** | 运行时版本约束（镜像/引擎版本） | 字符串 | `docker:26.0`, `openjdk:21-jre-slim` |
| **environmentStatus** | 环境生命周期状态 | 枚举 | `CREATING`, `READY`, `DEPLOYING`, `RUNNING`, `ERROR`, `DESTROYED` |
| **resourceQuota** | 环境资源配额 | 值对象 | `{ cpu: "1.0", memory: "512m" }` |

### 关键区分

- **environmentType** vs **isolationType**:
  - `environmentType` 回答"这个环境用来做什么"（业务维度）
  - `isolationType` 回答"这个环境用什么技术隔离"（技术维度）
  - 二者是正交关系：一个 TEST 环境可以用 DOCKER 隔离，也可以用 NATIVE 隔离。

- **isolationType** vs **runtimeConstraint**:
  - `isolationType` 是分类（DOCKER / NATIVE）
  - `runtimeConstraint` 是具体要求（`docker:26.0`）
  - 当 `isolationType=DOCKER` 时，`runtimeConstraint` 可以是 `docker:26.0`；当 `isolationType=NATIVE` 时，`runtimeConstraint` 可以是 `openjdk:21-jre-slim`。

### 已废弃的命名（代码待对齐）

| 废弃用法 | 问题 | 正确用法 |
|----------|------|----------|
| `type` 表示环境业务用途 | 与 Host 的 `type`、Schema 的 `type` 冲突 | `environmentType` |
| `type` 表示运行时隔离 | 与 `environmentType` 冲突，一词两义 | `isolationType` |
| `runtime` 表示运行时类型 | 与 V3 设计的"版本约束"意图冲突 | `isolationType`（分类）+ `runtimeConstraint`（版本） |

## 3. Deploy Context（部署上下文）

| 术语 | 语义 | 类型 | 合法值 |
|------|------|------|--------|
| **serviceName** | 服务目录中的注册名（对外契约） | 枚举 | `redis-counter-service`, `devops-dashboard`, `mcp-host-agent`, `redis-cache` |
| **templateName** | 服务模板配置中的模板标识（内部实现） | 字符串 | 如 `nacos-server` |
| **serviceRegistry** | 服务目录白名单，维护合法的 serviceName 集合 | 领域服务 | 配置驱动 |
| **serviceManifest** | 服务部署规格 | 值对象 | `{ templateName, image, envOverrides }` |

### 命名约束

- 外部 MCP Tool Schema 统一使用 `serviceName`。
- 内部模板系统可能仍使用 `templateName`，二者在防腐层（ACL）做映射：Schema 的 `serviceName` → DTO 的 `serviceName` → 领域的 `templateName`（如果内部模板系统未改造完成）。
- **禁止**在 Tool Schema 中使用 `templateName`，在 DTO 中使用 `serviceName` 这种内外颠倒的命名。

## 4. Pipeline Context（流水线上下文）

| 术语 | 语义 | 类型 | 合法值 |
|------|------|------|--------|
| **pipelineId** | 部署流水线的身份标识 | 值对象 | `pipe-{timestamp}-{seq}` |
| **pipelineStatus** | 流水线执行状态 | 枚举 | `PENDING`, `CREATING`, `DEPLOYING`, `VERIFYING`, `ANALYZING`, `SUCCEEDED`, `FAILED`, `COMPENSATED` |
| **stageStatus** | 流水线子阶段状态 | 枚举 | `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `SKIPPED` |
| **keepOnFailure** | 失败时是否保留环境用于排查 | 布尔 | 默认 `false` |

## 7. 跨上下文引用规则

当需要在 A 上下文中引用 B 上下文的概念时，**必须带上下文前缀**，禁止简称。

| 场景 | 错误 | 正确 |
|------|------|------|
| Environment Handler 中引用 Host 的物理形态 | `type` | `hostType` |
| env_create Schema 中表达隔离技术 | `type` | `isolationType` |
| env_create Schema 中表达业务用途 | ~~`type`~~（已废弃） | `environmentType` |
| env_list 返回中表达隔离技术 | `type` | `isolationType` |
| deploy_pipeline 中表达隔离技术 | `envType` | `isolationType` |
