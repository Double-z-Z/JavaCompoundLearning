## ADR-001: Environment 作为聚合根而非 Service

**背景**: 初期可能认为 Service 是核心（"我要管理 Nacos/RabbitMQ"）

**选项**:
- A) Service 为聚合根（直接管理服务）
- B) Environment 为聚合根（管理环境，环境包含服务）

**选择**: B) Environment 为聚合根

**理由**:
1. **生命周期一致性**: 服务不能脱离环境独立存在
2. **不变量保护**: 端口冲突、资源配额等约束需要在环境级别保证
3. **原子操作**: 创建/销毁环境时，所有服务应一起操作
4. **符合认知**: 用户思维是"启动开发环境"，不是"启动 Nacos+MySQL"

**影响**:
- 所有服务操作都通过 Environment 进行
- ServiceInstance 没有独立的 Repository

**日期**: 2026-05-17 | **状态**: ✅ 已实施

## ADR-002: Experiment 独立聚合根而非 Environment 子类

**背景**: Experiment 也需要创建环境，看起来像特殊 Environment

**选项**:
- A) Experiment 继承 Environment（is-a 关系）
- B) Experiment 组合 Environment（has-a 关系）
- C) Experiment 独立聚合根，内部包含专用环境

**选择**: C) 独立聚合根

**理由**:
1. **职责分离**: Experiment 关注"假设验证"，Environment 关注"资源管理"
2. **生命周期差异**: Experiment 有明确结论状态，普通 Environment 没有
3. **特殊行为**: Experiment 需要自动归档、自动销毁逻辑
4. **避免继承滥用**: 继承导致强耦合，组合更灵活

**影响**:
- Experiment 有自己的 Repository
- ExperimentEnvironment 复用 Environment 的逻辑但增加实验特有属性

**日期**: 2026-05-17 | **状态**: ✅ 已实施

## ADR-003: Pipeline 不是聚合根

**背景**: Pipeline 也有状态和流程，看起来像领域对象

**选项**:
- A) Pipeline 作为聚合根（持久化 Pipeline 状态）
- B) Pipeline 作为流程编排器（轻量级，不持久化核心状态）

**选择**: B) 流程编排器

**理由**:
1. **Pipeline 描述过程，不拥有业务数据**: 它说"怎么做"，不是"是什么"
2. **状态短暂**: 执行完就结束，不像 Environment 长期存在
3. **高可替换性**: 今天 Jenkins 明天 GitLab CI，不影响领域模型
4. **DDD 原则**: 聚合根代表业务核心概念，Pipeline 是基础设施关注点

**影响**:
- Pipeline 配置可以存在 YAML 文件或配置中心
- Pipeline 执行历史可以单独记录（非核心领域）

**日期**: 2026-05-17 | **状态**: ✅ 已实施

## ADR-004: 插件化基础设施架构

**背景**: 底层应该用 Docker Compose 还是 K8s？还是都要支持？

**选项**:
- A) 只用 Docker Compose（简单但不可扩展）
- B) 只用 K8s（强大但复杂度高）
- C) 插件化架构（InfrastructureProvider 接口）

**选择**: C) 插件化架构

**理由**:
1. **渐进式演进**: 先实现 ComposeProvider，后续加 KubernetesProvider
2. **多环境适配**: 个人用 Compose，企业用 K8s，同一套上层 API
3. **学习价值**: 理解抽象层设计的权衡
4. **测试友好**: 可以 Mock Provider 进行单元测试

**接口定义**:
```java
public interface EnvironmentProvisioner {
    Mono<Environment> provision(EnvironmentSpec spec);
    Mono<Void> teardown(EnvironmentId id);
    Mono<EnvironmentStatus> checkStatus(EnvironmentId id);
}
```

**当前实现**: DockerComposeProvider（Phase 2）

**日期**: 2026-05-17 | **状态**: ✅ 已实施

## ADR-005: 声明式实验生命周期管理

**背景**: 如何确保实验环境不会长期占用资源？

**选项**:
- A) 纯手动（用户自己记得清理）
- B) 定时任务扫描过期实验
- C) 实验创建时声明最大存活时间，系统自动清理

**选择**: C) 声明式生命周期

**理由**:
1. **符合云原生理念**: 声明期望状态，系统负责维持
2. **防止资源泄漏**: 即使忘记清理，系统也会回收
3. **灵活配置**: 不同实验可以有不同的存活时间
4. **可观测**: 用户可以看到即将过期的实验

**默认策略**:
```yaml
experiment_lifecycle_policy:
  default_max_lifetime: "2小时"
  default_idle_timeout: "30分钟"
  warning_before_cleanup: "15分钟"
```

**日期**: 2026-05-17 | **状态**: ⏳ 待实施（Phase 2）

## ADR-006: 数据库选型 — PostgreSQL

**候选方案**: PostgreSQL / MySQL / MongoDB / SQLite

**选择**: PostgreSQL

**理由**:
1. **JSONB 支持**: 环境配置/服务规格等嵌套结构用 JSONB 存储最自然
2. **复杂查询能力**: CTE、Window 函数支持未来分析需求
3. **并发控制**: MVCC 机制适合多环境并行管理场景
4. **扩展性**: PostGIS、TimescaleDB 插件为未来监控功能预留空间
5. **Spring Boot 生态**: Spring Data JPA 对 PostgreSQL 支持完善

**关键应用场景**:
```sql
CREATE TABLE environments (
    id UUID PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    services JSONB,
    resource_quota JSONB
);

SELECT * FROM environments 
WHERE status = 'RUNNING' 
AND services @> '[{"template": "nacos-server"}]';
```

**日期**: 2026-05-17 | **状态**: ✅ 已实施

## ADR-007: WebFlux 纯响应式架构

**选项**:
- A) Spring MVC（传统同步阻塞）
- B) WebFlux（响应式非阻塞）
- C) 混合模式

**选择**: B) WebFlux（纯响应式）

**理由**:
1. **场景匹配性高**:
   - Ansible 执行: 耗时操作(30s~5min)，非阻塞等待
   - Docker 日志流: 实时数据推送，WebSocket/SSE 天然支持
   - 并发部署: Event Loop 效率更高
2. **性能优势**: 少量线程处理大量连接，背压机制防过载
3. **学习价值**: 响应式编程是现代 Java 趋势（Spring 6 默认）
4. **生态兼容**: Spring Data R2DBC、Spring Cloud Gateway、WebClient

**权衡与缓解**:
| 风险 | 缓解措施 |
|------|---------|
| 学习曲线 | 先从简单 CRUD 开始，渐进式学习 |
| 调试难度 | 使用 BlockHound 检测阻塞操作 |
| 库兼容性 | 必要时用 `Mono.fromFuture()` 包装 |

**日期**: 2026-05-17 | **状态**: ✅ 已实施

## ADR-009: Lombok + MapStruct 使用规范

**Lombok 规范**:
- ✅ 允许使用: `@Getter`, `@Setter`, `@Builder`, `@NoArgsConstructor`, `@AllArgsConstructor`
- ❌ **禁止在实体类使用**: `@Data`（破坏封装性）
- ⚠️ 必须安装 IDE 插件
- 📌 推荐值对象使用: `@Value`（不可变对象）

**MapStruct 规范**:
- ✅ 用于 DTO 转换: Domain Object ↔ VO/DTO
- ✅ 启用 Spring 组件模式: `@Mapper(componentModel = "spring")`
- ❌ 不用于简单对象: 字段 < 5 个且无特殊映射规则时手写即可

**理由**:
1. **编译时代码生成**: 无运行时反射开销（优于 BeanUtils.copyProperties）
2. **类型安全**: 编译期检查字段匹配（避免运行时错误）
3. **声明式映射**: 复杂转换逻辑集中管理

**日期**: 2026-05-17 | **状态**: ✅ 已实施

## ADR-011: 采用 MCP 协议作为 AI 交互层

**背景**: 现有 REST API 要求用户手写 JSON/YAML 配置来定义实验蓝图、部署策略，配置过程与编码一样复杂。

**决策**: 在现有 REST API 之上引入 **MCP (Model Context Protocol) Server 层**，作为 AI Agent 与 DevOps 能力的标准化交互协议。

**理由**:
1. **意图驱动**: 用户通过自然语言描述意图，AI 调用 MCP Tools 逐步执行
2. **工具发现**: MCP Resources 让 AI 实时发现当前基础设施状态
3. **生态兼容**: 支持 Claude Desktop、Trae、Kimi 等任何 MCP Client
4. **渐进增强**: REST API 继续存在，MCP 是附加层，非替代层

**影响**:
- 新增 `mcp-server` 模块，依赖 `io.modelcontextprotocol.sdk:mcp-server-spring-webflux`
- 核心领域服务保持不变，通过 Adapter 暴露为 MCP Tools

**日期**: 2026-05-22 | **状态**: 🔄 实施中

## ADR-012: 保守式交互 — AI 仅作为向导

**背景**: MCP 的强大能力可能导致 AI 过度自信：自动选择节点、自动推断端口、自动执行不可逆操作。

**决策**: **AI 角色限定为 "交互式向导"，所有写操作必须经过用户显式确认。**

**原则**:
1. **发现优先**: AI 必须先调用只读 Resources 获取真实状态，再呈现选项
2. **逐步确认**: 每个 Tool 调用前向用户展示完整参数清单，等待确认
3. **无默认推断**: 不能默认用 Docker/默认端口/默认内存，必须询问
4. **二元决策**: 用户的选择应该是选择题或确认题，非开放式配置

**影响**:
- Prompts 设计中加入 `conservative_experiment_wizard` 系统提示词
- Tool 设计保持原子化，禁止粗粒度"一键完成实验"

**日期**: 2026-05-22 | **状态**: 🔄 实施中

## ADR-013: 三层角色分离 — MCP Host / Target Host / Loadgen Host

**背景**: MCP Server 运行的机器不一定是部署目标，也不一定是压测发起端。同机压测将导致结果失真。

**决策**: 引入 **Host 角色模型**，明确区分三种角色：
- **MCP Host**: 运行 MCP Server 进程（通常是 Fedora Dev VM）
- **Target Host**: 实际承载环境/服务的宿主机
- **Loadgen Host**: 执行压测工具的机器，必须独立于 Target Host

**原则**:
1. **显式绑定**: `env_create` 必须指定 `target_host_id`；`test_load` 必须指定 `loadgen_host_id`
2. **角色校验**: Tool 执行前校验 Host 的 `roles` 字段
3. **压测隔离**: `test_load` 禁止 loadgen 与 target 为同一主机（除非用户显式覆盖）

**影响**:
- 新增 `Host` 领域对象，高于 `Environment`
- `Environment` 增加 `hostId` 字段
- 新增 `LoadgenExecutor`，通过 SSH 在远端 Host 执行压测命令

**日期**: 2026-05-22 | **状态**: 🔄 实施中

## ADR-014: 层次化主机拓扑 — 表达 PVE → VM → Docker 嵌套

**背景**: 基础设施是层次化的：PVE 宿主机 → 虚拟机 → (可选) Docker Daemon。扁平化节点列表会丢失层次信息。

**决策**: `Host` 对象引入 `parent_id` 和 `type` 字段，构建树形拓扑。

**层次定义**:
```
pve-hypervisor (根)
└── vm (虚拟机)
    └── docker (可选，作为运行时属性而非独立 Host)
```

**原则**:
1. **父子关系**: `vm` 的 `parent_id` 指向 `pve-hypervisor`
2. **网络区域**: `network_zone` 标识虚拟网络边界
3. **能力声明**: `capabilities: [docker, native, vm]`

**影响**:
- 新增 `HostRegistry`（内存 + 配置文件驱动）
- `analyze_network_path` Tool 基于拓扑推理，而非实际 traceroute

**日期**: 2026-05-22 | **状态**: 🔄 实施中

## ADR-015: 原子化 Tool 设计 — 禁止粗粒度封装

**背景**: 如果提供 `run_experiment` 这种粗粒度 Tool，AI 可能一次性完成"创建+部署+测试+收集证据"，违背保守交互原则。

**决策**: **所有 MCP Tools 保持原子化，单一职责，显式参数。**

**分类**:
| 类别 | 示例 | 职责 |
|------|------|------|
| **发现** | `hosts://topology`, `templates://list` | 只读，暴露当前状态 |
| **环境** | `env_create`, `env_deploy_service`, `env_destroy` | 环境生命周期 |
| **测试** | `test_health_check`, `test_functional`, `test_load` | 原子测试操作 |
| **诊断** | `test_stream_logs`, `test_exec_command`, `analyze_network_path` | 排查与验证 |

**影响**:
- `ExperimentBlueprint` 自动生成逻辑转移到 AI Client 侧（通过多轮对话逐步组装）
- MCP Server 只提供"积木"，不组装"模型"

**日期**: 2026-05-22 | **状态**: 🔄 实施中

## ADR-016: 网络路径感知 — 压测可信度分析

**背景**: 虚拟化环境下，同 PVE 宿主机内的 VM 间通信仅经 Linux Bridge，不过物理网卡。压测结果可能过于乐观。

**决策**: 引入 `analyze_network_path` Tool，在压测前进行网络拓扑分析。

**路径类型**:
| 类型 | 说明 | 可信度提示 |
|------|------|-----------|
| `same-host` | 同机 | ⚠️ 共享 CPU/内存/回环网络，结果失真 |
| `same-hypervisor` | 同 PVE 下不同 VM | ⚠️ 仅经虚拟交换机，未过物理网卡 |
| `same-lan` | 同局域网不同物理机 | ✅ 正常局域网压测 |
| `wan` | 跨网络/VPN | ⚠️ 延迟显著 |

**影响**:
- `Host` 对象增加 `network_zone` 字段
- `analyze_network_path` 成为 `test_load` 的前置推荐步骤

**日期**: 2026-05-22 | **状态**: 🔄 实施中

## ADR-017: 分层证据收集 — 自动采集 + 手动补充

**背景**: 完全手动录入负担重；完全自动收集又可能遗漏人工观察。

**决策**: **分层证据收集**: 监控指标自动采，功能验证自动采，人工观察点需用户确认。

**原则**:
1. **自动证据**: `test_load` 输出 QPS/延迟/错误率；`test_collect_metrics` 采 CPU/内存
2. **半自动证据**: `test_functional` 输出布尔结果
3. **手动证据**: `submit_evidence_note` 录入文本，用户确认后调用
4. **证据归属**: 所有证据关联到 `env_id` 或 `run_id`

**影响**:
- 新增 `EvidenceCollector` 领域服务
- `ExperimentSession` 作为证据聚合容器

**日期**: 2026-05-22 | **状态**: 🔄 实施中

## ADR-018: 模板化服务部署 — 不手写 Docker Compose

**背景**: 部署 Nacos、MySQL、Redis 时，端口、环境变量、健康检查端点应该内置于系统。

**决策**: 保留并增强现有 `ServiceTemplate` 机制，通过 `templates://list` Resource 暴露给 AI。

**模板内容**:
- `display_name`, `category`, `versions`
- `default_ports`: 容器端口与建议宿主机端口映射
- `configurable_params`: 可覆盖的环境变量列表
- `requirements`: 最低/推荐资源
- `dependencies`: 依赖的其他模板
- `health_check`: 默认健康检查端点

**影响**: 现有 `service-templates.yml` 直接复用

**日期**: 2026-05-22 | **状态**: 🔄 实施中

## ADR-019: 状态机与并发安全 — WebFlux 响应式保持

**背景**: 现有系统基于 Spring WebFlux + Reactor。MCP 层引入后不能退化为阻塞模型。

**决策**: **MCP Server 层继续使用 WebFlux，所有异步操作返回 `Mono<T>` 或 `Flux<T>`。**

**原则**:
1. **非阻塞 I/O**: SSH 远程命令、Docker API、日志流全部使用 Netty/Reactor
2. **背压控制**: `stream_logs` 等流式 Tool 支持背压，防内存堆积
3. **超时控制**: 每个 Tool 调用必须有超时（默认 30s，压测类 300s）

**影响**:
- MCP SDK 选择 `mcp-server-spring-webflux` 适配器
- 远程命令执行使用 `reactor-netty` 或 `jsch` 异步封装

**日期**: 2026-05-22 | **状态**: 🔄 实施中

## ADR-020: 渐进改造 — 双轨运行，不破坏现有 API

**背景**: 现有 DevOps Dashboard 已有 REST API、Swagger UI。MCP 化不能一次性推翻重来。

**决策**: **MCP Server 作为独立模块（`mcp-server`）运行，与现有 `web-api` 模块共存。**

**改造路径**:
1. **Phase 1**: 新增 `mcp-server` 模块，只暴露发现类 Resources + 只读类 Tools。REST API 继续承载写操作
2. **Phase 2**: 逐步将写操作以 MCP Tool 形式暴露，REST API 保留用于前端
3. **Phase 3**: 前端也接入 MCP（可选），REST API 降级为内部通信协议

**影响**:
- 代码层面：新增 `mcp` package，不修改 `domain`、`infrastructure` 核心包
- 部署层面：可独立启动（端口 8081），也可同进程（端口 8080 `/mcp/sse`）

**日期**: 2026-05-22 | **状态**: 🔄 实施中
