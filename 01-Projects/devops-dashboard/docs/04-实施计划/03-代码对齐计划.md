# 代码对齐计划 —— 按术语表统一命名

> **目标**: 消除代码与 `00-术语表.md`、`03-接口契约/02-MCP-Tools.md` 之间的命名偏差。
> **教训来源**: V2→V3 因文档重写后未同步修改代码，导致 `type`/`runtime`/`serviceName` 三处核心命名在文档、Schema、代码中各说各话。
> **执行原则**: 见下文「防退化六条」，任何 Agent 执行本计划前必须先阅读。

---

## 一、防退化六条（V2→V3 教训总结）

| # | 规则 | 违反后果 |
|---|------|---------|
| 1 | **术语表唯一权威** | 任何命名争议以 `00-术语表.md` 为准，禁止用「代码里已经这么写了」作为理由保留旧名 |
| 2 | **全栈同改** | 一个字段改名必须同时改：DTO → Handler → Service → Domain → Entity → DB Column（如需）→ Test，禁止局部重构 |
| 3 | **测试同提交** | 生产代码与测试代码必须在同一个 commit 内完成，禁止「先改代码，测试以后补」 |
| 4 | **grep 清零** | 修改完成后必须 `grep` 旧命名，确认仓库内零残留（含注释、日志字符串、私有方法名） |
| 5 | **Schema 即契约** | `03-接口契约/02-MCP-Tools.md` 中的 JSON Schema 是外部不可变契约，代码只能向 Schema 对齐，不能反过来改 Schema 迁就代码 |
| 6 | **先读后动** | 开始修改前必须重新阅读本计划指定的「相关文件」列表，禁止凭记忆编码 |

---

## 二、核心命名偏差总览

当前代码与 Schema / 术语表的四处关键偏差：

| 外部 Schema 参数 | 当前代码字段名 | 当前代码领域名 | 术语表规定 | 偏差说明 |
|-----------------|--------------|--------------|-----------|---------|
| `environmentType` | `EnvCreateRequest.type` | `EnvironmentType` (枚举) | `environmentType` | 代码用 `type` 表示环境业务用途，与 Schema 的 `environmentType` 不一致 |
| `isolationType` | `EnvCreateRequest.runtime` | `RuntimeType` (枚举) | `isolationType` | 代码用 `runtime` 表示 docker/native 隔离类型，与 Schema 的 `isolationType` 不一致 |
| `runtimeConstraint` | 无 | 无 | `runtimeConstraint` (String) | Schema 有，代码完全缺失 |
| `serviceName` | `EnvDeployRequest.templateName` | `ServiceManifest.templateName` | `serviceName` | 代码用 `templateName`，Schema 用 `serviceName` |

> **历史注**: 上述偏差在 `03-接口契约/02-MCP-Tools.md` 第 157 行已明确标注为已知问题，本计划负责将其清零。

## 六、禁止行为（会复现 V2→V3 错误）

- ❌ 只改 DTO 不改 Domain / Entity
- ❌ 只改代码不改测试
- ❌ 保留旧字段名作为 `@Deprecated` 兼容（增加复杂度，本系统无外部 API 消费者需要兼容）
- ❌ 修改 Schema 来迁就代码（Schema 是 AI 契约，不可变）
- ❌ 用 `type` 作为任何字段名前缀以外的独立字段名（`type` 在术语表中是禁用词）
- ❌ 提交代码前未执行「验证 Checklist」
