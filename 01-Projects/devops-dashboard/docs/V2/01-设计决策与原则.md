## ADR-MCP-001: 采用 MCP 协议作为 AI 交互层

### 背景
现有 DevOps Dashboard 提供 REST API，但用户（开发者）需要手动编写 JSON/YAML 配置来定义实验蓝图、部署策略、测试协议。配置过程与编码一样复杂，违背了"快速验证"的初衷。

### 决策
在现有 REST API 之上引入 **MCP (Model Context Protocol) Server 层**，作为 AI Agent 与 DevOps 能力的标准化交互协议。

### 理由
1. **意图驱动**: 用户通过自然语言描述意图，AI 调用 MCP Tools 逐步执行，无需手写复杂配置。
2. **工具发现**: MCP 的 Resources 机制让 AI 能实时发现当前基础设施状态（可用节点、模板、环境），避免基于静态知识推断。
3. **生态兼容**: 支持 Claude Desktop、Trae、Kimi 等任何 MCP Client，不绑定单一 AI 产品。
4. **渐进增强**: REST API 继续存在，MCP 是附加层，非替代层。

### 影响
- 新增 `mcp-server` 模块，依赖 `io.modelcontextprotocol.sdk:mcp-server-spring-webflux`
- 现有 `EnvironmentService`、`ExperimentService` 等核心领域服务保持不变，通过 Adapter 暴露为 MCP Tools

## ADR-MCP-002: 保守式交互 — AI 仅作为向导，不自动推断

### 背景
MCP 的强大能力可能导致 AI 过度自信：自动选择节点、自动推断端口、自动执行不可逆操作（销毁环境）。这在基础设施操作中是危险的。

### 决策
**AI 角色限定为 "交互式向导"，所有写操作必须经过用户显式确认。**

### 原则
1. **发现优先**: AI 必须先调用只读 Resources（`hosts://topology`, `templates://list`）获取真实状态，再呈现选项。
2. **逐步确认**: 每个写操作 Tool 调用前，AI 必须向用户展示完整参数清单，等待 "确认/执行/yes"。
3. **无默认推断**: 用户说 "部署 Nacos"，AI 不能默认用 Docker/默认端口/默认内存。必须询问。
4. **二元决策**: 用户的选择应该是选择题（A/B/C）或确认题，而非开放式配置。

### 影响
- Prompts 设计中加入 `conservative_experiment_wizard` 系统提示词，约束 AI 行为。
- Tool 设计保持原子化，禁止粗粒度 "一键完成实验" 的 Tool。

## ADR-MCP-003: 三层角色分离 — MCP Host / Target Host / Loadgen Host

### 背景
MCP Server 进程运行的机器（MCP Host）不一定是部署目标，也不一定是压测发起端。压测端与被测端同机/同宿主机将导致结果失真。

### 决策
引入 **Host 角色模型**，明确区分三种角色：
- **MCP Host**: 运行 MCP Server 进程，通常是你的 Fedora Dev VM。
- **Target Host**: 实际承载环境/服务的宿主机，可以是 VM 内的 Docker Daemon、独立 VM、裸金属。
- **Loadgen Host**: 执行压测工具的机器，必须独立于 Target Host。

### 原则
1. **显式绑定**: `env_create` 必须指定 `target_host_id`；`test_load` 必须指定 `loadgen_host_id`。
2. **角色校验**: Tool 执行前校验 Host 的 `roles` 字段是否包含所需角色。
3. **压测隔离**: `test_load` 禁止 `loadgen_host_id` 与目标服务所在 `target_host_id` 相同（除非用户显式覆盖并知晓风险）。

### 影响
- 新增 `Host` 领域对象，高于 `Environment`。
- `Environment` 增加 `hostId` 字段，明确归属。
- 新增 `LoadgenExecutor`，通过 SSH 在远端 Host 执行压测命令。

## ADR-MCP-004: 层次化主机拓扑 — 表达 PVE → VM → Docker 嵌套

### 背景
你的基础设施是层次化的：PVE 宿主机 → 虚拟机 → (可选) Docker Daemon。扁平化的节点列表会丢失这种层次，导致 AI 无法判断 "流量是否经过物理网卡"、"资源是否共享同一宿主机"。

### 决策
`Host` 对象引入 `parent_id` 和 `type` 字段，构建树形拓扑。

### 层次定义
```
pve-hypervisor (根)
└── vm (虚拟机)
    └── docker (可选，作为运行时属性而非独立 Host)
```

### 原则
1. **父子关系**: `vm` 的 `parent_id` 指向 `pve-hypervisor`；`docker` 不作为独立 Host，而是 Target Host 的 `capabilities` 之一。
2. **网络区域**: `network_zone` 标识虚拟网络边界，用于 `analyze_network_path` 推理。
3. **能力声明**: `capabilities: [docker, native, vm]` 表明该 Host 支持哪些运行时。

### 影响
- 新增 `HostRegistry`（内存 + 配置文件驱动），维护节点层次。
- `analyze_network_path` Tool 基于拓扑推理（比较 parent_id + network_zone），而非实际 traceroute。

## ADR-MCP-005: 原子化 Tool 设计 — 禁止粗粒度封装

### 背景
如果提供 `run_experiment` 这种粗粒度 Tool，AI 可能一次性完成"创建环境+部署服务+执行测试+收集证据"，违背了保守交互原则。

### 决策
**所有 MCP Tools 保持原子化，单一职责，显式参数。**

### 分类
| 类别 | 示例 | 职责 |
|------|------|------|
| **发现** | `hosts://topology`, `templates://list` | 只读，暴露当前状态 |
| **环境** | `env_create`, `env_deploy_service`, `env_destroy` | 环境生命周期 |
| **测试** | `test_health_check`, `test_functional`, `test_load`, `test_collect_metrics` | 原子测试操作 |
| **诊断** | `test_stream_logs`, `test_exec_command`, `analyze_network_path` | 排查与验证 |

### 影响
- `ExperimentBlueprint` 的自动生成逻辑从 MCP Server 移除，转移到 AI Client 侧（通过多轮对话逐步组装）。
- MCP Server 只提供 "积木"，不组装 "模型"。

## ADR-MCP-006: 网络路径感知 — 压测可信度分析

### 背景
虚拟化环境下，同 PVE 宿主机内的 VM 间通信仅经过 Linux Bridge，不经过物理网卡。压测结果可能过于乐观，无法代表生产环境。

### 决策
引入 `analyze_network_path` Tool，在压测前强制进行网络拓扑分析。

### 路径类型
| 类型 | 说明 | 可信度提示 |
|------|------|-----------|
| `same-host` | 压测端与被测端在同一台机器 | ⚠️ 共享 CPU/内存/回环网络，结果失真 |
| `same-hypervisor` | 同一 PVE 下的不同 VM | ⚠️ 仅经过虚拟交换机，未经过物理网卡 |
| `same-lan` | 同一局域网，不同物理机 | ✅ 正常局域网压测 |
| `wan` | 跨网络/VPN | ⚠️ 延迟显著，适合测广域网表现 |

### 影响
- `Host` 对象增加 `network_zone` 字段。
- `analyze_network_path` 成为 `test_load` 的前置推荐步骤（非强制，但 AI Prompt 要求必须提示）。

## ADR-MCP-007: 证据收集 — 自动采集 + 手动补充

### 背景
实验需要证据支撑结论，但完全手动录入负担重；完全自动收集又可能遗漏人工观察（如 "控制台 UI 是否卡顿"）。

### 决策
**分层证据收集**: 监控指标自动采，功能验证自动采，人工观察点必须用户确认。

### 原则
1. **自动证据**: `test_load` 自动输出 QPS/延迟/错误率；`test_collect_metrics` 自动采 CPU/内存/网络。
2. **半自动证据**: `test_functional` 输出布尔结果（通过/失败）。
3. **手动证据**: `test_manual_observation`（预留）要求用户确认后 AI 调用 `submit_evidence_note` 录入文本。
4. **证据归属**: 所有证据必须关联到 `env_id` 或 `run_id`，确保可追溯。

### 影响
- 新增 `EvidenceCollector` 领域服务，统一结构化证据数据。
- `ExperimentRun`（或 `ExperimentSession`）作为证据聚合容器。

## ADR-MCP-008: 模板化服务部署 — 不手写 Docker Compose

### 背景
部署 Nacos、MySQL、Redis 等中间件时，端口、环境变量、健康检查端点、资源默认值应该内置于系统，而非每次手动指定。

### 决策
保留并增强现有 `ServiceTemplate` 机制，通过 `templates://list` Resource 暴露给 AI。

### 模板内容
- `display_name`, `category`, `versions`
- `default_ports`: 容器端口与建议宿主机端口映射
- `configurable_params`: 可覆盖的环境变量列表
- `requirements`: 最低/推荐资源
- `dependencies`: 依赖的其他模板（如 Nacos 集群依赖 MySQL）
- `health_check`: 默认健康检查端点

### 影响
- 现有 `service-templates.yml` 直接复用。
- AI 通过 `templates://{template_id}` Resource 获取详情，向用户展示可配置项。

## ADR-MCP-009: 状态机与并发安全 — WebFlux 响应式保持

### 背景
现有系统基于 Spring WebFlux + Reactor。MCP 层引入后不能退化为阻塞模型，尤其日志流式传输（`stream_logs` 返回 `Flux<String>`）。

### 决策
**MCP Server 层继续使用 WebFlux，所有异步操作返回 `Mono<T>` 或 `Flux<T>`。**

### 原则
1. **非阻塞 I/O**: SSH 执行远程命令、Docker API 调用、日志流全部使用 Netty/Reactor。
2. **背压控制**: `stream_logs` 等流式 Tool 支持背压，防止 AI Client 消费慢导致内存堆积。
3. **超时控制**: 每个 Tool 调用必须有超时（默认 30s，压测类 300s）。

### 影响
- MCP SDK 选择 `mcp-server-spring-webflux` 适配器。
- 远程命令执行使用 `reactor-netty` 或 `jsch` 的异步封装。

## ADR-MCP-010: 渐进改造 — 双轨运行，不破坏现有 API

### 背景
现有 DevOps Dashboard 已有 REST API、Swagger UI、前端页面。MCP 化不能一次性推翻重来。

### 决策
**MCP Server 作为独立模块（`mcp-server`）运行，与现有 `web-api` 模块共存。**

### 改造路径
1. **Phase 1**: 新增 `mcp-server` 模块，只暴露发现类 Resources + 只读类 Tools。REST API 继续承载所有写操作。
2. **Phase 2**: 逐步将写操作（`env_create`, `test_load`）以 MCP Tool 形式暴露，REST API 保留用于前端。
3. **Phase 3**: 前端也接入 MCP（可选），REST API 降级为内部通信协议。

### 影响
- 代码层面：新增 `mcp` package，不修改 `domain`、`infrastructure` 核心包。
- 部署层面：可独立启动 MCP Server（端口 8081），也可与主应用同进程（端口 8080 增加 `/mcp` 路径）。

## 附录: 设计原则速查表

| 原则 | 一句话说明 |
|------|-----------|
| **保守交互** | AI 只向导，不决策；每步确认 |
| **原子工具** | 一 Tool 一职责，不封装流程 |
| **发现优先** | 先查 Resources，再呈现选项 |
| **角色分离** | MCP / Target / Loadgen 三者显式区分 |
| **层次拓扑** | PVE → VM → Docker 父子关系必须表达 |
| **网络感知** | 压测前分析路径，提示可信度 |
| **响应式保持** | WebFlux 非阻塞，流式日志背压 |
| **渐进改造** | MCP 附加层，不破坏 REST API |
