# V3 架构决策记录 (ADR-021 ~ ADR-028)

> 本文档记录 DevOps Dashboard 从 V2（原子化 MCP 工具集）到 V3（聚合根入口 + 反退化约束）的关键架构决策。
>
> **前置**: V2 的 ADR-011~020 继续有效，V3 在其基础上增加约束层。

---

## ADR-021: 聚合根作为 MCP 入口 — 新增 DeployPipeline 与 LogAggregate

### 背景

V2 提供了 15 个原子化 Tools，AI 可以自由组合。但这也导致 AI 在需要完整部署流程时，倾向于手动拆解步骤（先 env_create，再 env_deploy_service...），甚至绕过 MCP 在本地执行 docker/ssh。

### 决策

**将 MCP Toolset 重构为部署领域的聚合根。新增 `DeployPipeline`（编排聚合根）和 `LogAggregate`（日志聚合根）。**

### 新增聚合根

```java
// DeployPipeline — 首选入口，封装完整部署流水线
DeployPipeline
├── deploy_pipeline (tool)
│   ├── 内部协调: env_create → env_deploy_service → test_health_check → analyze_network_path
│   ├── 原子性: 任何子步骤失败即整体失败，触发补偿清理
│   └── 语义: 【首选入口】禁止 AI 手动分步调用子工具

// LogAggregate — 闭环排查，替代 SSH + docker logs
LogAggregate
├── env_get_logs (tool)
│   ├── 输入: envId (来自 env_list)
│   ├── 能力: 实时/历史日志、按服务筛选、行数控制
│   └── 语义: 【唯一合法日志源】
```

### 理由

1. **语义引导**: 聚合根的描述携带强烈的"入口"语义，AI 在决策时会优先选择聚合根而非自行组合
2. **原子性保障**: `deploy_pipeline` 内部失败时自动回滚已创建的资源，避免半成品环境
3. **封堵替代路径**: `env_get_logs` 提供与 SSH 同等能力（实时/历史/筛选），使 AI 没有绕过理由
4. **与 V2 兼容**: `env_create`、`env_deploy_service` 等底层工具继续存在，只是从"直接暴露"变为"聚合根内部调用"

### 影响

- 新增 `domain/mcp/DeployPipeline.java`、`domain/mcp/LogAggregate.java`（或放在现有 domain 包下）
- `mcp/handler/` 新增 `PipelineHandler.java`、`LogHandler.java`
- `tools/list` 返回的 Tool 数量从 15 精简为 10（移除部分细粒度 Tools）

**日期**: 2026-05-23 | **状态**: 📝 设计中

## ADR-022: 禁止 AI 本地替代 — Description 三段式 + Error Forbidden 字段

### 背景

V2 的工具 description 是"功能说明"风格，如："在指定的 Target Host 上创建一个新的空环境。" AI 可能认为"这不就是个 docker run 包装吗？我自己也能做。"

### 决策

**每个工具的 `description` 必须按三段式编写，错误响应必须包含 `forbidden` 字段。**

### 三段式模板

```markdown
【角色标签】功能一句话。
技术价值一句话（为什么必须走我）。
错误示例：❌ 禁止 ... 这将导致 ...
```

### 角色标签规范

| 标签 | 用途 | 示例工具 |
|------|------|---------|
| `【首选入口】` | 高层编排聚合根，AI 应该优先调用 | `deploy_pipeline` |
| `【唯一入口】` | 不可替代，所有同类操作必须经过此 | `env_create`, `env_get_logs`, `test_exec_command` |
| `【唯一合法】` | 审计类工具，本地替代会导致结果失真 | `test_health_check`, `test_load`, `analyze_network_path` |

### 错误响应封堵格式

```json
{
  "error": {
    "data": {
      "forbidden": "禁止本地执行 docker/ssh/curl 替代",
      "nextSteps": ["env_get_logs", "test_health_check"]
    }
  }
}
```

### 理由

1. **心理锚点**: 在 AI 的上下文中植入"禁止本地操作"的明确否定，降低绕过概率
2. **回退路径**: `nextSteps` 告诉 AI 合法的 MCP 内回退方案，避免 AI "创新"出本地替代
3. **可审计**: 所有操作都经过 MCP，日志统一、敏感信息脱敏

### 影响

- 重写全部 10 个工具的 `description`
- 统一错误响应封装类 `MCPErrorResponse`
- Server 初始化时发送约束 Prompt（另附）

**日期**: 2026-05-23 | **状态**: 📝 设计中

## ADR-023: Environment 状态机精化 — 引入 READY / DEPLOYING / ERROR

### 背景

V2 的 Environment 状态为：`CREATING, RUNNING, STOPPED, DESTROYED, FAILED, NOT_FOUND`。在实际部署流程中发现：
- 环境创建成功但尚未部署服务时，标记为 `RUNNING` 不够精确
- 部署进行中没有中间状态，AI 可能在此期间重复调用部署
- `FAILED` 语义模糊（创建失败？部署失败？健康检查失败？）

### 决策

**Environment 状态精化为：CREATING → READY → DEPLOYING → RUNNING → DESTROYED，异常统一为 ERROR。**

### 状态定义

| 状态 | 含义 | 允许的操作 |
|------|------|-----------|
| `CREATING` | env_create 已调用，初始化中 | 无（等待） |
| `READY` | 环境就绪，允许部署 | env_deploy_service, env_destroy |
| `DEPLOYING` | 部署已锁定，进行中 | 无（等待） |
| `RUNNING` | 部署成功，健康检查通过 | test_*, env_get_logs, env_destroy |
| `ERROR` | 部署或检查失败，需排查 | env_get_logs（排查）, env_destroy（清理） |
| `DESTROYED` | 终态，资源已释放 | 无 |

### 状态转换规则

```
CREATING  → READY | ERROR
READY     → DEPLOYING | DESTROYED
DEPLOYING → RUNNING | ERROR
RUNNING   → DESTROYED | DEPLOYING (覆盖部署)
ERROR     → DESTROYED | READY (修复后)
DESTROYED → (终态)
```

### 理由

1. **精确表达中间态**: `READY` 明确表示"环境空壳已好，等服务"，`DEPLOYING` 防止并发部署
2. **统一异常态**: `ERROR` 表示"需要排查"，不区分错误来源，排查后可通过修复回到 READY
3. **支持覆盖部署**: `RUNNING → DEPLOYING` 允许版本升级，无需先销毁

### 影响

- 修改 `domain/environment/EnvironmentStatus.java`
- `env_deploy_service` 调用前校验状态必须是 `READY` 或 `RUNNING`
- 状态转换时加分布式锁（防止 AI 并发调用竞态）
- 非法状态转换返回：`当前状态为 X，不允许 Y 操作。必须先执行 Z。`

**日期**: 2026-05-23 | **状态**: 📝 设计中

## ADR-024: 参数数据源约束 — 所有 ID 类参数必须声明来源

### 背景

V2 的参数描述如：`"目标宿主机 ID"`。AI 容易编造 ID（如 `vm-ubuntu-test-01` 而非 `vm-ubuntu-test`），导致 `HostNotFoundException`。

### 决策

**每个参数描述必须包含"数据源指向"，枚举字段必须列出全部合法值。**

### 规范

| 参数类型 | 描述模板 | 示例 |
|---------|---------|------|
| ID 类 | `必须来自 {tool} 返回的 {field} 字段` | `必须来自 env_list 返回的 id 字段` |
| 枚举类 | 必须列出全部 enum 值 | `enum: ["docker", "native"]` |
| 版本类 | 给出格式示例 | `如 '1.0-SNAPSHOT'、'latest'、'sha-7a3f2b'` |
| ID 格式 | 声明格式约束 | `只允许小写字母、数字和连字符 [a-z0-9-]` |

### 示例对比

**V2 (不规范)**:
```json
"target_host_id": { "type": "string", "description": "目标宿主机 ID" }
```

**V3 (规范)**:
```json
"targetHostId": {
  "type": "string",
  "description": "目标宿主机 ID，必须来自 env_list 返回的 availableHosts 列表中的 id 字段"
}
```

### 理由

1. **减少编造**: AI 看到"必须来自 env_list 返回"时，会先调用 `env_list` 获取真实值
2. **自文档化**: 参数描述本身就构成了 Tool 间的依赖关系图
3. **校验依据**: Server 端可根据描述实现参数来源校验（如 envId 是否存在于当前环境列表）

### 影响

- 重写全部 10 个工具的 `inputSchema` 中所有参数的 `description`
- 为所有可枚举字段增加 `enum`

**日期**: 2026-05-23 | **状态**: 📝 设计中

## ADR-025: 服务目录校验 — env_deploy_service 的 serviceName 注册表

### 背景

V2 的 `env_deploy_service` 通过 `template_id` 选择服务模板，但模板系统与 MCP Tool 参数未完全对齐。AI 可能传入未注册的服务名。

### 决策

**Server 端维护 `ServiceRegistry` 白名单，`serviceName` 必须在注册表中。**

```java
Set<String> serviceRegistry = Set.of(
    "redis-counter-service",
    "devops-dashboard",
    "mcp-host-agent",
    "redis-cache"
);
```

### 错误响应

```json
{
  "error": {
    "code": -32000,
    "message": "服务 'unknown-service' 未在 MCP 目录注册",
    "data": {
      "availableServices": ["redis-counter-service", "devops-dashboard", "mcp-host-agent", "redis-cache"],
      "forbidden": "禁止部署未注册服务",
      "nextSteps": ["调用 env_list 查看已部署服务", "联系管理员注册新服务"]
    }
  }
}
```

### 理由

1. **防止拼写错误**: AI 可能写 `redis-couter-service`（拼写错误），白名单可拦截
2. **安全边界**: 禁止部署任意镜像，只允许经过审核的服务
3. **可扩展**: 新服务通过配置文件注册，无需改代码

### 影响

- 新增 `application/ServiceRegistry.java`（或配置驱动）
- `env_deploy_service` 处理逻辑增加注册表校验
- `tools/list` 的 `serviceName` enum 与注册表同步

**日期**: 2026-05-23 | **状态**: 📝 设计中

## ADR-026: 错误响应封堵 — forbidden + nextSteps 字段

### 背景

V2 的错误响应仅说明原因（如 `Host not found`），AI 收到错误后可能自行"解决"——通过 SSH 直连或本地执行。

### 决策

**统一错误响应格式，强制包含 `forbidden` 和 `nextSteps` 字段。**

### 错误响应规范

```json
{
  "error": {
    "code": -32000,
    "message": "业务错误简述",
    "data": {
      "currentStatus": "RUNNING",
      "requiredStatus": "READY",
      "suggestion": "调用 env_list 确认状态，或 env_get_logs 排查",
      "forbidden": "禁止本地执行 docker/ssh/curl 替代",
      "nextSteps": ["env_list", "env_get_logs", "test_health_check"]
    }
  }
}
```

### 字段说明

| 字段 | 用途 |
|------|------|
| `currentStatus` | 当前对象状态（用于状态机错误） |
| `requiredStatus` | 期望状态（用于状态机错误） |
| `suggestion` | 人可读的解决建议 |
| `forbidden` | **关键**: 明确否定本地替代方案，形成心理锚点 |
| `nextSteps` | **关键**: 给出合法的 MCP 内回退路径 |

### 理由

1. **封堵绕过**: `forbidden` 直接在 AI 上下文中否定本地操作
2. **引导回退**: `nextSteps` 告诉 AI "你应该调用这些 Tools"，而不是自行解决
3. **一致性**: 所有错误统一格式，便于 AI Client 解析和呈现

### 影响

- 新增 `mcp/error/MCPErrorResponse.java` 封装类
- 修改 `McpExceptionTranslator`，所有异常翻译为统一格式
- 每个 Tool 的 Handler 在 catch 块中补充 `forbidden` 和 `nextSteps`

**日期**: 2026-05-23 | **状态**: 📝 设计中

## ADR-027: 编排聚合根原子性 — deploy_pipeline 内部协调与失败补偿

### 背景

`deploy_pipeline` 内部需要调用多个子步骤（env_create → env_deploy_service → test_health_check → analyze_network_path）。如果中间步骤失败，已创建的资源可能成为孤儿。

### 决策

**`deploy_pipeline` 实现 Saga 模式：任何子步骤失败触发补偿清理。**

### 补偿规则

| 失败步骤 | 已完成的步骤 | 补偿操作 |
|---------|-------------|---------|
| env_create 失败 | 无 | 无 |
| env_deploy_service 失败 | env_create 成功 | env_destroy(createdEnvId) |
| test_health_check 失败 | env_create, env_deploy_service 成功 | env_destroy(createdEnvId) 或标记为 ERROR 保留排查 |
| analyze_network_path 失败 | 前述全部成功 | 仅报告警告，不清理（网络分析非致命） |

### 理由

1. **资源不泄漏**: 失败时自动清理，不产生孤儿环境
2. **可配置**: `deploy_pipeline` 参数可增加 `keepOnFailure: true` 保留失败环境用于排查
3. **幂等性**: 补偿操作必须是幂等的（`env_destroy` 对 DESTROYED 环境无操作）

### 影响

- `DeployPipeline` 内部实现 Saga 协调器
- `env_destroy` 需支持幂等调用
- `deploy_pipeline` 的 `inputSchema` 增加 `keepOnFailure` 可选参数

**日期**: 2026-05-23 | **状态**: 📝 设计中

## ADR-028: 日志聚合根闭环 — env_get_logs 替代 SSH + docker logs

### 背景

V2 的日志获取途径有二：`test_stream_logs`（MCP Tool）和 SSH 直连执行 `docker logs`。AI 在排查问题时倾向于后者，因为后者更灵活。

### 决策

**将日志获取提升为聚合根 `LogAggregate`，`env_get_logs` 成为唯一合法日志源。**

### 能力对比

| 能力 | V2 SSH+docker logs | V3 env_get_logs |
|------|-------------------|-----------------|
| 实时日志 | ✅ | ✅ |
| 历史日志 | ✅ | ✅ |
| 按服务筛选 | ✅ | ✅ |
| 行数控制 | ✅ `--tail` | ✅ `tailLines` |
| 时间范围 | ✅ `--since` | ✅ `since` |
| 日志格式统一 | ❌ 原始格式 | ✅ MCP 统一格式 |
| 敏感信息脱敏 | ❌ | ✅ |
| 审计追溯 | ❌ | ✅ |

### 理由

1. **能力对等**: `env_get_logs` 提供与 `docker logs` 完全对等的能力，AI 没有绕过理由
2. **安全增强**: 统一格式 + 脱敏，防止日志泄露敏感信息
3. **审计闭环**: 所有日志查询经过 MCP，可追溯

### 影响

- 新增 `LogAggregate` 领域对象
- `env_get_logs` 的 `serviceName` 留空时返回整个环境的聚合日志
- 废弃 V2 的 `test_stream_logs`，由 `env_get_logs` 替代

**日期**: 2026-05-23 | **状态**: 📝 设计中
