## 4. 下一步（代码实施阶段，另起计划）

设计文档完成后，代码实施按以下顺序进行：

| 阶段 | 内容 | 估计工作量 | 验收标准 |
|------|------|-----------|---------|
| **Phase A** | 新增领域对象：DeployPipeline, LogAggregate, ServiceRegistry | 1-2 天 | 领域模型编译通过 |
| **Phase B** | 改造 Environment 状态机 + 分布式锁 | 1 天 | 状态转换单元测试通过 |
| **Phase C** | 重写 MCP Handlers（10 个 Tools） | 2-3 天 | tools/list 返回正确 Schema |
| **Phase D** | 统一错误响应格式 | 0.5 天 | 所有错误包含 forbidden + nextSteps |
| **Phase E** | deploy_pipeline Saga 协调器 | 1-2 天 | 失败时自动补偿清理 |
| **Phase F** | System Instructions 集成 | 0.5 天 | Server 初始化发送约束 Prompt |
| **Phase G** | 集成测试 + 回归测试 | 1-2 天 | 现有 58 个测试全部通过 |

## 5. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| V3 文档与 V2 文档内容重复 | 维护负担 | V3 聚焦"差异"和"改造"，复用内容用引用而非复制 |
| tools-list.json 与文档不一致 | 实现偏差 | 以 `tools-list.json` 为单一数据源，文档中不做修改 |
| 状态机精化导致兼容性问题 | V2 环境状态不兼容 | 提供状态迁移脚本：FAILED→ERROR, STOPPED→DESTROYED |
| AI 仍绕过 MCP | 设计失效 | System Instructions + 错误响应封堵双重约束 |
