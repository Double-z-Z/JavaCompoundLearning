## 二、分库分表实践项目设计

### 目标

将 mybatis-sql-lab 改造为**长时间运行的 Web 服务**，通过 REST API 执行订单 CRUD、观察分片路由、执行迁移全流程、查看监控指标。

### 拓扑

```
2 分片 × 2 分表 = 4 逻辑分片
复用现有 mysql-master(3307)=ds0, mysql-slave(3308)=ds1

ds0: t_order_0, t_order_1, t_order_item_0, t_order_item_1, t_user
ds1: t_order_0, t_order_1, t_order_item_0, t_order_item_1, t_user

分片规则: user_id % 2 → 库; (user_id % 4) / 2 → 表
绑定表:   t_order ↔ t_order_item (同分片键，单分片内 JOIN)
广播表:   t_user (全分片复制)
```

### 技术栈

- Spring Boot 3.1.12 Web
- MyBatis-Plus 3.5.7
- ShardingSphere-JDBC 5.4.1（分库分表 + 读写分离叠加）
- MySQL 8.0 × 2（Docker）
- Snowflake 分布式主键（ShardingSphere 内置）
- Prometheus Actuator（分片指标暴露）

### REST API

```
# 业务 CRUD
POST   /api/orders              → 创建订单（自动路由到分片）
GET    /api/orders/{orderId}    → 查订单
GET    /api/orders?userId=5     → 按用户查（单分片）
GET    /api/orders?status=PAID  → 按状态查（广播归并）
GET    /api/orders/page?page=1&size=10 → 分页（带分片键）

# 迁移控制
POST   /api/migration/start     → 启动迁移（%2→%4 扩容模拟）
GET    /api/migration/status    → 查看迁移状态/进度
POST   /api/migration/advance?percent=30 → 推进灰度
POST   /api/migration/pause     → 暂停推进
POST   /api/migration/rollback?shard=1  → 回退指定分片
POST   /api/migration/complete  → 100% 完成，停旧写

# 监控
GET    /api/metrics/shards      → 各分片数据量/QPS
GET    /api/metrics/migration   → 迁移延迟/进度
GET    /actuator/health         → 分片连接健康

# 造数据
POST   /api/orders/batch?count=1000 → 批量写入，压测用
```

### 迁移状态机

```
IDLE ──start──→ SYNCING ──lag≈0──→ DOUBLE_WRITE ──advance(n%)──→ ADVANCING
                    ↑                      │                        │
                    │    ┌─────────────────┘                  n%<100│
                    │    │ rollback                                  │ n%=100
                    │    ▼                                          ▼
                    └─ ROLLING_BACK                           COMPLETE
```

### 灰度控制

```java
// GrayRelease.java
// 按 user_id % 100 分批迁移，不随机采样
// 每批迁移完成后，读路径切到新分片
// 未迁移用户的读永远走旧分片
```

### 监控指标体系

| 指标 | 来源 | 用途 |
|------|------|------|
| 各分片行数 | `SELECT COUNT(*)` 定时采集 | 数据分布均匀性 |
| 单分片连接池活跃数 | HikariCP MXBean | 连接池水位 |
| 迁移延迟 | 增量同步位点差 | 推进决策 |
| API 慢请求 | Actuator `http.server.requests` | 灰度异常检测 |

## 三、实施计划

| Phase | 内容 | 验证方式 |
|-------|------|---------|
| 1 | +spring-boot-starter-web → 服务长跑 | `curl localhost:8089/actuator/health` |
| 2 | 水平分片配置（分库+分表+绑定表+广播表） | `sql-show` 日志验证路由正确 |
| 3 | OrderController CRUD 全套 API | curl 创建/查询，观察分片路由 |
| 4 | 跨分片归并验证（不带分片键查询/聚合/分页） | API 返回正确合并结果 |
| 5 | MigrationController 迁移状态机 | 启动迁移 → 观察双写 → 推进灰度 |
| 6 | Snowflake 主键集成 | 验证分片内 ID 不冲突 |
| 7 | MetricsController + Prometheus Actuator | `/metrics/shards` 返回分片数据 |
| 8 | 数据迁移全流程演练 | %2→%4, 灰度 10%→100%, 回退测试 |

## 四、验收标准

1. 启动服务后 `POST /api/orders` 创建订单，日志显示正确路由到 ds0/t_order_0 或 ds1/t_order_1
2. `GET /api/orders?userId=5` 仅查一个分片
3. `GET /api/orders?status=PAID` 广播全部 4 个分片 + 正确归并
4. 迁移启动 → 灰度 10% → 30% → 100% → 完成，期间 `POST /api/orders/batch` 无数据丢失
5. 回退命令执行后分片 1 的读切回旧分片，其余分片不受影响
6. `/api/metrics/shards` 返回实时分片数据量
