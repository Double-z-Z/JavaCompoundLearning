# 本地缓存 vs 直接访问 Redis - 性能压测报告

> **测试时间**: 2026-05-10
> **测试目标**: 对比带 Caffeine 本地缓存和直接访问 Redis 的读性能差异
> **测试工具**: bombardier
> **服务器地址**: 10.0.0.142:8080

---

## 1. 背景与目标

秒杀场景下，L5 层库存查询是热点路径。引入 Caffeine 本地缓存后，可减少 Redis 网络往返，提升读性能。本次测试验证：
1. 本地缓存相比直接访问 Redis 的性能提升幅度
2. 缓存预热后的稳定性能表现
3. 延迟波动和长尾情况
4. 给出缓存使用场景的明确建议

### 场景推荐

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| **纯读操作** | 带本地缓存 | QPS 提升 50%，延迟降低 34% |
| **写操作频繁** | 直接访问 Redis | 避免缓存失效开销 |
| **一致性要求高** | 直接访问 Redis | 本地缓存存在数据同步延迟 |

## 6. 关键发现

### 发现 1：本地缓存显著提升读性能

最佳 QPS 从 64,943 提升至 97,663（**+50.4%**），平均延迟从 1.54ms 降至 1.02ms（**-33.8%**）。在 Redis 网络延迟 < 1ms 的环境下，本地缓存仍能带来如此明显的提升，说明在更高网络延迟的生产环境中收益会更大。

### 发现 2：最大延迟略有上升

带缓存的最大延迟 44.84ms 高于直接访问的 34.86ms（**+28.6%**）。这主要由缓存未命中时的回填操作导致：首次访问或缓存过期时，需要额外执行"查 Redis → 写缓存"两步操作，产生长尾延迟。

### 发现 3：延迟波动基本持平

StdDev 从 767.69μs 升至 844.07μs，增幅约 10%。说明缓存带来的性能提升是稳定的，没有引入明显的延迟抖动。

### 发现 4：命中率是关键

当前测试场景（单一 SKU、连续 10 万次请求）下缓存命中率接近 100%，因此收益最大化。实际生产环境中，缓存命中率取决于数据访问的局部性，需通过 `recordStats()` 持续监控。

## 7. 瓶颈分析

```
┌─────────────────────────────────────────────────────────────┐
│ 第一层：应用层（WebFlux 响应式处理）                           │
│   非阻塞 IO，非当前瓶颈                                      │
├─────────────────────────────────────────────────────────────┤
│ 第二层：本地缓存层（Caffeine）                               │
│   命中时：O(1) 内存访问，延迟极低                            │
│   未命中时：额外一次 Redis 往返 + HashMap 写入开销           │
├─────────────────────────────────────────────────────────────┤
│ 第三层：网络层（本机 Redis，延迟 <1ms）                       │
│   直接访问 Redis 时的主要开销来源                            │
│   带缓存时仅在未命中或过期时触发                             │
├─────────────────────────────────────────────────────────────┤
│ 第四层：Redis 服务端                                         │
│   当前负载远低于服务端上限（~22%），非瓶颈                   │
└─────────────────────────────────────────────────────────────┘
```

**关键证据**：
1. 直接访问 Redis 64K QPS vs 带缓存 97K QPS，差值 33K（33% 性能来自网络层消除）
2. 缓存命中时的 1.02ms 接近纯内存访问延迟，证明 Caffeine 本身不是瓶颈
3. Redis 服务端能力 150K+ QPS，当前 97K 仍有约 35% 余量
