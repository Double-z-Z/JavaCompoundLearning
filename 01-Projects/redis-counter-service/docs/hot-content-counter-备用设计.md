### 关键设计决策

- **决策1：本地缓存用 Guava 而非 Caffeine**
  - 选择熟悉度高的，后续可对比 Caffeine 性能差异
  - 固定容量 LRU，简单可预测

- **决策2：分层边界按"访问密度"动态调整**
  - 静态配置难以适应业务变化
  - 定时扫描，自动升降级

- **决策3：一致性采用"延迟双删"而非"双写"**
  - 延迟双删：写DB → 清缓存 → 延迟N秒 → 再清缓存
  - 适合读多写少场景，复杂度低

### 组件交互流程

```
用户请求
    ↓
[L1: 本地缓存] ← Guava Cache
    ↓ 未命中
[L2: Redis] ← 你已部署的Cluster
    ↓ 未命中/过期
[L3: MySQL] ← 业务数据库
    ↓ 读取
数据逐级回填
```

### 读写流程（Cache-Aside + 分层）

```
读：
请求 → L1查 → 未命中 → L2查 → 未命中 → L3查 → 回填L2 → 回填L1 → 返回

写：
请求 → 写L3 DB → 删除L2 Redis → 删除L1 本地缓存（延迟双删）
```


## 实现阶段

### Phase 1: 本地缓存层（L1）
**目标**: 实现基于 Guava Cache 的本地缓存层，理解"热点数据本地化"的价值

**验证方式**:
- 10万次随机读取，本地缓存命中率 > 70%（热点数据Zipf分布）
- 对比无缓存 vs 有本地缓存的QPS

**关联练习**: [[练习记录-Phase1]]（待创建）

**可能遇到的问题**:
- ⚠️ 并发回源：多个请求同时发现缓存未命中，一起查数据库
- ⚠️ 缓存容量设置不当导致频繁淘汰

---

### Phase 2: Redis热数据层（L2）+ 分层策略
**目标**: 实现 Cache-Aside 模式 + 冷热数据自动升降级

**验证方式**:
- 模拟热点集中分布（Top 10% 占 80% 流量）
- 观察 Redis 内存使用曲线
- 验证冷数据降级和热数据升级

**关联练习**: [[练习记录-Phase2]]（待创建）

**可能遇到的问题**:
- ⚠️ 分层边界模糊：不知道什么时候该从L2降级到L3
- ⚠️ 热点数据突然变冷时的"降级风暴"

---

### Phase 3: MySQL全量层（L3）+ 一致性保障
**目标**: 实现延迟双删策略，理解"缓存与数据库一致性"的挑战

**验证方式**:
- 连续写入后立即读取，验证数据一致
- 对比"双写"和"延迟双删"在不一致窗口的差异

**关联练习**: [[练习记录-Phase3]]（待创建）

**可能遇到的问题**:
- ⚠️ 边界情况：删除缓存时 Redis 恰好过期，数据被"复活"
- ⚠️ 延迟时间设置不当（太短无法覆盖脏读，太长影响性能）

---

### Phase 4（可选）: 故障降级
**目标**: 建立"设计要考虑故障"的架构思维

**验证方式**:
- 模拟 Redis 不可用（kill节点），验证降级到本地缓存
- 观察服务可用性和数据一致性

**关联练习**: [[练习记录-Phase4]]（待创建）
