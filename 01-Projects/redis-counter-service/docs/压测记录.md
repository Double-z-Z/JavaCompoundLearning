# Redis 计数器服务压测报告

---

## 背景与目标

本次压测旨在验证 Redis 计数器服务的性能上限，识别瓶颈并确定优化方向。

## 测试环境

| 组件           | IP                                | 说明          |
| ------------ | --------------------------------- | ----------- |
| 网关           | 192.168.1.1                       | 家用路由器       |
| 外部压测端        | 192.168.1.2 (Windows + WSL)       | 8C16T       |
| PVE 宿主机      | WAN: 192.168.1.7 / LAN: 10.0.0.1  | OpenWrt NAT |
| 内部压测端        | 10.0.0.110 (Debian VM)            | 2C2GB，CPU受限 |
| 应用服务器        | 10.0.0.142:8080                   | Spring Boot |
| Redis Master | 10.0.0.104:6379 / 10.0.0.103:6379 | 被测系统        |

## 测试工具

- **Redis Benchmark**：单机基准测试，验证 Redis 服务端上限
- **wrk**：轻量 HTTP 压测，获取应用层基准
- **JMeter**：复杂场景压测，支持 HTML Report 生成

## 关键发现

### 发现 1：服务稳定性优秀

JMeter 150并发、100万+样本压测全程 **0 错误率**，最大响应时间 177ms，P99 仅 7ms。证明服务在设计负载下运行可靠。

### 发现 2：吞吐量天花板约 35K/s

JMeter 并发从 80 增至 150，QPS 仅增长 4%（33,622 → 35,010）。服务在当前配置下接近上限。

### 发现 3：瓶颈在压测端 CPU，非服务端

外部 Windows JMeter（8C16T）达到 33,622 QPS，内部 Debian VM（2C）仅 21,741 QPS，**差距 35%**。iperf 测得网络带宽 950Mbps，排除网络瓶颈。

### 发现 4：应用层开销是主要差距来源

Redis Benchmark 内部测试 155K QPS，HTTP 应用层 JMeter 仅 33K QPS，约 **4.7x 差距** 来自 HTTP + JSON + Lettuce 连接开销。

### 发现 5：延迟长尾问题在并发升高时加剧

并发 80 时 P99 仅 3ms，150 时升至 7ms。平均响应时间从 1.93ms 增至 3.51ms（+82%），但中位数相对稳定（2ms → 4ms），说明主要是长尾在恶化。

## 瓶颈分层分析

```
┌─────────────────────────────────────────────────────────────┐
│ 第一层：压测端 CPU（内部VM 自身瓶颈）                           │
│   外部 Windows 33K vs 内部 VM 21K = 35% 性能差距              │
├─────────────────────────────────────────────────────────────┤
│ 第二层：网络路径（已排除）                                     │
│   iperf 950Mbps 远高于 Redis QPS 需求，NAT 无明显瓶颈         │
├─────────────────────────────────────────────────────────────┤
│ 第三层：应用层（HTTP + Lettuce + Lua）                        │
│   内部 benchmark 155K vs HTTP 33K，约 4.7x 差距              │
├─────────────────────────────────────────────────────────────┤
│ 第四层：Redis 服务端（无瓶颈）                                 │
│   当前利用率 ~22%（33K / 155K），水平扩展可进一步提升          │
└─────────────────────────────────────────────────────────────┘
```

## 实践经验总结

### 1. 压测端选择

| 场景 | 推荐工具 | 原因 |
|------|----------|------|
| 复杂 HTTP 场景 | JMeter | 支持 cookies、headers、POST body |
| 快速基准测试 | wrk | 轻量，单文件，Lua 脚本扩展 |
| 外部压测 | 使用高配物理机 | VM CPU 受限会影响压测准确性 |

**结论**：压测端 CPU 规格直接影响压测结果上限，应使用高配物理机而非 VM。

### 2. 测试位置选择

| 测试方式 | 适用场景 | 注意事项 |
|----------|----------|----------|
| 同物理机测试 | 快速验证 | 压测工具和服务共享资源，互相影响 |
| 内部网络测试 | 基线验证 | 排除网络因素，专注服务端能力 |
| 外部压测 | 真实场景 | 最接近生产环境，但需排除压测端瓶颈 |

**结论**：服务端能力测试用内部网络，性能验收测试用外部高配物理机。

### 3. 瓶颈分析方法

```
问题：QPS 低于预期
↓
排查顺序：压测端 CPU → 网络带宽 → 应用层 → Redis 服务端
↓
验证方法：iperf 测带宽、VM 对比排除 CPU 瓶颈、benchmark 测服务端上限
```

## 命令速查

### 初始化库存

```bash
curl -X POST http://10.0.0.142:8080/stock/SKU001/init?quantity=1000000000
```

### Redis Benchmark

```bash
# PVE 内部测试（服务端上限）
redis-benchmark -h 10.0.0.104 -p 6379 -t set -n 1000000 -c 100 -d 10
```

### WRK 压测

```bash
# post.lua
echo 'wrk.method = "POST"' > ~/workspace/post.lua

# 压测 decrement 接口
wrk -t4 -c100 -d30s -s ~/workspace/post.lua http://10.0.0.142:8080/stock/SKU001/decrement?quantity=1
```

### JMeter

```powershell
$ts = Get-Date -Format "yyyyMMdd-HHmmss"
jmeter -n -t .\stock_decr.jmx `
    -l "benchmark_results_$ts.jtl" `
    -e -o "benchmark_report_$ts" `
    -J "benchmark_log_$ts"
```

参数说明：`-n` 非GUI模式，`-t` 测试计划文件，`-l` 结果文件，`-j` 日志文件（时间戳区分不同运行）。
