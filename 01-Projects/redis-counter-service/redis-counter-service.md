## 核心设计

### Lua 脚本（原子扣减）
```lua
local stock = tonumber(redis.call('GET', KEYS[1]) or 0)
local quantity = tonumber(ARGV[1])
if stock >= quantity then
    return redis.call('DECRBY', KEYS[1], quantity)
else
    return -1
end
```

### 业务流程
```
用户下单 → 库存扣减 → Redis Lua 原子操作 → 成功/库存不足
```

### 设计决策
- **库存用 Redis**：抵挡秒杀高并发写请求
- **Lua 保证原子性**：避免并发超卖
- **最终一致性**：异步同步到 MySQL

### WSL 本地测试（2026-05-04）

| 指标 | 值 | 说明 |
|------|-----|------|
| QPS | 3.5万 | WSL 本地 redis-benchmark |
| 延迟 avg | 3.34ms | - |
| 延迟 p99 | 5.99ms | - |

**关键认知**：
- WSL 测试瓶颈是 WSL 虚拟机本身，非网络路径
- WSL 受 Windows 宿主机调度影响，无法独占 CPU
- WSL 只适合功能验证，不适合性能基准测试
- 真实性能以开发机直连结果（20W+ QPS）为准

### 关键发现

**⚠️ PVE 内部 CPU 抢占问题**：
- 多台 VM 同时压测时存在 CPU 资源竞争
- 测试结果经常变动
- 建议从外部网络压测更合理

**网络拓扑对测试的影响**：
```
开发机 → WRT（2核1G）→ PVE 虚拟网桥 → Redis VM
```
- WRT 可能成为路由器瓶颈
- 虚拟网桥无带宽限制，但 VM 共享宿主机资源

### 测试结果

| 配置 | QPS | 说明 |
|------|-----|------|
| 开发机直连 PVE（2核2G） | 约 20 万 | 关闭 AOF |
| 开发机直连 PVE（1核1G） | 约 20 万 | 关闭 AOF |

## 架构决策

### 扩展策略
- **不要追求高配单机**：单线程无法利用多核
- **水平扩展**：3 节点 Cluster ≈ 60 万 QPS
- **Pipeline**：可提升 5-6 倍吞吐量（需要客户端支持）

### 容量估算
```
目标 QPS ÷ 20万 ≈ 所需节点数

示例：50 万 QPS → 3 节点
示例：100 万 QPS → 5 节点
```

### 成本效益

|---------|-----------|--------|
| 1核 1GB | ~20万 | $6 |

## 测试方法论

### 关键教训
1. **压测端也可能成为瓶颈**：开发机/客户端网络栈
2. **PVE 内部存在资源竞争**：多 VM 同时压测结果不稳定
3. **从外部网络测试更可靠**：避免 VM 间资源竞争
4. **本地压测与远程压测结果不同**：网络路径和客户端性能差异

### 推荐的测试方法
1. 从外部机器（非 PVE 内）发起压测
2. 多台客户端分散负载
3. 使用 Pipeline 模式提升客户端效率
