## 决策 1：场景重新定义

### 背景

原需求文档定义了 5 个应用场景（秒杀、防重复提交、API 限流、任务调度、优惠券发放），经逐一分析，4 个不需要分布式锁。

### 决策

**保留 2 个真实场景，删除 3 个伪需求。**

| 场景 | 决策 | 原因 |
|------|------|------|
| 配额重置窗口互斥 | ✅ 保留 | 时间窗口互斥 = 租约语义 = 锁的天然匹配 |
| 缓存热点重建防护 | ✅ 保留 | 临界区保护计算资源 = 锁的天然匹配 |
| 秒杀扣库存 | ❌ 剔除 | `DECR` 原子操作即可 |
| 防重复提交 | ❌ 剔除 | `SETNX idempotent:key` 幂等键即可 |
| 任务调度 Leader 选举 | ❌ 剔除 | Raft 共识更适合 |

## 决策 2：看门狗优先级提升

### 原决策

看门狗是 Phase 2 P1 需求。

### 新决策

**看门狗提升为 P0，与基础锁同步交付。**

### 原因

- 场景 B（缓存重建）的耗时由 DB 负载决定，不可预估
- 固定 TTL 无法适配：设短了 GC 停顿导致误释放，设长了资源占用太久
- `renew_lock.lua` 已写好，差一个后台调度线程——工作量大半已就绪

### 实现方案

- 续期间隔：`TTL / 3`
- 使用 `ScheduledExecutorService` 单线程调度
- 续期前检查锁是否仍被当前实例持有
- unlock 或异常时取消调度任务

## 决策 3：tryLock 等待机制

### 现状

`tryLock` 使用 `Thread.sleep(50)` 轮询。

### 评估

- sleep 期间不消耗 CPU（OS 级线程调度）
- 但等待时长是盲猜的——缓存重建 2ms 完成，多等了 48ms
- Pub/Sub 通知可消除盲等，但增加复杂度

### 决策

**Phase 1-2 保留 sleep 轮询，Phase 3 引入 Pub/Sub 通知。**

- 当前两个场景对 sub-50ms 延迟不敏感
- Pub/Sub 需要独立的订阅管理和消息去重逻辑
- 后续若扩展到实时性要求更高的场景再启用

## 决策 4：可重入锁

### 决策

**保留为 P1，Phase 2 实现。**

### 原因

- 场景 B（缓存重建）的内部逻辑可能递归进入临界区
- 使用 Hash 结构 `lock:resource → {threadId: count}`
- 但当前两个场景的单线程执行路径不触发重入需求
- 代码框架预留重入点，先不实现

## 决策 5：限流模块独立

### 原决策

限流和锁作为同一个项目。

### 新决策

**限流模块保留在本项目中，但架构上与锁解耦。**

- 限流不依赖锁（限流器内部使用 Redis 原子操作 + Lua）
- 共用 `Lettuce` 连接池和 `RedisConfig`
- 限流算法已实现（滑动窗口/令牌桶/固定窗口），本次不主要变更

## 决策 6：Redlock 优先级降低

### 原决策

Phase 3 实现 Redlock（5 实例多数投票）。

### 新决策

**Redlock 暂不纳入本项目计划。**

### 原因

- 两个场景都不需要多实例协调（单 Redis 实例的锁已足够）
- Redlock 的复杂性在于时钟漂移和网络分区处理
- 作为独立的学习主题更合适（属于"Redis 多实例一致性"而非"锁的模式"）

---

## 决策 7：Redis 客户端选型（维持原决策）

**Lettuce**。Spring Boot 3 内置，异步非阻塞。不引入 Redisson——本项目目的是理解锁的底层原理。
