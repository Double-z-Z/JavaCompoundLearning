### 目标

实现能容忍 GC 停顿的生产级分布式锁，支撑**场景 A（配额重置窗口互斥）**。

### 实现步骤

#### Step 1.1：分析现有代码的问题

```java
// RedisLock.java 当前实现
public boolean lock(String key, long ttl) {
    Long result = redisTemplate.execute(
        luaScripts.getAcquireLockScript(),
        luaScripts.getAcquireKeys(key),
        uniqueId,
        String.valueOf(ttl)
    );
    return result != null && result == 1;
}
```

**问题**：`lock()` 成功后没有启动看门狗。GC 停顿若超过 TTL，锁被 Redis 自动释放，另一个实例抢到锁，出现双写。

#### Step 1.2：实现 Watchdog

```
Watchdog 职责：
1. lock() 成功后：调度续期任务（间隔 = TTL/3）
2. renew_lock.lua：检查 uniqueId → EXPIRE key ttl
3. unlock() 时：取消续期任务
4. 续期失败（锁被他人持有或过期）：通知业务回调（可选）
```

**设计要点**：

- 使用 `ScheduledExecutorService(1)` —— 单线程足够，避免并发复杂度
- 每次续期前检查 `isLocked()` —— 锁已不在则停止续期
- unlock 时必须取消 `ScheduledFuture`，防止泄漏
- TTL/3 的计算：30s TTL → 每 10s 续一次，耐 20s GC 停顿（实际 GC 极少超过 5s）

```java
// Watchdog 伪代码
class Watchdog {
    ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
    Map<String, ScheduledFuture<?>> tasks = new ConcurrentHashMap<>();

    void start(String key, long ttl, RedisLock owner) {
        long interval = ttl / 3;
        ScheduledFuture<?> task = scheduler.scheduleAtFixedRate(() -> {
            if (!owner.isLocked(key)) {
                stop(key);
                return;
            }
            owner.renew(key, ttl);  // 调用 renew_lock.lua
        }, interval, interval, TimeUnit.SECONDS);
        tasks.put(key, task);
    }

    void stop(String key) {
        ScheduledFuture<?> task = tasks.remove(key);
        if (task != null) task.cancel(false);
    }
}
```

#### Step 1.3：RedisLock 集成 Watchdog

```
RedisLock.lock(key, ttl) →
  1. 执行 acquire_lock.lua → 成功
  2. watchdog.start(key, ttl, this)  ← 新增
  3. 返回 true

RedisLock.unlock(key) →
  1. watchdog.stop(key)              ← 新增
  2. 执行 release_lock.lua
  3. 返回结果
```

### 验收标准

- [ ] lock() 后看门狗自动启动，TTL/3 间隔续期
- [ ] 模拟长时间业务：sleep 超过 TTL，锁没有被释放
- [ ] unlock() 后看门狗停止，`tasks map` 无泄漏
- [ ] 续期脚本校验 uniqueId，不能续期他人的锁

### 易错点预警

| 错误 | 原因 | 预防 |
|------|------|------|
| 看门狗空转 | unlock 后未取消 ScheduledFuture | finally 块中取消 |
| 续期键不存在 | 锁已过期/被删 | 续期前检查 isLocked() |
| 线程泄漏 | ScheduledExecutorService 未 shutdown | @PreDestroy 关闭 |

## Phase 2：可重入锁 + 通知机制

### 目标

支撑**场景 B（缓存热点重建防护）**，支持可重入和 Pub/Sub 通知。

### 实现步骤

#### Step 2.1：可重入锁

```
数据结构切换：String → Hash

lock:rebuild:product:1001 (Hash)
  ├── owner: "uuid-abc-123"
  ├── threadId:1 → 2     (threadId → 重入次数)
  └── threadId:2 → 1
```

加锁 Lua 脚本逻辑：
```
1. HEXISTS key owner → 如果存在（已被某实例持有）
2.   HINCRBY key threadId 1 → 同一线程重入
3.   返回 1
4. 如果不存在 → 首次获取
5.   HSET key owner uuid, threadId 1
6.   EXPIRE key ttl
7.   返回 1
```

#### Step 2.2：Pub/Sub 通知（替代 sleep 轮询）

```
tryLock 流程：
1. lock() → 成功，直接返回
2. 失败 → SUBSCRIBE lock:notify:{key}
3. 收到通知 → lock() 重试
4. 超时未收到通知 → 返回 false
```

```
unlock 流程增强：
1. watchdog.stop()
2. release_lock.lua
3. PUBLISH lock:notify:{key} "released"  ← 新增
```

### 验收标准

- [ ] 同一线程可多次获取同一把锁（重入计数 +1）
- [ ] 重入锁全部释放后才删除 key
- [ ] Pub/Sub 通知替代 sleep 后，tryLock 等待延迟 < 10ms
