## 1. 核心洞察

经过对秒杀、防重复提交、优惠券发放、任务调度四个场景的逐一分析，结论是：

> **分布式锁解决的是"多进程临界区保护"问题，不是"状态一致性"问题。**

```
临界区保护（锁的领域）:   "同一时刻只让一个人干这件事"
状态一致性（事务的领域）:   "多个操作要么全成功、要么全失败"
```

大多数 Java 后端场景被误诊为"需要分布式锁"，实际需要的是：
- Redis 原子指令（`DECR`/`SETNX`）
- 幂等键（`SETNX idempotent:order:123`）
- 共识协议（Raft Leader Election）
- Saga/2PC 分布式事务

## 2. 真实应用场景

### 场景 A：配额重置窗口互斥

**业务背景**：SaaS 多租户平台，每月 1 号 0:00 全局重置所有租户配额。

**为什么需要锁**：
- 集群中有 N 个实例，每个都能执行重置任务
- 必须保证同一月只重置一次——重复重置导致配额翻倍
- 这不是事务问题（没有多步跨资源），而是"时间窗口内互斥"问题

**为什么 Saga/2PC 不适用**：
- 配额重置没有补偿语义——"把租户 A 的配额改回去"毫无意义
- 2PC 的投票/预写日志是为跨库事务设计的，这里没有事务边界
- 这个操作需要的是**租约机制**（Lease），不是事务机制

**锁的使用方式**：

```
每月 1 号 0:05，所有实例执行：
  if (lock.tryLock("quota:reset:2026-06", 0, 5min)) {
      执行全局配额重置
  }
  // 锁的 TTL = 保护窗口，5 分钟后自然过期
```

**关键约束**：
- 重置操作正常耗时 <30 秒，TTL 设 5 分钟留有充足余量
- 执行节点崩溃 → 锁在 5 分钟后自动释放，其他节点可补救
- 看门狗兜底：即使 JVM GC 暂停 1 分钟，锁不会误释放

### 场景 B：缓存热点重建防护

**业务背景**：热点数据缓存在 Redis，过期瞬间大量请求直击 MySQL。

**为什么需要锁**：
- 1000 个请求同时发现缓存为空，都要去查 DB 重建
- 只允许一个人查 DB 重建，其余 999 人等结果或降级
- 保护的不是数据状态（缓存是 DB 的衍生），保护的是**计算资源（DB）**

**为什么 Saga/2PC 不适用**：
- 缓存重建失败不需要"补偿"——下次再查再重建
- 不需要"DB 和 Cache 原子提交"——允许缓存短暂不一致

**锁的使用方式**：

```
GET cache:hot:product:1001 → null
  → if (lock.tryLock("rebuild:product:1001", 5s, 30s)) {
        data = DB.query(...)
        SET cache:hot:product:1001 data EX 3600
        lock.unlock()
     } else {
        // 方案 A: 阻塞等待后读缓存（需要 Pub/Sub 通知）
        // 方案 B: 快速失败返回降级数据
     }
```

**关键约束**：
- 重建耗时不固定（取决于 DB 负载），TTL 不能固定
- 需要看门狗自动续期——重建过程中锁不能过期
- 999 个等待请求不应轮询，应用 Pub/Sub 或 BLPOP 通知

## 3. 被剔除的"伪需求"

| 原场景 | 为什么不需要锁 | 真正需要的机制 |
|--------|-------------|-------------|
| 秒杀扣库存 | `DECR stock:sku` 原子操作 | Redis 原子指令 + LUA |
| 防重复提交 | 幂等键 `SETNX order:123` | 幂等 ID |
| 优惠券单人限领 | `SETNX coupon:1:user:123` | 幂等键（key 含 userID）|
| 任务调度 Leader 选举 | 共识协议 | Raft / K8s Lease |

## 4. 功能需求

### 4.1 分布式锁模块

| 需求 | 描述 | 优先级 | 对应场景 |
|------|------|--------|---------|
| `lock(key, ttl)` | SET NX EX 原子加锁 | P0 | A / B |
| `unlock(key)` | Lua Check-and-Delete 解锁 | P0 | A / B |
| `tryLock(key, ttl, waitTime)` | 支持等待的加锁 | P0 | B（等待缓存重建）|
| 看门狗续期 | TTL/3 间隔续期，业务完成前锁不释放 | P0 | B（重建耗时不可预估）|
| 可重入锁 | Hash 记录 threadId:count | P1 | B（同一线程多次进入临界区）|
| Pub/Sub 通知 | 锁释放时通知等待者 | P2 | B（替代 sleep 轮询）|

### 4.2 安全保证

- **防误删**：Lua 脚本校验 UUID，只能删自己的锁
- **死锁预防**：所有锁必须有 TTL，绝不允许永久锁
- **GC 停顿防护**：看门狗在 TTL/3 时续期，容忍最长 TTL/3 的 GC 停顿
- **原子性**：所有 Check-Then-Act 操作封装在 Lua 脚本中

### 4.3 限流模块（保留，与锁解耦）

> 注意：限流和锁是两个独立模块。本项目的限流器不依赖锁。

| 算法 | 描述 | 优先级 |
|------|------|--------|
| 滑动窗口 | 精确 QPS 控制（ZSet） | P0 |
| 令牌桶 | 支持突发流量（Hash） | P0 |
| 固定窗口 | 简单计数（String） | P1 |

## 5. 非功能需求

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 锁获取延迟 | < 3ms (P99) | SET NX EX 单次 Redis 往返 |
| 解锁延迟 | < 2ms (P99) | Lua GET+DEL |
| 看门狗续期间隔 | TTL / 3 | 自动适配不同 TTL |
| 缓存重建二次穿透率 | < 1% | 1000 并发重建，DB 查询 ≤1 次 |

## 6. 技术方案

| 组件 | 选型 | 原因 |
|------|------|------|
| Java | 17 | 当前环境 |

## 7. 学习目标（更新）

完成本项目 v2.0 后，将掌握：

- [ ] **理解锁的真正边界**：能区分"需要锁"和"需要原子指令/幂等键/共识"的场景
