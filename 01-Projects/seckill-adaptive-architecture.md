# 秒杀系统：可预知流量与动态优化架构设计

> 状态：📋 设计阶段 | 创建时间：2026-05-09

## 1. 问题背景

### 1.1 数据倾斜的核心矛盾

```
Web 服务器（无状态）          Redis（有状态）
┌──────────────────┐        ┌──────────────────┐
│ 负载均衡器        │        │ Hash(key) % 16384│
│   ↓              │        │      ↓           │
│ 实例A ← 请求可分发 │   vs   │ Slot 5432         │
│ 实例B ← 到任意实例 │        │   ↓               │
│ 实例C              │        │ 固定节点！无法分散！│
└──────────────────┘        └──────────────────┘
```

**Redis 的槽位是预分配的** —— `stock:IPHONE15` 永远落在同一个节点！

### 1.2 三大风险

| 风险 | 表现 | 后果 |
|------|------|------|
| Redis CPU 飙高 | 单点 QPS 过载 | 响应延迟飙升 |
| 网络延迟叠加 | 所有请求串行等待 | RT 从 1ms → 100ms+ |
| 超卖风险 | 并发扣减竞争 | 库存变负数 |

## 2. 架构分层防御

```
                    ┌─────────────────────────────────┐
  用户请求 ─────────▶│ 第0层：Nginx 令牌桶限流          │  ← "解决提出需求的人"
                    │ （拒绝溢出部分）                   │
                    └──────────────┬──────────────────┘
                                   ▼
                    ┌─────────────────────────────────┐
  通过限流 ────────▶│ 第1层：前端削峰（排队/延时）      │  ← "降低响应时间"
                    │ （异步队列缓冲）                  │
                    └──────────────┬──────────────────┘
                                   ▼
                    ┌─────────────────────────────────┐
  到达后端 ────────▶│ 第2层：Caffeine 本地缓存          │  ← 吸收读压力
                    │ （L1 Cache）                     │
                    └──────────────┬──────────────────┘
                                   ▼
                    ┌─────────────────────────────────┐
  写操作 ──────────▶│ 第3层：Redis + Lua              │  ← 最后防线
                    │ （原子扣减，尽力而为）             │
                    └─────────────────────────────────┘
```

| 层级 | 策略 | 牺牲什么 |
|------|------|---------|
| Nginx 限流 | **拒绝** | 部分用户体验（"抢购人数过多"） |
| 前端削峰 | **延时** | 响应时间（"排队中，预计5分钟"） |
| 本地缓存 | **近似** | 强一致性（可能读到旧值） |
| Redis Lua | **串行** | 吞吐量上限 |

## 3. 可预知流量与动态优化的结合

> "爆点流量可预知"是**前置条件**，决定了系统能提前准备到什么程度。

### 3.1 可预知场景：预热与静态策略

**场景示例**：知道"周五20:00 iPhone16 10000台"

#### 3.1.1 多级缓存预热

```java
// 提前5分钟：多级缓存预热
caffeineCache.put("hot:sku1001", stockVO);  // 本地缓存
redis.set("stock:sku1001", 10000);           // Redis
```

#### 3.1.2 弹性扩容

```java
// 提前1分钟：弹性扩容（K8s HPA / 云厂商弹性伸缩）
// 将秒杀服务实例从10个扩容到100个，分散连接压力
```

#### 3.1.3 队列预热

```java
// 提前30秒：队列预热
rocketMQ.createTopic("seckill:sku1001", 16); // 预分配队列，避免创建延迟
```

#### 3.1.4 交互层配合

- **前端倒计时结束后**：按钮不是立即开放，而是**分批脉冲式开放**（如每100ms放行一批请求），配合后端令牌桶速率
- **用户侧显示真实排队信息**："前方排队XXX人"，这个XXX是真实的Redis队列长度或MQ堆积量，**不是假数据**

---

### 3.2 半可预知/突发场景：自适应动态优化

但真实业务中，"可预知"往往是模糊的（如"大概晚上8点人多"）。这时需要**闭环反馈**：

#### 3.2.1 动态优化矩阵

| 优化维度 | 触发条件 | 动作 |
|---------|---------|------|
| **限流阈值自适应** | CPU > 80% 或 RT > 500ms | Sentinel滑动窗口自动下调QPS阈值，而非固定200k |
| **缓存TTL动态调整** | Redis单节点QPS > 50k | 延长本地缓存TTL（如1秒→3秒），牺牲一定实时性换可用性 |
| **队列消费背压** | MQ堆积 > 10万 | 降低消费速率，防止MySQL被打挂，前端提示"系统繁忙，正在处理" |
| **批次粒度调整** | 第一批次10秒售罄 | 第二批次减少单批数量、增加批次间隔，平滑曲线 |

#### 3.2.2 自适应限流伪代码

```java
// 自适应限流核心逻辑
if (systemLoad.getCpuUsage() > 0.8) {
    // 动态下调令牌桶速率，而非硬编码200k
    tokenBucket.setRate(currentRate * 0.7);
    
    // 通知前端：当前抢购人数过多，进入排队模式
    eventPublisher.publish(new ThrottleEvent("reduce_rate", currentRate * 0.7));
}
```

## 4. 安全性挑战

### 4.1 客户端不可信原则

> **永远不要信任客户端传来的任何数据**

```
                    ┌──────────────────────────────┐
  正常用户 ─────────▶│ Nginx 令牌桶：每秒放行20万    │
                     │ （诚实遵守规则）              │
                     └──────────────┬──────────────┘
                                  ✅ 公平
                    
                    ┌──────────────────────────────┐
  作弊者/脚本 ──────▶│ 绕过令牌桶 / 多开 / 刷代理     │
                     │ （不守规则的人）              │
                     └──────────────┬──────────────┘
                                  ❌ 不公平！
```

### 4.2 攻击手段与防御

| 攻击方式 | Nginx IP限流 | 前端验证码 | Redis Lua |
|---------|-------------|-----------|----------|
| 多IP代理刷单 | ❌ 绕过 | ❌ 无效 | ✅ 最终兜底 |
| 绕过JS直接调API | ❌ 无效 | ❌ 被绕过 | ✅ 最终兜底 |
| 脚本自动化 | ⚠️ 部分有效 | ✅ 有效 | ✅ 兜底 |
