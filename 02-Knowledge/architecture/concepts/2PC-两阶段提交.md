# 2PC（两阶段提交）

## 一句话定义

2PC 是分布式事务的强一致性协议，通过"准备→提交"两阶段投票机制，保证跨多库操作要么全部成功、要么全部失败，代价是全程持锁导致的阻塞和协调者单点风险。

## 核心理解

### 协议流程

```
Coordinator                   Participant A          Participant B
    |                              |                      |
Phase 1 — Prepare（投票）
    |--[prepare: A扣100]---------->|                      |
    |                              | 预提交，行锁           |
    |--[prepare: B加100]------------------------------>|
    |                              |                 预提交，行锁
    |<--[YES, undo=A+100]----------|                      |
    |<--[YES, undo=B-100]------------------------------|
    |                              |                      |
Phase 2 — Commit（执行）                                           |
    |--[commit]------------------->| (不可逆)               |
    |--[commit]------------------------------->|
    |                              | 提交成功              | 提交成功
```

- **Prepare**：参与者执行 SQL 放入临时区，回答 YES/NO。此时行锁已持有。
- **Commit**：所有 YES → 发 commit；任一 NO → 发 rollback。

### 核心特性

| 维度 | 2PC |
|------|-----|
| 一致性 | 强一致（零不一致窗口） |
| 性能 | 低（Prepare-Commit 间持锁阻塞） |
| 可用性 | 低（协调者宕机→参与者锁死） |
| 适用规模 | 小（参与者越多，慢节点拖垮整体） |

### 协调者故障：协议的最大弱点

Prepare 发出后协调者宕机 → 参与者全部持锁等待 → 无人知该 commit 还是 rollback。解决方案：协调者写**事务日志**（类似 Redis AOF），重启后从日志恢复未完成事务的状态。但日志落盘本身也是瓶颈。

### 2PC vs Saga vs 无事务

| | 2PC | Saga | 原子指令 |
|------|-----|------|---------|
| 一致性 | 强 | 最终 | 单步 |
| 并发能力 | 低 | 高 | 最高 |
| 适用 | 银行转账 | 秒杀下单 | 扣库存 |
| 补偿成本 | 无 | 有 | 无 |

## 关键关联

- [[Saga模式]] - 关联原因：两者都是分布式事务方案，2PC 做"先问再做"，Saga 做"先做再补"，恰好在两个极端
- [[分布式锁]] - 关联原因：2PC 和锁常被混淆——锁解决并发冲突，2PC 解决跨资源原子性，两者正交
- [[Redis-AOF]] - 关联原因：2PC 协调者的事务日志和 Redis AOF 都是"用持久化日志恢复内存状态"的思路

## 我的误区与疑问

- ❌ 误区：以为 2PC 和分布式锁是同类机制（实际：锁=临界区互斥，2PC=跨资源原子提交）
- ❓ 疑问：3PC 加了"预提交"阶段解决单点阻塞，但引入了网络分区的脑裂风险——哪个代价更大？

## 深入思考

💡 2PC 的 Prepare 阶段行锁持有——如果参与者 A 说 YES 后它的 DB 宕机了，重启后它凭什么还能提交？答案：Prepare 时已经写了 undo/redo 日志到磁盘。
💡 为什么银行不直接用 Saga？因为 50ms 的不一致窗口被另一笔查询读到，就是"账户余额凭空少了 100 块"的金融事故。
