# Saga 模式

## 一句话定义

Saga 是将跨服务/跨节点的大事务拆解为**一系列顺序执行的本地事务**，通过**正常路径完成业务**或**异常路径触发补偿事务**来实现最终一致性的分布式事务模式。


## 核心理解

### 为什么需要 Saga？

Redis Cluster 不支持跨节点 MULTI/EXEC，MySQL 分库分表后行锁无法跨库生效。**当业务操作天然分布在多个节点时，ACID 事务的边界被物理打破**，Saga 提供了一种"放弃强一致、接受最终一致"的工程妥协。

```
传统事务（ACID）          Saga 模式
├─ BEGIN                 ├─ T1: 扣减 SKU001（Node1）→ 成功
├─ UPDATE A              ├─ T2: 扣减 SKU002（Node2）→ 成功
├─ UPDATE B              ├─ T3: 扣减 SKU003（Node3）→ 失败
├─ UPDATE C              └─ 触发补偿：C2 → C1
└─ COMMIT/ROLLBACK
    ↑ 数据库引擎内原子完成      ↑ 业务层顺序执行 + 失败时反向修复
```

### 两种实现方式

| 类型 | 原理 | 类比 | 适用场景 |
|------|------|------|---------|
| **编排式（Choreography）** | 每个服务完成本地事务后发送事件到 MQ，下游服务监听事件自动执行 | 接力赛，跑完一棒传下一棒 | 步骤少、服务间耦合松（如秒杀库存扣减） |
| **协调式（Orchestration）** | 中央协调器统一调度各服务按顺序执行 | 导演指挥演员，按剧本逐场拍 | 步骤多、流程复杂（如电商订单：库存→支付→物流→积分） |

### 正常路径 vs 异常路径

```text
Saga 模式
├── 正常路径：T1 → T2 → T3 → ... → Tn（全部成功，事务完成）
└── 异常路径：T1 → T2 → T3(失败) → C2 → C1（逆向补偿，事务回退）
         ↑___________________________|
              补偿事务在这里发挥作用
```


## 关键关联

- [[补偿事务]] - 关联原因：Saga 异常路径依赖补偿事务完成逆向修复，补偿是 Saga 的"兜底机制"
- [[秒杀超卖与库存一致性]] - 关联原因：秒杀多 SKU 跨节点扣减是 Saga 的典型应用场景，Redis Cluster 不支持跨节点事务，必须用 Saga + 补偿解决
- [[2PC与3PC]] - 关联原因：Saga 是 2PC 的替代方案，2PC 追求强一致但性能差，Saga 放弃强一致换取高吞吐
- [[消息队列]] - 关联原因：编排式 Saga 依赖 MQ 传递事件，保证步骤顺序和补偿触发


## 我的误区与疑问

- ❌ 误区：Saga 和补偿事务是同一个东西
  - 纠正：Saga 是**架构模式/协议**（定义如何组织多个本地事务），补偿事务是**具体执行手段**（失败时如何收拾残局）。两者层级不同。
- ❌ 误区：Saga 能保证和 2PC 一样的强一致性
  - 纠正：Saga 保证的是**最终一致性**。过程中可能出现脏读（T1 扣减后、C1 补偿前，其他服务已读到中间状态），这是性能换一致性的必要代价。
- ❓ 疑问：协调式和编排式如何选择？
  - 答案：步骤少（≤5）且服务间松耦合用编排式；步骤多、需要人工介入或流程经常变动用协调式。

### 与 Seata 的对比

| 方案 | 类型 | 特点 | 重量级 |
|------|------|------|--------|
| **Seata Saga** | 协调式 | 基于状态机引擎，JSON/YAML 定义流程 | 重 |
| **Seata TCC** | 两阶段 | Try-Confirm-Cancel，补偿逻辑显式实现 | 重 |
| **自研 MQ + 本地表** | 编排式 | 最轻量，本地事务表记录步骤，MQ 传递事件 | 轻 |


## 深入思考

💡 Saga 的本质是"用可靠性换性能"——接受"补偿可能失败、需要人工兜底"的风险，换取秒杀场景下必须的毫秒级响应。这不是技术缺陷，而是 CAP 定理下的理性选择。
