# Sentinel 核心架构

## 一句话定义
Sentinel 是面向分布式服务架构的流量控制组件，以"本地优先、分层防护、优雅降级"为设计哲学，通过轻量级 SDK 嵌入实现纳秒级流量决策。


## 核心架构三角

```
┌─────────────────────────────────────────────┐
│              Sentinel 设计三角               │
├──────────┬──────────┬───────────────────────┤
│ 本地优先 │ 分层防护 │ 优雅降级             │
│ (效率)   │ (粒度)   │ (可用性)             │
└──────────┴──────────┴───────────────────────┘
         ↓           ↓           ↓
    纳秒级决策    漏斗式过滤   故障时回退
```

### 本地优先（效率优先）
- 决策在本地内存完成，不依赖远程调用
- 网络抖动/机房故障时依然可控
- 对比：Redis 计数器方案强依赖网络

### 分层防护（粒度递进）
| 层级 | 位置 | 可见信息 | 控制粒度 |
|------|------|---------|---------|
| 网关层 | API Gateway | URL、Header | 粗（按路径） |
| 应用层 | 业务服务内部 | 完整业务上下文 | 细（按语义） |

### 优雅降级（可用性保障）
- Token Server 挂了 → 回退到本地独立限流
- 时钟回拨 → 复用旧窗口，接受模糊统计
- 规则配置中心不可用 → 使用本地缓存规则


## 部署模式

### 应用层嵌入模式（SDK）
- Sentinel 作为 Jar 包嵌入业务进程
- 优点：零网络延迟、完整业务上下文
- 适用：90% 的场景

### 接入层网关模式
- Sentinel 作为独立进程运行
- 优点：统一入口、非侵入式
- 适用：多语言混合架构

### 集群限流模式（Token Server）
- 架构：集中管控 + 本地执行
- Token Server 定时同步阈值，各节点本地令牌桶执行
- 降级策略：Token Server 故障时回退到本地独立限流


## 监控与规则管理

### 数据收集策略
- **主模式**：客户端主动上报（定时 push 指标到 Dashboard）
- **辅模式**：Dashboard 按 API 轮询拉取（按需实时监控）

### 规则下发机制
- 支持多种持久化后端：MySQL / Nacos / Apollo / ZooKeeper
- 异步推送 + 本地版本校验保证最终一致性
- 规则存储可插拔（专注核心，边界开放）

## 我的误区与疑问

- ❌ 误区：曾认为应用层网关和接入层的区别仅在于是否涉及业务逻辑，实际上更核心的是**可见信息范围**和**拒绝链路长度**
- ❓ 疑问：单机限流场景下使用 monotonic time 是否比 Wall-Clock 更合理？Sentinel 为何统一用 Wall-Clock？
- 💡 洞察：悬挂请求的分代桶方案（新生代→老年代→回收）比 Sentinel 的"延迟计入"更真实反映系统压力
