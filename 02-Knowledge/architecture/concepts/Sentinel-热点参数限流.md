# 热点参数限流

## 一句话定义
热点参数限流是对"同一热点参数值"设置独立阈值的精确流量控制策略，通过 Doorkeeper + Count-Min Sketch + Precise Counter 三层混合架构，在极低内存开销下实现对 Top-K 热点的精确限流，**长尾参数不存储**。


## 问题场景

```
普通限流：限制整个 /order/create 接口 10000 QPS

问题：
product/001 → 5000 QPS (爆款！) ← 单品打垮库存服务
product/002 → 100 QPS
product/003 → 80 QPS
...其他 99000 个商品共 4820 QPS

需求：对 product=001 单独设置更严格阈值（如 1000 QPS）
```


## 三层混合架构

```
┌─────────────────────────────────────────────────┐
│              热点参数限流 三层模型                │
├─────────────────────────────────────────────────┤
│                                                 │
│  Layer 1: Doorkeeper (布隆过滤器)               │
│  ├── 功能: 过滤掉只访问 1-2 次的长尾参数          │
│  └── 动作: 25% 概率放行到下一层                  │
│                                                 │
│  Layer 2: Count-Min Sketch (概率统计)            │
│  ├── 功能: 粗略估算各参数的热度                  │
│  ├── 结构: d个hash函数 × w宽度的计数器数组       │
│  └── 动作: 计数 > 阈值时触发晋升                 │
│                                                 │
│  Layer 3: Precise Counter (精确计数) ← Top-K    │
│  ├── 功能: 对确认的热点做精确限流                │
│  ├── 结构: ConcurrentHashMap<Param, LeapArray>  │
│  └── 容量: 固定大小 (如 2000 个)，满则丢弃新参数 │
│                                                 │
└─────────────────────────────────────────────────┘

核心原则：长尾参数不存储 = 宽松放行（工程正确取舍）
```


## Doorkeeper（布隆过滤器）

### 作用
过滤"一次性访问"的参数，防止 CMS 被冷门数据填满。

### 机制
```
首次访问的 key:
  ├─ 75% 概率: 直接丢弃（不放行）
  └─ 25% 概率: 放行进入 CMS 统计

已见过的 key:
  └─ 100% 放行

为什么是 25%?
  → 给部分新 key 机会证明自己是热点
  → 大部分一次性访问被过滤，节省 CMS 空间
```


## Count-Min Sketch（概率计数器）

### 结构
```
     d 个 hash 函数（通常 d=4）
     ┌─────────────────────────────────┐
h1  │ [0] [1] [2] ... [w-1]          │  ← 数组1 (宽度 w)
h2  │ [0] [1] [2] ... [w-1]          │  ← 数组2
h3  │ [0] [1] [2] ... [w-1]          │  ← 数组3
h4  │ [0] [1] [2] ... [w-1]          │  ← 数组4
    └─────────────────────────────────┘
```

### 操作
- **写入**: key 经 d 个 hash 函数映射，对应位置都 +1
- **查询**: 取 d 个位置的**最小值**（"Count-Min" 名字由来）

### 为什么取最小值？
```
冲突场景: key A 和 key B 映射到同一位置
array[1]: pos=X, count=A+B+其他 (碰撞! 高估)
array[2]: pos=Y, count=A+其他    (没碰撞)
array[3]: pos=Z, count=B+其他    (没碰撞)

min(A+B+, A+, B+) = A 或 B (接近真实值!) ✅
```

### 为什么叫 "Sketch"?
> **Sketch（素描）vs Photo（照片）**
> - Photo (HashMap): 每个像素精准，内存大
> - Sketch (CMS): 轮廓对、细节模糊，内存极小（几KB vs 几MB）


## 升降级机制

### 升级路径（冷→热）
```
新参数到达
    ↓
Doorkeeper: 25% 幸运通过?
    ↓ 是
CMS: 计数累加...
    ↓
计数 > 热点阈值 (如 QPS > 100)?
    ↓ 是
尝试晋升 Layer 3:
    Layer 3 有空位? → 创建精确计数器 ✅
    Layer 3 满?      → 淘汰最冷的 / 直接丢弃 ⚠️
```

### 降级路径（热→冷）
```
Layer 3 中的参数:
    定期检查热度...
    ↓
QPS < 冷却阈值 (如 < 10) 持续 N 秒?
    ↓ 是
降级回 CMS (删除精确计数器，释放槽位)
```


## 内存效率对比

| 方案 | 100万不同 key | 压缩比 |
|------|-------------|--------|
| HashMap (精确) | ~40MB | 1× |
| Count-Min Sketch | ~4KB | **~10000×** |

Sentinel 默认配置: 最多追踪 2000 个精确热点 + CMS 覆盖全量
