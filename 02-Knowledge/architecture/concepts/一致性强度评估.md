# 一致性强度评估

## 一句话定义
一致性强度评估是根据**业务容忍度、数据敏感性、修复成本**三个维度，判断系统需要强一致性、最终一致性还是弱一致性的评估框架；不同一致性强度对应不同的技术方案和成本。

## 核心理解

### 一致性强度光谱

```
强一致 ←────────────────────────────────→ 弱一致
  │                    │                    │
  2PC                 Saga              无锁/无事务
  Paxos/Raft          最终一致性        异步复制
  │                    │                    │
  银行转账            电商订单            社交点赞
  库存扣减（零容忍）   秒杀超卖（0.01%）    阅读计数
```

### 评估维度

| 维度 | 强一致 | 最终一致 | 弱一致 |
|------|--------|---------|--------|
| **业务容忍度** | 绝对零容忍 | 极低容忍（0.01%） | 有限容忍（1%~5%） |
| **数据敏感性** | 资金、核心账务 | 订单、库存 | 计数、日志、非关键数据 |
| **修复成本** | 极高（法律/品牌风险） | 中等（赔付/补偿） | 低（可忽略） |
| **性能要求** | 低（准确优先） | 高（吞吐优先） | 极高（可用优先） |
| **典型方案** | 2PC、Paxos/Raft | Saga、锁+幂等+对账 | 异步复制、无锁 |

### 业务场景映射

| 场景 | 容忍度 | 一致性强度 | 技术方案 |
|------|--------|-----------|---------|
| **银行核心账务** | 0（绝对零） | 强一致 | 2PC、Paxos |
| **火车票/机票** | 0（物理上限） | 强一致 | 悲观锁、2PC |
| **主流电商秒杀** | ≤0.01% | 最终一致 | Redis Lua + 异步落库 + 补偿 |
| **电商普通订单** | ≤0.1% | 最终一致 | Saga + 补偿 |
| **优惠券发放** | 1%~5% | 弱一致 | 异步队列 + 对账 |
| **社交点赞/阅读** | 10%+ | 弱一致 | 异步计数 + 定时合并 |

### 关键认知：不是"越强越好"

```
一致性强度 ↑
    │
    │     ╱────── 成本曲线（指数增长）
    │    ╱
    │   ╱  ╲────── 价值曲线（边际递减）
    │  ╱    ╲
    │ ╱      ╲
    │╱        ╲
    └──────────────────→ 业务容忍度
         ↑
      最佳平衡点（不是最强，而是"足够强"）
```

**核心原则**：一致性强度应该匹配业务容忍度，过度追求强一致会导致成本指数增长而价值边际递减。

### 容忍度三层级框架

| 层级 | 容忍度指标 | 典型场景 | 商业逻辑 |
|------|-----------|---------|---------|
| **绝对零容忍** | 0 | 火车票、机票、限量潮品、iPhone首发 | 库存物理上限刚性约束，超卖=无法履约，法律/品牌风险极高 |
| **极低容忍** | ≤0.01% | 主流电商秒杀（双11、618）、餐饮团购 | 允许极端并发下的统计误差，但需人工/系统兜底赔付 |
| **有限容忍** | 1%~5% | 快消品、预售模式、多仓异步调配 | 供应链可快速补货，或通过协商退款/换货解决，追求吞吐量优先 |

## 我的误区与疑问

- ❌ 误区：以为所有系统都应该追求最强一致性（实际应该匹配业务容忍度）
- ❌ 误区：以为"最终一致"就是"不一致也行"（实际是"最终必须一致"，需要补偿/对账兜底）
- ❓ 疑问：如何量化"容忍度"？（答：通过历史数据分析超卖/不一致的频率和业务损失）

## 深入思考

💡 如果业务容忍度随时间变化（如大促期间容忍度提高），一致性策略是否应该动态调整？
💡 不同一致性强度的模块如何在同一个系统中共存？（如订单模块用 Saga，库存模块用 2PC）
