# 分布式锁

## 一句话定义
分布式锁是通过**租约机制（Lease/TTL）**在分布式系统中实现**空间互斥**的技术——确保同一时刻只有一个节点能进入临界区执行特定代码，解决的是"不让冲突发生"而非"冲突发生后如何修复"。

## 核心理解

### 分布式锁 vs 本地锁

| 维度 | 本地锁（synchronized/ReentrantLock） | 分布式锁（Redis/ZK） |
|------|-------------------------------------|---------------------|
| **作用范围** | 单个 JVM 进程内 | 跨进程、跨节点 |
| **实现机制** | JVM 对象监视器 / AQS | 租约（Redis SETNX + EXPIRE） |
| **容错性** | 进程崩溃则锁释放 | 依赖 TTL 自动释放 |
| **适用场景** | 单机多线程并发 | 多节点分布式并发 |

### 分布式锁的三个不可替代场景

#### 场景一：跨越不可控边界的操作协调

**核心矛盾**：当操作流跨越到不可控的外部系统，Saga/2PC 失效，锁做预防性互斥。

```
获得锁
  → 调用支付宝扣款（全局只有一个节点在发起）
  → 扣款成功后，写本地订单状态
释放锁
```

- 锁不保证"扣款 + 写库"的原子性
- 锁保证的是"**同一笔业务不会因为并发竞争而被重复扣款**"
- 配合支付接口的**幂等键**（如 `out_trade_no`），形成"锁防并发 + 幂等防重试"的双重保险

#### 场景二：时间窗口互斥

**核心矛盾**：配额重置、定时任务等场景需要"某段时间内保证只执行一次"。

```java
// 每月1号 0:05 触发
if (redisson.getLock("quota:reset:2026-06").tryLock(0, 5, TimeUnit.MINUTES)) {
    try {
        // 执行全局配额重置
    } finally {
        redisson.getLock("quota:reset:2026-06").unlock();
    }
}
```

- **TTL 即窗口期**：锁的存活时间 = 保护窗口
- **自动过期即容错**：节点崩溃后锁自动释放，其他节点可补救
- **无状态协调**：不需要维护事务日志或补偿记录

#### 场景三：资源保护（缓存重建防击穿）

**核心矛盾**：保护下游系统（如 DB）不被并发压垮。

```
缓存失效
  → 1000 个请求同时到达
  → 只有一个线程获得锁，执行：查 DB → 计算 → 写 Redis
  → 其余 999 个线程：
       方案A：阻塞等待锁释放后读缓存
       方案B：快速失败返回降级数据
```

- **锁的临界区语义**：精确匹配"保护一段昂贵计算"
- **吞吐量权衡**：允许 999 个请求并发读缓存，只串行化那 1 个重建操作

### 分布式锁的局限性

| 局限 | 说明 | 解决方案 |
|------|------|---------|
| **不保证原子性** | 锁内操作失败后，状态可能不一致 | 配合幂等 + 对账 |
| **TTL 设置困难** | 太短可能导致锁提前释放，太长可能阻塞过久 | Redisson watchdog 自动续期 |
| **单点故障** | Redis 主从切换时可能丢失锁 | RedLock 算法（多节点 majority） |
| **性能瓶颈** | 高并发下锁竞争严重 | 限流 + 降级 + 本地缓存 |

## 关键关联

- [[互斥与原子性]] - 关联原因：分布式锁解决互斥问题（空间隔离），不解决原子性问题（状态一致）
- [[系统边界分类]] - 关联原因：不可控边界是分布式锁三个不可替代场景之首
- [[幂等性]] - 关联原因：锁 + 幂等形成"防并发 + 防重试"的双重保险
- [[最终一致性]] - 关联原因：跨越不可控边界后，锁只是最终一致性方案的一部分
- [[秒杀超卖与库存一致性]] - 关联原因：秒杀场景中 Redis 原子指令（DECR/Lua）已覆盖纯计数场景，分布式锁只在复合操作时才需要
- [[可重入分布式锁]] - 关联原因：分布式锁的增强特性，解决调用链嵌套导致的自我死锁
- [[锁上提模式]] - 关联原因：通过设计消除可重入需求的首选架构模式

## 我的误区与疑问

- ❌ 误区：以为分布式锁能保证操作的原子性（实际只保证互斥，不保证状态一致）
- ❌ 误区：以为分布式锁是分布式并发的默认选项（实际优先用原子指令、Lua 脚本、幂等键）
- ❓ 疑问：Redisson 的 watchdog 自动续期机制如何实现？（答：后台线程定期检查锁是否仍被持有，如果是则续期 TTL）

## 代码与实践

```java
// Redisson 分布式锁（标准用法）
RLock lock = redisson.getLock("order:deduct:123");
try {
    // 尝试获取锁，等待 10 秒，锁持有 30 秒
    boolean locked = lock.tryLock(10, 30, TimeUnit.SECONDS);
    if (locked) {
        // 执行业务逻辑
        // watchdog 会自动续期（默认每 10 秒检查一次）
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```
