# 动态路由场景分类（三层决策模型）

## 一句话定义

**按路由变化频率将 Web 服务分为三类，每类对应不同的编程风格和架构选择**

## 核心理解

### 三层决策框架

```
┌──────────┬──────────────────┬───────────────────────┐
│ 高频率    │ API 网关         │ ✅ 函数式（组合能力）   │
│ 变化      │ 多租户 SaaS      │                       │
├──────────┼──────────────────┼───────────────────────┤
│ 低频率    │ 灰度发布         │ 🔀 混合模式            │
│ 变化      │ 特性开关         │ (注解 + Filter/AOP)    │
├──────────┼──────────────────┼───────────────────────┤
│ 固定      │ 大多数业务 API   │ 📝 注解式（开发效率）   │
│ 不变      │ CRUD 服务        │                       │
└──────────┴──────────────────┴───────────────────────┘
```

### 核心洞察

1. **场景 1（高频变化）**：路由本身是产品功能，需要运行时动态调整
2. **场景 2（低频变化）**：本质上是场景 3 的临时变体，不是内容需求而是特殊需求
3. **场景 3（固定不变）**：大多数 Web 服务的常态，URL 规范化可读

---

## 场景 1 详细分析：高频变化

### 特征
- 路由需要根据外部条件动态生成或修改
- 不同用户/租户/环境看到不同的 API
- 路由结构可能随时间演变

### 典型案例

#### 案例 A：API 网关 / BFF（Backend for Frontend）

```
                    ┌──────────────┐
   移动端 App ─────→│              │
                    │   API 网关    │ ← 动态路由聚合
   Web 前端 ──────→│  (BFF 层)     │
                    │              │
   第三方调用 ─────→└──────┬───────┘
                           │
            ┌──────────────┼──────────────┐
            ↓              ↓              ↓
      用户服务          订单服务         库存服务
```

```java
// 根据客户端类型返回不同的数据格式
@Bean
RouterFunction<ServerResponse> bffRoutes(Handler handler) {
    return route()
        .nest(path("/api"), req -> {
            String client = req.headers().firstHeader("X-Client-Type");
            
            return switch (client) {
                case "mobile" -> mobileRoutes(handler);     // 精简版
                case "web" -> webRoutes(handler);           // 完整版
                case "third-party" -> thirdPartyRoutes(handler); // 开放版
                default -> errorResponse("Unknown client");
            };
        })
        .build();
}
```

**关键点**：URL 对消费者是稳定的，但后端路由是动态组合的

#### 案例 B：多租户 SaaS

```java
// 不同租户看到不同的 API 功能
@Bean
RouterFunction<ServerResponse> tenantRoutes(TenantConfig config) {
    return route()
        .nest(path("/api/custom"), () -> 
            config.hasFeature("custom_fields")
                ? customFieldRoutes()
                : route()  // 无此功能，返回 404
        )
        .nest(path("/api/approval"), () ->
            config.getApprovalType() == "simple"
                ? simpleApprovalRoutes()
                : complexApprovalRoutes()
        )
        .build();
}
```

**例子**：Salesforce、钉钉、飞书、Shopify、有赞

#### 案例 C：插件化架构 / 低代码平台

```java
// 每个模块导出自己的路由
@Component
public class StockModule implements Module {
    @Override
    public RouterFunction<ServerResponse> routes(Handler handler) {
        return route()
            .nest(path("/stock"), () ->
                route()
                    .GET("/{sku}", handler::getStock)
                    .POST("/{sku}/decrement", handler::decrement)
            )
            .before(requestLogInterceptor)
            .after(responseTimeInterceptor);
    }
}

// 主应用自动聚合所有模块
@SpringBootApplication
public class Application {
    @Bean
    RouterFunction<ServerResponse> router(List<Module> modules, Handler handler) {
        return modules.stream()
            .map(m -> m.routes(handler))
            .reduce(RouterFunction::and)
            .orElse(route());
    }
}
```

**适用场景**：CMS、低代码平台、微信小程序平台、商家定制服务

#### 案例 D：环境差异

```java
// 开发环境暴露调试接口，生产环境自动移除
@Bean  
RouterFunction<ServerResponse> appRoutes(Handler handler) {
    RouterFunction<ServerResponse> prod = route()
        .GET("/api/stock", handler::getStock)
        .POST("/api/stock/decrement", handler::decrement);
    
    if (env.isDev()) {
        prod = prod.and(route()
            .GET("/debug/health", handler::healthCheck)
            .GET("/debug/metrics", handler::metrics)
            .POST("/debug/reset-data", handler::resetData)  // 危险！仅开发用
        );
    }
    
    return prod;
}
```

## 场景 2 详细分析：低频变化

### 特征
- 路由本身是固定的，但内部逻辑需要动态切换
- 通常用于发布策略或实验性功能
- 本质上是场景 3 的临时变体

### 最佳实践：混合模式（注解 + 拦截器）

#### 方案 A：注解 + AOP（最常用）

```java
// 保持注解式的简洁性，用 AOP 处理动态逻辑

@RestController
@RequestMapping("/api/stock")
public class StockController {
    
    @GetMapping("/{sku}")
    @GrayRelease(experiment = "new_algo", group = "B")  // 轻量注解
    public Mono<StockResponse> getStock(@PathVariable String sku) {
        return stockService.getStock(sku);
    }
}

// AOP 切面处理动态分发
@Aspect
@Component
public class GrayReleaseAspect {
    
    @Around("@annotation(gray)")
    public Object around(ProceedingJoinPoint pjp, GrayRelease gray) throws Throwable {
        String userId = getCurrentUserId();
        
        if (isInExperimentGroup(userId, gray.experiment(), gray.group())) {
            // 走新逻辑（可能调用不同的 Service）
            return ((StockService) getNewService()).getStock(...);
        }
        
        return pjp.proceed();  // 原始逻辑
    }
}
```

**优点**：代码改动小，开发者无感知  
**缺点**：AOP 有"魔法"，调试困难

#### 方案 B：配置驱动 + Filter（推荐）

```yaml
# application.yml
features:
  new-stock-api:
    enabled: true
    percentage: 10  # 10% 流量走新接口
```

```java
// 用 Filter 统一处理，不改任何 Controller
@Component
public class FeatureGateFilter implements WebFilter {
    
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, WebFilterChain chain) {
        String path = exchange.getRequest().getPath().value();
        
        if (shouldRedirectToV2(path)) {
            return chain.filter(mutatePath(exchange, "/api/v2" + path));
        }
        
        return chain.filter(exchange);
    }
}
```

**优点**：完全无侵入，配置驱动  
**缺点**：Filter 层逻辑可能变得复杂

### 其他场景

| 场景 | 实现方式 | 说明 |
|------|---------|------|
| 灰度发布 | Filter + 权重路由 | 按比例分流流量 |
| 特性开关 | 配置 + 条件判断 | 功能未上线时隐藏路由 |
| A/B 测试 | Cookie/Header + 动态分发 | 同 URL 不同逻辑 |

## 场景 3 详细分析：固定不变

### 特征
- URL 结构稳定，遵循 RESTful 规范
- 面向最终消费者（人或前端 JS）
- 大多数传统业务 API

### 适用范围

```java
// 典型的 CRUD 服务
@RestController
@RequestMapping("/api/v1")
public class StockController {
    
    @GetMapping("/stocks")           // 查询列表
    public Flux<StockResponse> listStocks() { ... }
    
    @GetMapping("/stocks/{sku}")     // 查询单个
    public Mono<StockResponse> getStock(@PathVariable String sku) { ... }
    
    @PostMapping("/stocks")          // 创建
    public Mono<StockResponse> createStock(@RequestBody CreateRequest req) { ... }
    
    @PutMapping("/stocks/{sku}")     // 更新
    public Mono<StockResponse> updateStock(...) { ... }
    
    @DeleteMapping("/stocks/{sku}")  // 删除
    public Mono<Void> deleteStock(@PathVariable String sku) { ... }
}
```

**为什么用注解式**：
- 开发效率最高（符合直觉，易读易维护）
- 团队协作友好（新人容易上手）
- 工具支持完善（Swagger 自动生成文档）
- 不需要动态组合能力

## 延伸思考：非人类消费者的 Web 服务

### 核心观点

**大多数 Web 服务都不是给人看的！**

```
现代 Web 服务的请求来源分布：

┌─────────────────────────────────────────┐
│                                         │
│  ██████████████  70%  前端 JS / App     │
│  ████████        30%  其他服务 / 机器    │
│  ██              5%   人类浏览器直连     │
│                                         │
│  结论：大部分 Web 服务主要给代码消费！    │
└─────────────────────────────────────────┘
```

### 非人类消费者分类

| 类别 | 示例 | 特点 |
|------|------|------|
| **机器对机器 (M2M)** | 支付回调、Webhook、微服务间调用 | 异步通知，JSON 格式 |
| **前端框架消费** | Vue/React 调用的 API | 返回 JSON，前端渲染 |
| **基础设施服务** | Prometheus metrics、K8s healthz | 纯文本/特定格式 |
| **AI/Agent 消费** | LLM Function Calling、MCP 协议 | 结构化输出 |

### HTTP vs 非 HTTP 决策

```
┌─────────────────────────────────────────────────────┐
│                  决策树                              │
│                                                     │
│  QPS > 100K？                                       │
│    ├─ 是 → 考虑 gRPC / 自定义协议                    │
│    └─ 否 → 继续 ↓                                   │
│                                                     │
│  延迟要求 < 1ms？                                    │
│    ├─ 是 → 考虑共享内存 / RDMA                       │
│    └─ 否 → 继续 ↓                                   │
│                                                     │
│  内部微服务且团队成熟？                               │
│    ├─ 是 → 可选 gRPC                                │
│    └─ 否 → HTTP（省心）                              │
│                                                     │
│  结论：除非有明确性能瓶颈，否则 HTTP 成本更低          │
└─────────────────────────────────────────────────────┘
```

**为什么机器间通信还用 HTTP**：
- 生态工具友好（curl、Postman、浏览器调试）
- 运维友好（Nginx/网关可直接代理）
- 可观测性好（日志/链路追踪成熟）
- 团队学习成本几乎为零
