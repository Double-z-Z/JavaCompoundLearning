# 可重入分布式锁

## 一句话定义
可重入分布式锁是**同一线程在持有锁期间，能够再次获取同一锁而不被阻塞**的分布式锁实现——解决的是"调用链嵌套导致的自我死锁"，而非"并发互斥"本身。

## 核心理解

### 为什么本地锁天然可重入，分布式锁需要额外实现？

| 维度 | 本地锁（ReentrantLock） | 分布式锁（Redis） |
|------|------------------------|------------------|
| **线程标识** | JVM Thread ID | 需模拟：UUID + threadId |
| **重入计数** | AQS state 字段 | 需模拟：Hash field value |
| **存储位置** | JVM 堆内存 | Redis 远程存储 |
| **实现成本** | 语言原生支持 | 需 Lua 脚本 + 网络交互 |

### Redisson 的可重入实现

Redisson 使用 **Hash 结构**实现可重入：

```
{lock_name} -> field: {UUID}:{threadId}, value: 重入计数
```

**加锁 Lua 脚本**（简化）：
```lua
if (redis.call('exists', KEYS[1]) == 0) then
    redis.call('hset', KEYS[1], ARGV[2], 1);
    redis.call('pexpire', KEYS[1], ARGV[1]);
    return nil;
end;
if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then
    redis.call('hincrby', KEYS[1], ARGV[2], 1);
    redis.call('pexpire', KEYS[1], ARGV[1]);
    return nil;
end;
return 1;
```

**释放 Lua 脚本**（简化）：
```lua
local counter = redis.call('hincrby', KEYS[1], ARGV[3], -1);
if (counter > 0) then
    redis.call('pexpire', KEYS[1], ARGV[2]);
    return 0;
end;
redis.call('del', KEYS[1]);
```

### 可重入锁的运行成本

| 成本项 | 不可重入锁（SET NX EX） | 可重入锁（Redisson Hash） |
|--------|------------------------|--------------------------|
| **Redis 交互** | 1 RTT 获取 + 1 RTT 释放 | 每次 EVAL Lua 脚本 |
| **数据结构** | String，O(1) | Hash，维护 field 映射 |
| **脚本复杂度** | 极简 if-get-del | 多分支 hexists/hincrby |
| **额外开销** | 无 | 每次加锁多一次 hexists 判断，Redis 执行时间增加约 20-40% |

> 关键洞察：可重入锁在**不可重入场景下也有额外开销**——这是 Redisson 作为通用框架的"防御性代价"。

## 我的误区与疑问

- ❌ 误区：以为可重入锁是分布式锁的"标配"（实际 80% 场景不需要）
- ❌ 误区：以为 Redisson 默认可重入意味着业务代码也应该默认可重入（框架防御性 ≠ 业务最佳实践）
