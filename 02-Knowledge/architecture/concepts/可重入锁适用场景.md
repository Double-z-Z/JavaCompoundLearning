# 可重入锁适用场景

## 一句话定义
可重入分布式锁只在**同一线程需要重复进入同一聚合根临界区**时才不可替代——场景属于"窄带刚需"，遇到时无法通过简单重构规避。

## 核心理解

### 场景一：递归聚合根操作（树/图结构）

**触发条件**：同一线程内对同一聚合根的递归调用，且每一层都需要锁保护。

```java
@DistributedLock(key = "'org:' + #orgId")
public void updateOrgTree(Long orgId) {
    OrgNode node = orgRepository.findById(orgId);
    node.updateName("newName");
    
    // 递归处理子节点，子节点变更需要级联回写根节点统计
    for (Long childId : node.getChildrenIds()) {
        updateOrgTree(childId);  // 再次进入同一锁
    }
    
    cacheEvict("org:" + orgId);
}
```

**为什么必须可重入**：
- 递归调用栈中，同一线程会多次尝试获取以 `orgId` 为 key 的分布式锁
- 如果锁不可重入，第二次调用时会被自己阻塞，导致死锁

**重构替代**：最外层加锁 + 内部无锁递归（但需保证递归深度可控）

---

### 场景二：框架层与业务层的锁重叠（AOP/拦截器嵌套）

**触发条件**：基础设施层和业务层各自独立加锁，运行时发生嵌套。

```java
// 基础设施层：防重复提交拦截器
@Interceptor
@DistributedLock(key = "'submit:' + #userId", waitTime = 0)
public void antiResubmit(InvocationContext ctx) {
    ctx.proceed();  // 进入业务层
}

// 业务层：库存扣减服务
@Service
@DistributedLock(key = "'stock:' + #skuId")
public void deductStock(Long skuId) {
    // ...
}
```

**更典型的变体——事务传播与锁传播不匹配**：
```java
@Transactional(propagation = REQUIRED)
@DistributedLock(key = "'account:' + #accountId")
public void transfer(Account from, Account to) {
    debit(from);
    credit(to);  // credit 内部也有 @DistributedLock(key = "'account:' + #to.id")
}
```

**为什么必须可重入**：
- Service 方法既被外部直接调用（需锁），又被内部组合调用（不应锁）
- 锁的职责没有内聚到单一入口

**重构替代**：抽取 Facade 层统一加锁，Core 层方法无锁（见 [[锁上提模式]]）

---

### 场景三：回调与事件驱动架构中的"循环进入"

**触发条件**：同步事件派发导致处理流程绕回已加锁的资源。

```java
@DistributedLock(key = "'order:' + #orderId")
public void processOrderEvent(OrderEvent event) {
    orderService.updateStatus(event);
    eventBus.publish(new InventoryReleaseEvent(event.getOrderId()));
}

@EventListener
@DistributedLock(key = "'order:' + #event.orderId")
public void onInventoryReleased(InventoryReleaseEvent event) {
    orderService.markInventoryReleased(event.getOrderId());
}
```

**为什么必须可重入**：
- Spring 的 `ApplicationEvent` 同线程传播时，事件处理器与发布者在同一线程
- 如果都需要保护同一聚合根，不可重入锁会死锁

**重构替代**：改为异步事件派发，或状态机驱动消除同步锁依赖

---

### 场景四：锁的"读-写升级"

**触发条件**：Redisson 的 `RReadWriteLock` 中，读锁内需要升级获取写锁。

```java
RReadWriteLock rwLock = redissonClient.getReadWriteLock("configLock");
RLock readLock = rwLock.readLock();
RLock writeLock = rwLock.writeLock();

readLock.lock();
try {
    Config config = configCache.get("global");
    if (config.isStale()) {
        writeLock.lock();  // 如果读写锁不可重入，此处死锁
        try {
            config = loadFromDB();
            configCache.put("global", config);
        } finally {
            writeLock.unlock();
        }
    }
} finally {
    readLock.unlock();
}
```

**Redisson 特性**：`RReadWriteLock` 支持**写锁可重入**和**读锁到写锁的升级**（需同一线程）。

**重构替代**：直接获取写锁（牺牲部分并发性，但消除可重入需求）

---

## 场景总结

| 场景 | 触发条件 | 重构可能性 | 不可替代性 |
|------|---------|-----------|-----------|
| 递归聚合根 | 同线程递归调用同一锁 | 中（外层锁+无锁递归） | 递归深度不确定时不可替代 |
| AOP 嵌套 | 框架锁与业务锁冲突 | 高（锁上提） | 第三方框架无法修改时不可替代 |
| 事件循环 | 同步事件绕回同一聚合根 | 中（异步化/状态机） | 同步事件架构下不可替代 |
| 读写升级 | 读锁内获取写锁 | 高（直接写锁） | 高并发读场景下不可替代 |

## 我的误区与疑问

- ❌ 误区：以为缓存重建需要可重入锁（实际业界标准是单锁无重入）
- ❌ 误区：以为分层缓存需要每层各自加锁（实际是不同层级用不同技术：Singleflight/分布式锁/限流）
