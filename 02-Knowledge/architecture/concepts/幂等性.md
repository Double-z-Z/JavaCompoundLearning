# 幂等性

## 一句话定义

幂等性是**同一操作执行一次或多次产生相同结果**的特性，它防重复执行但不防并发冲突，是分布式系统的"安全带"而非"防弹衣"。


## 核心理解

### 幂等解决什么问题？

分布式系统中，同一个请求被重复执行的根因：

| 根因 | 具体场景 |
|------|---------|
| **网络超时重试** | 客户端发送扣减请求，服务端已执行成功但响应丢失，客户端超时后重试 |
| **MQ 消息重复投递** | Kafka/RocketMQ 的 At-Least-Once 语义，消费者处理完但 ACK 超时，Broker 重新投递 |
| **用户重复点击** | 用户狂点"提交订单"按钮，前端防抖失效，发出多个相同请求 |
| **定时任务重叠** | 补偿任务扫描，上一轮还没跑完，下一轮又启动，重复触发补偿 |
| **服务发布/回滚** | 消费者处理消息时实例重启，消息被重新分发给新实例 |

### 幂等 ≠ 并发安全

**这是最关键的区分**：

| 问题 | 幂等能否解决 | 为什么 | 真正需要什么 |
|------|-------------|--------|-------------|
| **重复执行同一请求** | ✅ 能 | 幂等键命中，直接返回已处理结果 | 幂等键唯一索引 |
| **并发竞态（两个不同请求同时扣减）** | ❌ 不能 | 两个请求的幂等键不同，都是"第一次" | **原子操作**（Lua / CAS / 分布式锁） |
| **执行顺序错乱** | ❌ 不能 | 幂等不关心 T1 和 T2 谁先谁后 | **顺序控制**（MQ 分区顺序消费 / 状态机） |
| **补偿与正常请求冲突** | ❌ 不能 | 补偿请求和普通扣减并发，各自幂等键不同 | **并发控制**（版本号 / 分布式锁） |
| **业务逻辑错误** | ❌ 不能 | 代码把扣减写成增加，幂等只是重复执行错误 | **测试 / 对账 / 监控** |
| **数据全局不一致** | ❌ 不能 | Node1 和 Node2 数据已分叉 | **对账 / 最终一致性修复** |

### 幂等键设计原则

```
幂等键 = 业务唯一标识 + 操作维度

示例：
- 订单扣减：order_id + sku_id → "deduct:order_1001:SKU001"
- 支付回调：order_id + 支付渠道 → "pay:order_1001:alipay"
- 消息消费：msg_id + 消费者组 → "consume:msg_xxx:group_inventory"
```

**关键**：幂等键必须带有**过期时间**（如 24h），否则键空间无限增长；同时保留足够长的时间供对账使用。


## 关键关联

- [[Saga模式]] - 关联原因：Saga 的补偿阶段可能被重复触发，补偿操作必须是幂等的，否则重复补偿会导致库存超卖
- [[秒杀超卖与库存一致性]] - 关联原因：Redis Lua 脚本中的幂等键设计是秒杀库存扣减的标配，防网络重试和 MQ 重复消费
- [[Redis-String]] - 关联原因：`SETNX` / `SET key value EX seconds NX` 是实现分布式幂等键的原子命令基础
- [[乐观锁]] - 关联原因：幂等解决"重复"，乐观锁解决"并发"，两者必须配合使用才能保证库存安全
- [[最终一致性]] - 关联原因：幂等是最终一致性方案的第二层（防重层），与锁（预防层）和对账（修复层）配合
- [[分布式锁]] - 关联原因：锁 + 幂等形成"防并发 + 防重试"的双重保险，锁降低并发面，幂等处理残留风险


## 我的误区与疑问

- ❌ 误区：加了幂等键就万无一失了
  - 纠正：幂等只防重复执行，不防并发。秒杀场景下必须**幂等键 + Lua 原子脚本**同时使用。
- ❌ 误区：幂等键永久保存最安全
  - 纠正：永久保存会导致键空间爆炸，且无法清理历史。应设置 TTL（如 24h~7d），同时配合离线对账兜底。
- ❓ 疑问：补偿操作的幂等和正常操作的幂等需要不同的键吗？
  - 答案：建议统一。补偿操作本质上是对同一业务对象的修改，使用相同的业务唯一标识（order_id + sku_id）即可。关键是补偿逻辑本身也要检查幂等键，避免重复回补。


## 代码与实践

### 秒杀库存扣减的幂等 Lua 脚本

```lua
-- KEYS[1]: stock:SKU001
-- KEYS[2]: idempotent:order_1001:SKU001
-- ARGV[1]: quantity

-- 1. 幂等检查：是否已处理过该订单的该 SKU
if redis.call('EXISTS', KEYS[2]) == 1 then
    return {1, "ALREADY_PROCESSED"}
end

-- 2. 库存检查
local stock = tonumber(redis.call('GET', KEYS[1]))
if not stock or stock < tonumber(ARGV[1]) then
    return {0, "OUT_OF_STOCK"}
end

-- 3. 原子扣减 + 记录幂等（带过期时间）
redis.call('DECRBY', KEYS[1], ARGV[1])
redis.call('SET', KEYS[2], 1, 'EX', 86400)  -- 保留1天供对账

return {1, "SUCCESS"}
```

**设计要点**：
- `EXISTS` 检查 + `DECRBY` + `SET` 全部在同一个 Lua 脚本中，保证**原子性**
- 幂等键带 TTL，平衡防重和对账需求
- 返回值区分"已处理"、"库存不足"、"成功"三种状态


## 深入思考

💡 幂等性是分布式系统的"事后保险"——它假设"重复一定会发生"，并在发生后阻止破坏。但它不能替代"事前防御"（原子操作、并发控制）。好的架构是"事前防并发 + 事后防重复"的双重保障。
