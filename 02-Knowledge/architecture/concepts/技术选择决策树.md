# 分布式系统技术选择决策树

## 一句话定义
分布式系统技术选择决策树是根据**系统边界类型、一致性需求、业务流程复杂度**三个维度，快速判断应该使用分布式锁、Saga、2PC 还是最终一致性方案的决策工具。

## 核心理解

### 第一层：系统边界判断

```
操作是否跨越不可控系统边界？（外部 API、第三方服务、无补偿能力的遗留系统）
├─ 是 → 分布式锁做预防性互斥（Saga/2PC 失效）
│         ↓
│       配合幂等 + 对账实现最终一致性
└─ 否 → 进入第二层
```

**关键认知**：不是"跨存储介质"，而是"**跨不可控边界**"才需要分布式锁。

### 第二层：原子性需求判断

```
是否需要保证"一组操作要么全成功要么全回滚"？
├─ 否 → 分布式锁或本地事务即可
└─ 是 → 进入第三层
```

### 第三层：一致性强度判断

```
是否需要强一致且所有参与者支持 XA？
├─ 是 → 2PC（如银行核心账务）
└─ 否 → Saga（可补偿的长业务流程）
```

### 完整决策树

```
1. 操作是否跨越不可控系统边界？
   ├─ 是 → 分布式锁 + 幂等 + 对账（最终一致性）
   └─ 否 → 进入 2

2. 是否需要保证原子性（全有或全无）？
   ├─ 否 → 分布式锁或本地事务
   └─ 是 → 进入 3

3. 是否需要强一致且所有参与者支持 XA？
   ├─ 是 → 2PC
   └─ 否 → Saga
```

### 快速对照表

| 场景特征 | 推荐方案 | 原因 |
|---------|---------|------|
| 外部 API 调用 + 写本地 DB | **分布式锁 + 幂等 + 对账** | 不可控边界，Saga/2PC 失效 |
| 定时任务/配额重置 | **分布式锁** | 时间窗口互斥，无业务流程步骤 |
| 缓存重建防击穿 | **分布式锁** | 资源保护问题，非状态一致性问题 |
| 订单 → 库存 → 物流 → 积分 | **Saga** | 多步骤业务流程，所有步骤可补偿 |
| 银行转账 | **2PC** | 强一致必须保证，所有参与者支持 XA |
| 纯计数扣减（Redis DECR）| **原子指令** | 单条命令即可，无需锁/Saga/2PC |
| 网络超时重试 | **幂等键** | 防重但不防并发 |

### 三者核心区别速查

| 维度 | 分布式锁 | Saga | 2PC |
|------|---------|------|-----|
| **核心目标** | 空间互斥（单执行者） | 长事务原子性（可补偿） | 短事务原子性（强一致） |
| **一致性** | 无 | 最终一致 | 强一致 |
| **参与者要求** | 无需特殊协议 | 所有操作可补偿 | 所有参与者支持 XA/prepare |
| **性能** | 最好 | 好 | 差 |
| **故障代价** | 暂时串行化失败 | 补偿风暴/中间态 | 协调器阻塞/脑裂 |

## 我的误区与疑问

- ❌ 误区：以为所有分布式场景都需要分布式锁（实际优先用原子指令、Lua 脚本、幂等键）
- ❌ 误区：以为 Saga 可以替代分布式锁（实际两者正交，Saga 解决原子性，锁解决互斥）
- ❓ 疑问：如果业务场景同时需要互斥和原子性，如何组合使用？（答：锁内嵌套 Saga，或 Saga 的某一步使用锁）

## 深入思考

💡 决策树中的"不可控边界"是否有可能随着外部系统开放接口而变成"半可控"？
💡 如果业务场景在决策树的多个分支之间摇摆，说明什么？（答：可能业务需求不清晰，或需要拆分服务）
