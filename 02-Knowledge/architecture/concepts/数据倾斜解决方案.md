# 数据倾斜解决方案

## 一句话定义

数据倾斜是指**热点 key 集中落到 Redis 同一节点**导致的单点瓶颈问题，需要通过分层防御架构来解决。

## 核心理解

### 问题的本质

```
Web 服务器（无状态）          Redis（有状态）
┌──────────────────┐        ┌──────────────────┐
│ 负载均衡器        │        │ Hash(key) % 16384│
│   ↓              │        │      ↓           │
│ 实例A ← 请求可分发 │   vs   │ Slot 5432         │
│ 实例B ← 到任意实例 │        │   ↓               │
│ 实例C              │        │ 固定节点！无法分散！│
└──────────────────┘        └──────────────────┘

关键矛盾：
- Web 服务器：无状态，请求可以动态分配到任意实例
- Redis：有状态，槽位预分配，热点 key 永远落在同一节点
```

### 三大风险

| 风险 | 表现 | 后果 | 严重程度 |
|------|------|------|---------|
| Redis CPU 飙高 | 单点 QPS 过载 | 响应延迟飙升 | 🔴 高 |
| 网络延迟叠加 | 所有请求串行等待 | RT 从 1ms → 100ms+ | 🟡 中 |
| 超卖风险 | 并发扣减竞争 | 库存变负数 | 🔴 高 |

## 分层防御架构

```
                    ┌─────────────────────────────────┐
  用户请求 ─────────▶│ 第0层：Nginx 令牌桶限流          │  ← "解决提出需求的人"
                    │ （拒绝溢出部分，保护后端）          │
                    └──────────────┬──────────────────┘
                                   ▼
                    ┌─────────────────────────────────┐
  通过限流 ────────▶│ 第1层：前端削峰（排队/延时）      │  ← "降低响应时间"
                    │ （异步队列缓冲，平滑流量曲线）       │
                    └──────────────┬──────────────────┘
                                   ▼
                    ┌─────────────────────────────────┐
  到达后端 ────────▶│ 第2层：Caffeine 本地缓存          │  ← 吸收读压力
                    │ （L1 Cache，热点数据本地化）        │
                    └──────────────┬──────────────────┘
                                   ▼
                    ┌─────────────────────────────────┐
  写操作 ──────────▶│ 第3层：Redis + Lua              │  ← 最后防线
                    │ （原子扣减，尽力而为）             │
                    └─────────────────────────────────┘
```

### 各层策略对比

| 层级 | 策略 | 解决的问题 | 牺牲什么 | 技术实现 |
|------|------|-----------|---------|---------|
| **Nginx 限流** | **拒绝** | 流量过载 | 部分用户体验 | 令牌桶/漏桶算法 |
| **前端削峰** | **延时** | 瞬时峰值 | 响应时间 | MQ 异步队列、倒计时 |
| **本地缓存** | **近似** | 读热点 | 强一致性 | Caffeine LRU |
| **Redis Lua** | **串行** | 写一致性 | 吞吐量上限 | Lua 原子脚本 |

## 核心技术方案

### 方案1：多级缓存（读优化）

#### 架构设计

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  浏览器缓存   │ →  │  CDN 缓存   │ →  │ Nginx 缓存  │
│  (静态资源)   │    │ (边缘节点)   │    │ (本地缓存)   │
└─────────────┘    └─────────────┘    └─────────────┘
                                               │
                                               ▼
                                        ┌─────────────┐
                                        │ Caffeine     │
                                        │ (JVM本地)    │
                                        └─────────────┘
                                               │
                                               ▼
                                        ┌─────────────┐
                                        │ Redis        │
                                        │ (分布式)     │
                                        └─────────────┘
```

#### Caffeine 本地缓存配置

```java
// redis-counter-service-webflux 项目实际代码
this.localCache = Caffeine.newBuilder()
        .maximumSize(1000)                    // 最大1000条
        .expireAfterWrite(5, TimeUnit.MINUTES) // 5分钟过期
        .recordStats()                        // 记录统计信息
        .build();
```

#### 读操作流程

```java
public Mono<String> getStockWithCache(String sku) {
    String key = "stock:" + sku;

    // 第一步：先查本地缓存
    String cached = localCache.getIfPresent(key);
    if (cached != null) {
        log.debug("Cache hit for {}", sku);
        return Mono.just(cached);  // 命中直接返回
    }

    // 第二步：缓存未命中，查 Redis
    log.debug("Cache miss for {}", sku);
    return redisTemplate.opsForValue()
            .get(key)
            .switchIfEmpty(Mono.just("0"))
            .doOnNext(stock -> localCache.put(key, stock));  // 回填缓存
}
```

**关键原则**：**本地缓存只能解决读热点问题！**

### 方案2：写操作穿透 + 缓存失效

#### 为什么写操作不能走本地缓存？

```java
// ❌ 错误场景：如果写操作也走本地缓存
实例1: 本地库存=100 → 扣10 → 本地变成90 ✓
实例2: 本地库存=100 → 扣20 → 本地变成80 ✓  
实例3: 本地库存=100 → 扣30 → 本地变成70 ✓

// 实际 Redis 还是 100... 超卖了60个！❌
```

**生活类比**：
- **本地缓存 = 门口的电子屏**：显示"当前还有5桌空位"（读操作，大家都能看）
- **Redis = 收银台系统**：真正下单扣减座位（写操作，必须统一）

#### 正确的写操作策略

```java
public Mono<String> decrementWithCache(String sku, long quantity) {
    String key = "stock:" + sku;

    // 注意：写操作直接走 Redis！
    return redisTemplate.execute(
                    decrementScript,
                    List.of(key),
                    List.of(String.valueOf(quantity))
            ).next()
            .map(result -> {
                long remaining = result.longValue();
                if (remaining != -1) {
                    localCache.invalidate(key);  // ✅ 扣减成功后主动失效缓存
                    log.debug("Decremented {} to {}, invalidated cache", sku, remaining);
                }
                return String.valueOf(remaining);
            })
            .onErrorReturn("-1")
            .defaultIfEmpty("-1");
}
```

**核心策略**：**写操作必须穿透到 Redis 保证一致性，然后主动失效本地缓存**

### 方案3：Lua 脚本原子操作（防超卖）

#### 库存扣减脚本

```lua
-- ReactiveRedisConfig.java 中的 Lua 脚本
local stock = tonumber(redis.call('GET', KEYS[1]) or 0)
local quantity = tonumber(ARGV[1])
if stock >= quantity then
    return redis.call('DECRBY', KEYS[1], quantity)
else
    return -1  -- 库存不足
end
```

**为什么用 Lua？**
- ✅ **原子性**：整个脚本在 Redis 单线程中执行，不会被其他命令打断
- ✅ **减少网络往返**：一次调用完成 "读取→判断→扣减"
- ⚠️ **但不是万能**：Lua 能防超卖，但不能解决单点击穿问题

## 可预知流量 vs 动态优化

### 场景分类

| 场景类型 | 特征 | 策略方向 |
|---------|------|---------|
| **完全可预知** | 时间+流量已知（如双11秒杀） | 提前预热 + 静态策略 |
| **半可预知** | 大概时间段已知（如晚上8点多） | 自适应动态优化 |
| **突发不可预知** | 无法预测（如热搜事件） | 自动化限流 + 降级 |

### 可预知场景：预热与静态策略

**示例**："周五20:00 iPhone16 10000台"

```java
// 1. 提前5分钟：多级缓存预热
caffeineCache.put("hot:sku1001", stockVO);  // 本地缓存
redis.set("stock:sku1001", 10000);           // Redis

// 2. 提前1分钟：弹性扩容（K8s HPA / 云厂商弹性伸缩）
// 将秒杀服务实例从10个扩容到100个，分散连接压力

// 3. 提前30秒：队列预热
rocketMQ.createTopic("seckill:sku1001", 16); // 预分配队列，避免创建延迟
```

**交互层配合**：
- **脉冲式放流**：按钮不是立即开放，而是每100ms放行一批请求
- **真实排队信息**：显示"前方排队XXX人"，XXX是真实的Redis/MQ堆积量

### 半可预知场景：自适应动态优化

#### 动态优化矩阵

| 优化维度 | 触发条件 | 动作 | 效果 |
|---------|---------|------|------|
| **限流阈值自适应** | CPU > 80% 或 RT > 500ms | Sentinel 下调 QPS 阈值 | 保护系统不崩 |
| **缓存TTL动态调整** | Redis 单节点QPS > 50k | 延长本地缓存TTL（1s→3s） | 减少Redis压力 |
| **队列消费背压** | MQ 堆积 > 10万 | 降低消费速率 | 防止MySQL被打挂 |
| **批次粒度调整** | 第一批次10秒售罄 | 减少单批数量、增加间隔 | 平滑流量曲线 |

#### 自适应限流伪代码

```java
if (systemLoad.getCpuUsage() > 0.8) {
    // 动态下调令牌桶速率，而非硬编码200k
    tokenBucket.setRate(currentRate * 0.7);
    
    // 通知前端：当前抢购人数过多，进入排队模式
    eventPublisher.publish(new ThrottleEvent("reduce_rate", currentRate * 0.7));
}
```

## 常见误区

| 误区 | 正确理解 |
|------|----------|
| "本地缓存能解决所有性能问题" | 只能解决读热点；写操作必须穿透 Redis |
| "增加 Redis 节点就能解决倾斜" | 槽位是预分配的，热点 key 仍在同一节点 |
| "Lua 脚本能防止所有问题" | Lua 保证原子性，但不提升吞吐量 |
| "限流是最后手段" | 限流应该是**第一道防线**，保护后端系统 |
| "前端验证能防止刷单" | 前端验证可被绕过，必须在服务端做最终校验 |

## 最佳实践

### 架构设计原则

```java
// ✅ 推荐的多级缓存架构
public class HotStockCacheServiceImpl implements HotStockCacheService {

    private final Cache<String, String> localCache;  // L1: Caffeine
    private final ReactiveStringRedisTemplate redisTemplate;  // L2: Redis

    public Mono<String> getStockWithCache(String sku) {
        // 1. 先查本地缓存（快速路径）
        String cached = localCache.getIfPresent(key);
        if (cached != null) {
            return Mono.just(cached);
        }
        
        // 2. 再查 Redis（慢速路径）
        return redisTemplate.opsForValue().get(key)
            .switchIfEmpty(Mono.just("0"))
            .doOnNext(stock -> localCache.put(key, stock));  // 3. 回填缓存
    }

    public Mono<String> decrementWithCache(String sku, long quantity) {
        // 4. 写操作直接穿透 Redis
        return redisTemplate.execute(decrementScript, ...)
            .next()
            .map(result -> {
                if (remaining != -1) {
                    localCache.invalidate(key);  // 5. 主动失效缓存
                }
                return String.valueOf(remaining);
            });
    }
}
```
