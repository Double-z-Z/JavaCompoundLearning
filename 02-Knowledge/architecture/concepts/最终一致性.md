# 最终一致性

## 一句话定义
最终一致性是分布式系统中**允许中间状态存在，但保证在没有新更新的情况下，所有副本最终达到一致**的一致性模型；跨越不可控边界后，锁 + 幂等 + 对账构成实现最终一致性的典型方案。

## 核心理解

### 为什么需要最终一致性

CAP 定理：在分区容错（P）的前提下，强一致（C）和可用性（A）无法兼得。

```
高并发场景下的选择：
├─ 追求强一致（2PC）→ 系统阻塞/吞吐量极低 → 全部用户失败
└─ 接受最终一致（Saga/锁+幂等+对账）→ 系统保持可用 → 极少数不一致可补偿
```

### 最终一致性的实现层次

| 层次 | 机制 | 作用 | 例子 |
|------|------|------|------|
| **L1: 预防** | 分布式锁 | 降低并发面，预防冲突发生 | 外部 API 调用前加锁 |
| **L2: 防重** | 幂等键 | 防止同一请求被重复执行 | 支付接口的 `out_trade_no` |
| **L3: 修复** | 对账 | 定期比对状态，发现不一致后修复 | 每日比对订单表和支付流水 |

### 跨越不可控边界的完整方案

```
场景：调用支付宝扣款 + 写本地订单状态

1. 预防层：分布式锁
   获得锁
     → 调用支付宝扣款（全局只有一个节点在发起）
     → 扣款成功后，写本地订单状态
   释放锁

2. 防重层：幂等键
   支付宝接口的 out_trade_no = 业务订单号
   即使锁失效导致重复调用，支付宝也会返回同一笔扣款结果

3. 修复层：对账
   每日比对本地订单表和支付宝流水
   发现"本地已扣款但支付宝未扣"或"支付宝已扣但本地未记录"时人工/自动修复
```

### 最终一致性 vs 强一致性

| 维度 | 最终一致性 | 强一致性 |
|------|-----------|---------|
| **一致性保证** | 无新更新时最终一致 | 任何时刻都一致 |
| **可用性** | 高 | 低（可能阻塞） |
| **实现复杂度** | 较低（异步 + 补偿） | 高（2PC/Paxos/Raft） |
| **适用场景** | 电商、社交、内容平台 | 银行核心账务、金融交易 |
| **用户体验** | 短暂不一致可接受 | 绝对一致必须保证 |

### 最终一致性的误区

- ❌ **不是"不一致也行"**：最终一致性要求"**最终**"达到一致，不是永远不一致
- ❌ **不是不需要对账**：没有补偿/修复机制的最终一致性是"放弃治疗"
- ❌ **不是所有场景都适用**：银行转账等场景必须强一致

## 关键关联

- [[互斥与原子性]] - 关联原因：最终一致性是跨越不可控边界后的兜底方案，锁解决互斥、幂等防重、对账修复
- [[分布式锁]] - 关联原因：锁是最终一致性方案的第一层（预防层）
- [[幂等性]] - 关联原因：幂等是最终一致性方案的第二层（防重层）
- [[系统边界分类]] - 关联原因：不可控边界上无法使用 2PC/Saga，最终一致性是唯一可行方案
- [[秒杀超卖与库存一致性]] - 关联原因：秒杀场景接受极低容忍度的超卖，通过最终一致性 + 补偿实现高可用

## 我的误区与疑问

- ❌ 误区：以为最终一致性就是"不一致也行"（实际是"最终必须一致"，需要补偿/对账机制兜底）
- ❓ 疑问：如何评估业务对"最终"的容忍时间？（答：看业务场景——电商订单秒级可接受，银行账务分钟级都不可接受）
