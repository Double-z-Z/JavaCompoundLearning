# 秒杀超卖与库存一致性

## 一句话定义

**超卖容忍度本质上是"你愿意用多少库存精确性换取系统可用性"，是商业契约与技术成本的权衡，而非纯技术问题**

## 核心理解

### 容忍度三层级分类框架

| 层级 | 容忍度指标 | 典型场景 | 商业逻辑 |
|------|-----------|---------|---------|
| **绝对零容忍** | 0（不允许库存为负） | 火车票、机票、限量潮品、iPhone首发 | 库存物理上限刚性约束，超卖=无法履约，法律/品牌风险极高 |
| **极低容忍** | ≤0.01%（万分之一） | 主流电商秒杀（双11、618）、餐饮团购 | 允许极端并发下的统计误差，但需人工/系统兜底赔付 |
| **有限容忍** | 1%~5% | 快消品、预售模式、多仓异步调配 | 供应链可快速补货，或通过协商退款/换货解决，追求吞吐量优先 |

### 为什么技术上无法做到"绝对零超卖"？

```
核心矛盾：CAP 定理下，分区容错（P）与强一致（C）无法兼得

秒杀流量洪峰时：
├─ 要求绝对强一致 → 系统瞬间被打垮 → 全部用户失败
└─ 允许适度妥协 → 系统保持可用 → 极少数超卖可补偿

结论：0.01% 的超卖对业务的伤害 < 系统全部不可用
```

### 技术方案与容忍度匹配

| 技术方案 | 一致性强度 | 性能代价 | 适用容忍度 |
|---------|-----------|---------|-----------|
| 单库悲观锁 | 最强 | QPS极低（<1K） | 零容忍（火车票） |
| **Redis原子扣减（Lua）** | 强 | **10万级QPS** | 极低容忍（主流电商） |
| **Redis预扣减 + 异步落库** | 最终一致 | **10万级QPS** | 极低容忍（主流电商，多SKU场景） |
| 异步消息队列 | 最终一致 | 百万级吞吐 | 有限容忍（快消） |
| 多主库同步 | 冲突可能 | 地理容灾 | 被动容忍 |

### Redis 预扣减 vs 直接数据库扣减

秒杀场景下，数据库行锁是瓶颈：
- **直接数据库**：`UPDATE stock SET count = count - 1` —— 10w 连接争抢 InnoDB 行锁，MySQL TPS 可能只有几千，直接雪崩
- **Redis 预扣减**：`DECR stock:HOT` —— 单线程 Lua，10w 请求排队执行，毫秒级返回成功/失败，数据库只处理最终成交的几千单

**预扣减的核心矛盾**：性能与饥饿（悬挂库存）

```text
预扣减流程：
用户下单 → Redis Lua 原子扣减（预占）→ 生成订单（PENDING）→ 用户支付 → 确认成交
                ↓
          用户超时未支付 → 库存悬空 → 其他用户无法购买
```

**饥饿问题的缓解方案**（无法根除）：

| 方案 | 原理 | 注意点 |
|------|------|--------|
| **TTL 过期标记** | `SET deduct:order_id:sku 1 EX 600` | Redis Key 过期不会自动触发库存回补，需配合定时任务 |
| **延迟队列释放** | RocketMQ Delay / Redis ZSET，超时后发送释放消息 | 秒级释放，最推荐 |
| **主动释放** | 用户取消/超时关单时，显式发送"释放库存"消息到 MQ | 依赖订单服务的状态机推进 |
| **离线对账兜底** | 每日比对 Redis 库存、订单表、预扣日志表 | 终极兜底，发现不一致人工修复 |

## 已验证的认知（实践基础）

### Redis Lua 原子操作 ✅

**已实践场景**：redis-counter-service 的库存扣减

```lua
-- Lua 脚本保证原子性
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock >= tonumber(ARGV[1]) then
    return redis.call('DECRBY', KEYS[1], ARGV[1])
else
    return -1  -- 库存不足
end
```

**关键理解**：
- Lua 脚本在 Redis 中**单线程执行**，天然原子性
- 无需分布式锁，性能远高于数据库悲观锁
- 主流电商（淘宝、京东）采用此方案

### CAP 定理权衡 ✅

**核心洞察**：
- 高并发秒杀场景下，**P（分区容错）和 A（可用性）优先**
- C（强一致性）通过**最终一致性 + 补偿机制**实现
- 不是"做不到准确"，而是"准确的成本过高"

### 多 SKU 跨节点的 Saga 应用 ✅

**已深化认知**：
购物车下单涉及 SKU001(Node1)、SKU002(Node2)、SKU003(Node3)，Redis Cluster 不支持跨节点事务：

```text
Saga 编排式流程：
├─ T1: 扣减 SKU001（Node1）→ 成功，发布事件到 MQ
├─ T2: 扣减 SKU002（Node2）→ 成功，发布事件到 MQ
├─ T3: 扣减 SKU003（Node3）→ 失败（库存不足）
└─ 触发补偿：C2 → C1（逆向释放已扣减库存）
```

**关键设计点**：
- 单 SKU 扣减用 **Lua 原子脚本**（保证单节点原子性）
- 跨 SKU 协调用 **编排式 Saga**（MQ 事件驱动）
- 补偿失败需五层兜底：**重试 → 死信队列 → 告警 → 人工干预 → 离线对账**
- 接受最终一致性：补偿过程中销量报表、监控曲线、用户感知都已留下痕迹

### 幂等性设计 ✅

**已深化认知**：
幂等只防"重复执行"，不防"并发冲突"，秒杀场景必须**幂等键 + Lua 原子脚本**双保险：

```lua
-- KEYS[1]: stock:SKU001, KEYS[2]: idempotent:order_1001:SKU001
if redis.call('EXISTS', KEYS[2]) == 1 then
    return {1, "ALREADY_PROCESSED"}  -- 幂等命中
end
-- 库存检查 + 扣减 + 记录幂等（EX 86400）
```

**幂等键设计**：`idempotent:{order_id}:{sku_id}`，TTL 24h~7d，平衡防重和对账需求。
