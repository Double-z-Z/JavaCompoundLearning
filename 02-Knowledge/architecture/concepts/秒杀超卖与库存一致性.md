# 秒杀超卖与库存一致性

## 一句话定义

**超卖容忍度本质上是"你愿意用多少库存精确性换取系统可用性"，是商业契约与技术成本的权衡，而非纯技术问题**

## 核心理解

### 容忍度三层级分类框架

| 层级 | 容忍度指标 | 典型场景 | 商业逻辑 |
|------|-----------|---------|---------|
| **绝对零容忍** | 0（不允许库存为负） | 火车票、机票、限量潮品、iPhone首发 | 库存物理上限刚性约束，超卖=无法履约，法律/品牌风险极高 |
| **极低容忍** | ≤0.01%（万分之一） | 主流电商秒杀（双11、618）、餐饮团购 | 允许极端并发下的统计误差，但需人工/系统兜底赔付 |
| **有限容忍** | 1%~5% | 快消品、预售模式、多仓异步调配 | 供应链可快速补货，或通过协商退款/换货解决，追求吞吐量优先 |

### 为什么技术上无法做到"绝对零超卖"？

```
核心矛盾：CAP 定理下，分区容错（P）与强一致（C）无法兼得

秒杀流量洪峰时：
├─ 要求绝对强一致 → 系统瞬间被打垮 → 全部用户失败
└─ 允许适度妥协 → 系统保持可用 → 极少数超卖可补偿

结论：0.01% 的超卖对业务的伤害 < 系统全部不可用
```

### 技术方案与容忍度匹配

| 技术方案 | 一致性强度 | 性能代价 | 适用容忍度 |
|---------|-----------|---------|-----------|
| 单库悲观锁 | 最强 | QPS极低（<1K） | 零容忍（火车票） |
| **Redis原子扣减（Lua）** | 强 | **10万级QPS** | 极低容忍（主流电商） |
| 异步消息队列 | 最终一致 | 百万级吞吐 | 有限容忍（快消） |
| 多主库同步 | 冲突可能 | 地理容灾 | 被动容忍 |

## 已验证的认知（实践基础）

### Redis Lua 原子操作 ✅

**已实践场景**：redis-counter-service 的库存扣减

```lua
-- Lua 脚本保证原子性
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock >= tonumber(ARGV[1]) then
    return redis.call('DECRBY', KEYS[1], ARGV[1])
else
    return -1  -- 库存不足
end
```

**关键理解**：
- Lua 脚本在 Redis 中**单线程执行**，天然原子性
- 无需分布式锁，性能远高于数据库悲观锁
- 主流电商（淘宝、京东）采用此方案

### CAP 定理权衡 ✅

**核心洞察**：
- 高并发秒杀场景下，**P（分区容错）和 A（可用性）优先**
- C（强一致性）通过**最终一致性 + 补偿机制**实现
- 不是"做不到准确"，而是"准确的成本过高"
