# 系统边界分类

## 一句话定义
系统边界分类是根据**参与者是否可控、是否支持补偿协议**将分布式系统中的操作对象分为可控边界、半可控边界和不可控边界三类，是选择互斥策略还是原子性策略的首要判断依据。

## 核心理解

### 三类边界

| 边界类型 | 典型参与者 | 是否支持 2PC | 是否支持 Saga 补偿 | 技术选择 |
|---------|-----------|------------|-------------------|---------|
| **可控边界** | MySQL、Redis、MQ、内部数据库 | 可（XA/TCC） | 可（本地回滚/消息补偿） | 本地事务、Saga、最终一致 |
| **半可控边界** | 内部微服务（自有团队维护） | 可设计 TCC 接口 | 可设计补偿接口 | Saga、TCC、分布式锁（可选） |
| **不可控边界** | 支付宝、微信、物流商、短信网关、第三方 API | **不支持** | **补偿不可靠/不可逆** | **分布式锁做预防性互斥** |

### 为什么"跨存储介质"不是本质

**误区**：以为 MySQL + Redis 的"跨介质"需要分布式锁或 Saga。

**事实**：
- MySQL + Redis 都在**可控边界**内
- 可用本地事务（`@Transactional` + JPA 缓存同步）或最终一致性（Binlog + Canal）解决
- **不需要**分布式锁或 Saga

**本质区别**：不是"跨介质"，而是"**跨边界**"——当操作流跨越到**不可控的外部系统**时，才需要特殊处理。

### 不可控边界的特征

| 特征 | 说明 | 例子 |
|------|------|------|
| **无补偿接口** | 不支持退款/撤销/回滚 | 短信发送后无法召回 |
| **补偿不可靠** | 退款可能失败、异步到账、收手续费 | 支付宝退款可能被风控拦截 |
| **补偿不可逆** | 物理操作无法撤销 | 物流包裹一旦揽收无法"补偿"回未下单状态 |
| **无 XA 支持** | 不支持 prepare/commit 协议 | 外部 API 不可能为你实现两阶段提交 |

### 边界判断的决策影响

```
操作是否跨越不可控边界？
├─ 是 → 分布式锁做预防性互斥（Saga/2PC 失效）
└─ 否 → 进入下一层判断（是否需要原子性？）
```

## 关键关联

- [[互斥与原子性]] - 关联原因：系统边界分类是选择互斥策略还是原子性策略的首要判断依据
- [[分布式锁]] - 关联原因：不可控边界是分布式锁三个不可替代场景之首
- [[Saga模式]] - 关联原因：Saga 的前提是"所有操作可补偿"，在不可控边界上这个前提不成立
- [[最终一致性]] - 关联原因：跨越不可控边界后，锁 + 幂等 + 对账构成最终一致性方案

## 我的误区与疑问

- ❌ 误区：以为"跨存储介质"（如 MySQL + Redis）需要分布式锁或 Saga（实际两者都在可控边界内，用本地事务或最终一致即可）
- ❓ 疑问：半可控边界和不可控边界的界限在哪里？（答：看团队是否能控制参与者的接口设计和补偿能力）
