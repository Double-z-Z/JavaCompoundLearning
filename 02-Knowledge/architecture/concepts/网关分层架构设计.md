# 网关分层架构设计

## 一句话定义

**网关分层不是简单的"多一层代理"，而是"横切关注点"与"业务耦合度"的博弈：接入网关负责物理防护，业务网关负责逻辑治理，两者缺一不可但必须严守边界**

## 核心认知（按层次组织）

### ⭐ 第一层：原创洞察 — "Redis前置"的真正含义

**你发现的关键矛盾**：
```
❌ 错误理解："Redis 在网络拓扑上位于所有 Java 应用服务之前"
✅ 正确理解："Redis 的库存判定逻辑前置到原子操作（Lua），而非物理位置前置"
```

**真实流量路径永远是**：
```
用户 → Nginx → 网关 → Java 应用服务 → Redis
```

**两种落地架构**：

| 架构 | 描述 | 适用场景 | 局限性 |
|------|------|---------|--------|
| **A: Nginx 直连 Redis** | OpenResty + lua-resty-redis 直接扣减 | 纯库存扣减单一判定 | 复杂规则（优惠券叠加）搞不定 |
| **B: 极简秒杀服务**（主流） | 网关认证 → 极简Java服务 → Redis Lua | 规则复杂、需事务保证 | 多一跳，但有完整Java生态 |

**结论**：架构B是国内电商主流做法。Redis在**逻辑上**"前置"（先做库存判定），但在**网络上**仍位于Java服务之后。

---

### 🌿 第二层：核心概念 — 接入网关 vs 业务网关

#### 职责分离（重要且受用）

```
┌─────────────────────────────────────────────────────┐
│  用户流量                                           │
│    ↓                                                │
│  ┌───────────────────┐                              │
│  │   接入网关         │ ← "网络保安"                 │
│  │  (Nginx/OpenResty)│                              │
│  │  • SSL 卸载        │                              │
│  │  • DDoS 防护       │                              │
│  │  • CC 防刷         │                              │
│  │  • IP 黑白名单     │                              │
│  │  • 域名级限流      │                              │
│  └────────┬──────────┘                              │
│           ↓                                        │
│  ┌───────────────────┐                              │
│  │   业务网关         │ ← "业务前台"                 │
│  │  (Spring Cloud     │                              │
│  │   Gateway)        │                              │
│  │  • JWT 认证鉴权    │                              │
│  │  • 路由转发        │                              │
│  │  • API 级限流      │                              │
│  │  • 熔断降级        │                              │
│  │  • 灰度发布        │                              │
│  └────────┬──────────┘                              │
│           ↓                                        │
│  ┌───────────────────┐                              │
│  │   业务服务集群     │                              │
│  └───────────────────┘                              │
└─────────────────────────────────────────────────────┘
```

#### 为什么必须拆两层？

| 如果只保留接入网关 | 问题 |
|-------------------|------|
| Nginx 上做 JWT 校验 | 配置臃肿，难以对接 OAuth2 授权服务器 |
| Nginx 上路由到具体服务 | 服务拓扑变化频繁，reload 成本高 |
| Nginx 上做熔断 | 缺乏健康检查机制，无法联动注册中心 |

| 如果只保留业务网关 | 问题 |
|-------------------|------|
| 直接暴露给公网 | SSL/DDoS 防护能力差一个量级 |
| 单点扛所有流量 | 静态资源/恶意流量把网关打满 |

**本质**：**接入网关负责"把坏人挡在门外"，业务网关负责"把没票的人挡在业务层外"**

### 📚 第三层：深入理解 — 认证与会话处理

**关键原则**：认证/会话必须在 **网关层完成**，不能依赖下游 Tomcat Session

| 层级 | 认证方式 | 说明 |
|------|---------|------|
| **接入网关层** | SSL 证书校验、Basic Auth（简单场景） | 仅做基础身份验证 |
| **业务网关层** | JWT Token 解析 + 权限 Scope 校验 | 解析用户身份，注入 Header |
| **业务服务层** | 直接使用已解析的用户信息 | 不再做重复认证 |

**实践建议**：
- 使用 **JWT + Redis 缓存公钥**（避免 RSA 非对称验签的 CPU 消耗）
- 业务网关将用户信息注入请求头，下游服务直接读取

### ✅ 第四层：实践原则 — 网关的成本与收益

#### 成本（多一级网关不是免费的）

| 成本项 | 具体表现 | 量化影响 |
|--------|---------|---------|
| **网络 RTT** | 多一跳延迟 | 增加 1~5ms（内网） |
| **故障面扩大** | 网关挂 = 所有下游不可达 | 需要高可用 + 兜底降级 |
| **资源消耗** | JWT验签、JSON解析、规则匹配 | 占总基础设施成本 10~20% |
| **调试复杂度** | 问题排查多一层 | 链路追踪必须穿透网关 |

#### 收益（为什么大多数电商保留它）

| 收益项 | 不可替代性 |
|--------|-----------|
| **统一认证收口** | 每个服务各自做鉴权 = 安全灾难 |
| **流量治理** | 按 API 维度限流（Nginx 不懂 API 语义） |
| **协议转换** | HTTP → gRPC、WebSocket 管理 |
| **灰度与蓝绿** | 按用户标签路由（VIP 走新版本） |
| **熔断降级** | 秒杀服务超时？网关返回 Mock 数据 |

**取舍公式**：
```
保留网关 = 统一鉴权 + 流量治理 + 灰度能力 + 熔断保护
        - (1次跳转 + 单点风险 + 10~20% 成本)
        
当系统有 >3 个微服务 + 需要统一鉴权 + 存在秒杀类流量不均时 → 收益 > 成本
```

### 🔶 第五层：待实践 — 防止网关膨胀的铁律

#### 问题：Gateway Fatigue（网关膨胀病）

```
初始：网关只做路由 + 鉴权
  ↓
半年后：加了限流、熔断、日志、灰度
  ↓
一年后：加了参数校验、数据脱敏、请求改写、缓存、计费
  ↓
两年后：网关代码量超过业务服务，发布 = 全站高危变更
```

#### 防守策略（待实践验证）

**策略1："三做三不做"边界**

| 类别 | 职责 | 示例 |
|------|------|------|
| ✅ **网关做** | 横切关注点（与具体业务无关） | 鉴权、路由、限流、熔断、日志、CORS |
| ❌ **网关不做** | 业务逻辑 | 库存查询、价格计算、优惠券规则 |
| ❌ **网关不做** | 有状态操作 | Session 存储、业务缓存 |
| ❌ **网关不做** | 重计算 | 图片处理、大数据量 JSON 聚合 |

**判断标准**：如果逻辑变更需要了解某个 SKU 的具体业务规则 → 不该在网关

**策略2：配置化优于代码化**
```yaml
# 反模式：硬编码业务判断 ❌
if (skuId == 1001 && userType == "VIP") { ... }

# 正模式：规则外置 ✅
filters:
  - name: RequestRateLimiter
    args:
      redis-rate-limiter.replenishRate: 1000
  - name: CircuitBreaker
    args:
      name: seckillService
      fallbackUri: forward:/fallback/seckill
```

**策略3：BFF 拆分（Backend for Frontend）**
```
接入网关（通用）
  ├── 移动 BFF → 移动端服务集群
  ├── PC BFF   → PC 端服务集群
  └── Admin BFF→ 运营后台
```
- 通用网关只保留鉴权、路由、全局熔断
- BFF 层处理各端的接口聚合、协议适配
- 业务逻辑继续下沉到领域服务

**策略4：无状态化**
- 配置外置（Nacos/Consul）
- 缓存外置（Redis，不用 Caffeine 本地缓存）
- 日志外置（Kafka）
- 目标：随时可扩缩容、替换、发布
