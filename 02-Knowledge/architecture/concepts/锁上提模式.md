# 锁上提模式

## 一句话定义
锁上提是将分散在调用链各层的分布式锁**收敛到唯一入口**，通过拆分"带锁的 Facade 方法"和"无锁的 Core 方法"来消除可重入需求的架构模式。

## 核心理解

### 问题：可重入锁掩盖设计问题

当同一线程在同一次调用链中多次进入同一锁，通常意味着：
1. **锁的职责没有内聚到单一入口**
2. **服务层方法既被外部直接调用（需锁），又被内部组合调用（不应锁）**

可重入锁会**掩盖**这个问题，让不合理的锁粒度继续存在。

### 锁上提的重构示例

**重构前（AOP 嵌套导致可重入需求）**：
```java
@AntiResubmit(key = "'order:' + #orderId")  // 外层锁
public void submitOrder(Long orderId) {
    orderService.create(orderId);  // 内部又带 @StockLock
}
```

**重构后（锁上提，内部无锁）**：
```java
@Transactional
@DistributedLock(key = "'order:' + #orderId")  // 唯一锁点
public void submitOrder(Long orderId) {
    validate(orderId);      // 无锁
    deductStock(orderId);   // 无锁（内部方法，信任外层契约）
    saveOrder(orderId);     // 无锁
}
```

---

### 分层锁契约

建立显式的锁契约体系，让可重入成为"应急工具"而非默认行为：

#### 1. 锁类型显式化

```java
public interface DistributedLock {
    // 不可重入，最简实现，默认使用
    boolean tryLock(String key, long waitMs, long leaseMs);
    void unlock(String key);
}

public interface ReentrantDistributedLock extends DistributedLock {
    // 可重入，需显式声明使用
    boolean tryReentrantLock(String key, long waitMs, long leaseMs);
    void reentrantUnlock(String key);
}
```

#### 2. 服务层锁契约

```java
@Service
public class OrderService {
    
    // === Facade 层：对外暴露，带锁 ===
    @DistributedLock(key = "'order:' + #orderId")
    public void placeOrder(Long orderId) {
        doPlaceOrder(orderId);  // 委托给无锁核心方法
    }
    
    // === Core 层：内部组合使用，无锁 ===
    // 命名约定：doXxx / internalXxx 表示"调用方已保证同步"
    void doPlaceOrder(Long orderId) {
        validate(orderId);
        deductStock(orderId);
        saveOrder(orderId);
    }
    
    // === 独立操作：可能被单独调用，自带锁 ===
    @DistributedLock(key = "'stock:' + #skuId")
    public void deductStock(Long skuId) {
        // ...
    }
}
```

**规则**：
- `public` 方法若可能被外部直接调用，可带锁
- `package-private` 或 `doXxx` 方法仅供内部组合，不带锁
- **禁止跨服务带锁调用**（Service A 带锁调用 Service B 的带锁方法）

---

### 当锁上提不可行时

如果框架层（如全局幂等拦截器）和业务层锁确实冲突，优先使用 **LockHint 模式**：

```java
// 拦截器只标记"需要锁"，不实际加锁
@Interceptor
@LockHint(key = "'submit:' + #userId")  // 仅声明，不执行
public void antiResubmit(InvocationContext ctx) {
    ctx.proceed();
}

// 业务层根据 LockHint 动态决定 key
@DistributedLock(key = "resolveLockKey(#context)")
public void businessMethod() {
    // 统一在这里加锁，避免嵌套
}
```

如果锁上提确实不可行（如第三方框架无法修改），再**显式降级**到可重入锁：
```java
// 仅在明确出现嵌套的场景启用 ReentrantLock
@ReentrantDistributedLock(key = "'order:' + #orderId")
public void legacyMethod() {
    // 遗留代码，调用链复杂，暂时无法重构
}
```

## 决策树

```
遇到可重入需求？
│
├─ 是否同一线程递归调用同一聚合根？
│   ├─ 是 → 能否改为"外层锁 + 内部无锁递归"？
│   │       ├─ 能 → 锁上提 ✅
│   │       └─ 不能（递归深度不确定/跨 JVM 边界）→ 可重入锁
│   └─ 否 → 继续
│
├─ 是否 AOP/拦截器与业务锁嵌套？
│   ├─ 是 → 能否将 AOP 锁改为"声明式 Hint"由业务层统一获取？
│   │       ├─ 能 → 锁上提 ✅
│   │       └─ 不能（第三方框架）→ 可重入锁（显式启用）
│   └─ 否 → 继续
│
├─ 是否 Saga/事件驱动导致循环进入？
│   ├─ 是 → 能否改为"状态机驱动"消除同步锁依赖？
│   │       ├─ 能 → 锁上提 ✅
│   │       └─ 不能 → 可重入锁
│   └─ 否 → 继续
│
└─ 是否读写锁升级？
    └─ 是 → 可重入锁（Redisson RReadWriteLock）
```

## 最终建议

| 场景 | 推荐策略 | 理由 |
|------|---------|------|
| **新建业务系统** | 锁上提 + 不可重入锁 | 运行成本低，锁边界清晰，强迫设计合理的 Facade/Core 分层 |
| **遗留系统改造** | 先锁上提，后显式可重入 | 逐步消除嵌套，仅在无法重构的边界保留可重入 |
| **基础设施/框架** | 默认可重入（如 Redisson） | 无法预知调用拓扑，必须提供最大兼容性 |
| **高频短持锁**（缓存、配额） | 绝对不可重入 | 避免 Redisson Hash 结构的纯 overhead |

> **核心原则**：Redisson 的默认可重入是框架的"防御性编程"，不是你的业务代码应该模仿的模式。你的 `ReentrantRedisLock` 应当作为**应急工具**放在工具箱里，而不是默认装备。

## 我的误区与疑问

- ❌ 误区：以为为"可能遇到的可重入需求"预置可重入结构是防御性编程（实际是过度设计）
- ✅ 洞察：锁上提迫使你面对"锁粒度不合理"的设计问题，拆分出清晰的 Facade/Core 边界
