# 防退化红线

## 一句话定义
**DDD 架构会自然退化**——必须守住两条红线：(1) Domain 接口只有业务语义；(2) Infra 实现只翻译、不决策。

## 核心理解

### 常见退化路径

#### 路径 1：Domain 接口混入技术词汇
```java
// ❌ 退化：接口变成技术需求汇总表
public interface ExperimentRepository {
    Experiment saveAndFlush(Experiment exp);              // "Flush" 是 JPA 词汇
    Experiment findByIdWithLock(ExperimentId id);         // "Lock" 是数据库概念
    void batchInsert(List<Experiment> experiments);       // "Batch" 是性能优化需求
}
```

#### 路径 2：所有逻辑以"实现类"名义堆在 Infra
```java
// ❌ 退化：Domain 变成空壳，Infra 承担业务逻辑
@Repository
public class ExperimentRepositoryImpl {
    
    public ExperimentDTO findDetailForDisplay(ExperimentId id) {
        // 业务逻辑（应该在 Domain 或 AppService）
        Experiment exp = jpa.findById(id);
        if (exp.getStatus() == RUNNING) {
            exp.setCanEdit(false);  // 在 Repository 里做业务判断！
        }
        return convertToDTO(exp);
    }
}
```

### 两条红线

| 红线 | 规则 | 检查方法 |
|------|------|---------|
| **红线 1** | Domain 接口只有业务语义，无技术词汇 | 搜索 `flush`, `batch`, `lock`, `native`, `query` |
| **红线 2** | Infra 实现只翻译、不决策 | 搜索 Repository/AppService 里的 `if/else` 业务判断 |

### 终极检查法

**🔄 换技术测试**：
> 如果把底层技术从 JPA 换成 MyBatis，或从 Docker 换成 K8s，**Domain 层的任何文件都不应该需要修改**。
>
> 如果需要改，说明技术细节泄漏了。

**具体检查项**：
- [ ] Domain 接口的方法名是否包含 `save`, `find`, `delete` 以外的技术词？
- [ ] Domain 接口的参数类型是否使用了框架类（Pageable, Specification）？
- [ ] Domain 层是否 import 了 `org.springframework.*`, `javax.persistence.*`？
- [ ] Repository 实现类是否包含业务逻辑（状态判断、权限检查）？
- [ ] 是否存在 `@OneToOne` / `@ManyToOne` 跨聚合引用？

### 自动化防护工具

**ArchUnit 测试**（推荐集成到 CI）：

```java
@Test
void domain_layer_should_not_depend_on_infrastructure() {
    noClasses()
        .that().resideInAPackage("..domain..")
        .should().dependOnClassesThat()
        .resideInAPackage("..infrastructure..")
        .check(myClasses());
}

@Test
void domain_interfaces_should_not_contain_technical_terms() {
    classes().that().resideInAPackage("..domain..")
        .and().areInterfaces()
        .should(new ArchCondition<>("only have business semantic methods") {
            @Override
            public void check(JavaClass item, ConditionEvents events) {
                for (JavaMethod method : item.getMethods()) {
                    String name = method.getName().toLowerCase();
                    if (name.contains("flush") || name.contains("lock") || 
                        name.contains("batch") || name.contains("native")) {
                        events.add(SimpleConditionEvent.violated(
                            method, 
                            "Method '" + name + "' contains technical term"
                        ));
                    }
                }
            }
        }).check(domainInterfaces);
}
```

## 我的误区与疑问

- ❌ 误区：以为"先快速实现，后面再重构"（实际上后面永远不会重构）
- ❌ 误区：以为 ArchUnit 测试太麻烦不值得写
- ❓ 疑问：如何在团队层面强制执行这两条红线？（Code Review + CI 卡点）

## 代码与实践

```java
// ❌ 退化的 Domain 层
public interface ExperimentRepository extends JpaRepository<Experiment, Long> {
    // 继承 JpaRepository 本身就是技术耦合！
    
    @Query("SELECT e FROM Experiment e WHERE e.status = :status")  // JPQL 泄漏
    List<Experiment> findByStatusWithLock(@Param("status") ExperimentStatus status);
}

// ✅ 纯洁的 Domain 层
public interface ExperimentRepository {
    Experiment save(Experiment experiment);
    Optional<Experiment> findById(ExperimentId id);
    List<Experiment> findByStatus(ExperimentStatus status);
    void delete(ExperimentId id);
}
```

## 深入思考
💡 如果现在对你的项目执行"换技术测试"（比如从 JPA → MyBatis），你需要修改多少个 Domain 层文件？这个数字反映了你的架构退化程度。
