# 领域接口纯洁性

## 一句话定义
**Domain 层接口只能有业务语义，不能包含任何技术词汇**——Infrastructure 实现类负责将技术细节翻译为领域契约。

## 核心理解

### ❌ 违规案例：技术大杂烩接口

```java
// 原始设计（来自你的复盘笔记第八章）
public interface InfrastructureProvider {
    // 合理：环境生命周期
    Mono<Environment> provision(EnvironmentSpec spec);
    Mono<Void> teardown(EnvironmentId id);
    
    // ❌ 违规：聚合根内部实体不应直接暴露
    Mono<ServiceInstance> startContainer(ServiceInstanceId id);
    Mono<Void> stopContainer(ServiceInstanceId id);
    
    // ❌ 违规：纯技术工具，不是领域行为
    Flux<String> streamLogs(ServiceInstanceId id);
    
    // ❌ 违规：与领域无关的技术操作
    Mono<String> executeCommand(String command);
    
    // ❌ 违规：应该是 provision 内部实现细节
    Mono<Boolean> waitForHealthy(EnvironmentId id);
}
```

**问题**：
1. 接口变成了"技术需求汇总表"
2. Domain 层可以感知 Docker、SSH、日志等技术细节
3. 换技术实现时需要改 Domain 接口（违反依赖倒置）

### ✅ 正确做法：只保留业务语义

```java
public interface EnvironmentProvisioner {
    // 只保留环境生命周期的业务语义
    Mono<Environment> provision(EnvironmentSpec spec);      // 创建环境
    Mono<Void> teardown(EnvironmentId id);                  // 销毁环境
    Mono<EnvironmentStatus> checkStatus(EnvironmentId id);  // 检查状态
}
```

**技术细节锁死在实现类**：

```java
@Component
public class DockerComposeProvisioner implements EnvironmentProvisioner {
    
    @Override
    public Mono<Environment> provision(EnvironmentSpec spec) {
        return dockerComposeUp(spec)           // 技术细节
            .flatMap(this::waitForHealthy)     // 健康轮询（私有方法）
            .map(this::extractServices);       // 提取容器信息（私有方法）
    }
    
    private Mono<Void> waitForHealthy(EnvironmentId id) {
        // 健康轮询是实现细节，不暴露在接口中
    }
    
    private Flux<String> streamLogsInternal(ServiceInstanceId id) {
        // 日志采集是实现细节，不暴露在接口中
    }
}
```

### 检查法则

**如果把底层技术从 JPA 换成 MyBatis，或从 Docker 换成 K8s，Domain 层的任何文件都不应该需要修改。如果需要改，说明技术细节泄漏了。**

**常见泄漏信号**：
- 接口方法名包含技术词汇：`saveAndFlush()`, `findByIdWithLock()`, `executeNativeQuery()`
- 参数类型是框架类：`@Param`, `Pageable`, `Specification`
- 异常类型是技术异常：`DataAccessException`, `JpaSystemException`

## 关键关联

- [[DDD分层架构]] - 关联原因：Domain 层位于核心位置，必须保持纯洁性才能保证架构稳定
- [[Infrastructure分包原则]] - 关联原因：按领域分包有助于隔离技术细节
- [[异常分层设计]] - 关联原因：接口纯洁性要求异常也必须是领域异常，不能是技术异常

## 我的误区与疑问

- ❌ 误区：以为接口多提供一些方法更"灵活"
- ❌ 误区：以为 `Pageable`、`Specification` 是 Spring Data 的标准用法，不算技术泄漏
- ❓ 疑问：如何处理确实需要跨技术的能力（如分页、排序）？

## 代码与实践

```java
// ❌ 技术泄漏
public interface ExperimentRepository extends JpaRepository<Experiment, Long> {
    Page<Experiment> findByStatus(ExperimentStatus status, Pageable pageable);
}

// ✅ 保持纯洁
public interface ExperimentRepository {
    Experiment save(Experiment experiment);
    Optional<Experiment> findById(ExperimentId id);
    List<Experiment> findByStatus(ExperimentStatus status);  // 无 Pageable
    
    // 分页参数封装为领域对象
    PagedResult<Experiment> query(ExperimentQuery query);
}

public class ExperimentQuery {
    private ExperimentStatus status;
    private int page;
    private int size;
    // getter/setter
}

public class PagedResult<T> {
    private List<T> content;
    private long totalElements;
    private int totalPages;
}
```
