# JVM 预热效应

## 一句话定义

JVM 从启动到达到最佳性能需要经过类加载、解释执行、C1/C2 编译、连接池初始化等阶段，首次压测数据往往比稳定态低 30%-50%。

## 核心理解

### 预热阶段模型

```
启动 → 解释执行 → C1编译 → C2编译 → 稳定态
 0s    1-10s      10-30s   30-60s    60s+
 │       │          │        │        │
 └── 慢 ──┘────────┘────────┘── 快 ──┘
```

### 影响压测的关键阶段

| 阶段 | 耗时 | 对 QPS 的影响 | 如何加速 |
|------|------|--------------|----------|
| 类加载 | 1-5s | 轻微 | 预加载关键类 |
| 解释执行 | 5-15s | **显著降低** | 跳过，直接触发编译 |
| C1 编译 | 10-30s | 中等降低 | 提高编译阈值 |
| C2 编译 | 30-60s | **大幅提升** | 充分预热后再测试 |
| 连接池初始化 | 5-20s | 中等降低 | 预创建连接 |

### 实战案例：redis-counter-service

```
首次测试:  26,753 QPS（未预热）
预热 10s:  37,965 QPS（+42%）
预热 30s:  38,841 QPS（+45%，稳定）
```

**结论**：未预热的数据不可信，必须预热到稳定态再记录。

## 常见误区

| 误区 | 正确理解 |
|------|----------|
| "启动后马上压测" | 需要预热 30-60s 或数万次请求 |
| "预热一次就够了" | JVM 可能去优化（deoptimize），需要持续观察 |
| "开发环境预热数据可以直接用" | 生产环境硬件不同，需要重新预热 |

## 最佳实践

```java
// 压测前强制预热
public static void warmup(Runnable task, int iterations) {
    for (int i = 0; i < iterations; i++) {
        task.run();
    }
    System.gc(); // 可选：触发 GC 减少干扰
    Thread.sleep(1000); // 等待 GC 完成
}
```
