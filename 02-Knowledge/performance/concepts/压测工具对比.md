# 压测工具对比与选择

## 一句话定义

不同压测工具在自身性能、协议支持、场景适配上有显著差异，工具选择不当会导致压测结果失真或无法定位真实瓶颈。

## 核心理解

### 工具特性矩阵

| 特性       | bombardier | wrk          | JMeter  | Jedis 直连 |
| -------- | ---------- | ------------ | ------- | -------- |
| 自身性能     | ⭐⭐⭐⭐⭐      | ⭐⭐⭐⭐⭐        | ⭐⭐⭐     | ⭐⭐⭐⭐⭐    |
| 资源占用     | 极低 (10MB)  | 低            | 高 (JVM) | 低        |
| HTTP/1.1 | ✅          | ✅            | ✅       | ❌        |
| HTTP/2   | ✅          | ❌            | ✅       | ❌        |
| POST 支持  | ✅          | ✅ (Lua)      | ✅       | N/A      |
| 自定义脚本    | ❌          | ✅ (Lua)      | ✅ (GUI) | Java     |
| 报告丰富度    | 中等         | 低            | ⭐⭐⭐⭐⭐   | 自定义      |
| 跨平台      | ✅          | ❌ (无Windows) | ✅       | ✅        |

### 适用场景

| 场景 | 推荐工具 | 原因 |
|------|----------|------|
| 快速 HTTP 基线测试 | bombardier / wrk | 单文件、秒级启动、自身不成为瓶颈 |
| 复杂业务流压测 | JMeter | 支持 cookies、headers、断言、报告 |
| 绕过 HTTP 测 Redis | Jedis 直连 | 排除协议层干扰，测真实客户端性能 |
| 长期稳定性测试 | JMeter | 可持续运行数小时，监控资源占用 |

### 实战教训：redis-counter-service

```
JMeter 结果:    33,622 QPS（未预热，工具自身较重）
bombardier 结果: 38,841 QPS（预热后，更轻量的客户端）
差距: 15% — 工具选择直接影响结果上限
```

**关键发现**：当服务端性能接近客户端上限时，工具自身性能会成为瓶颈。

## 常见误区

| 误区 | 正确理解 |
|------|----------|
| "JMeter 是行业标准，一定最准" | JMeter GUI 模式自身消耗大，非 GUI 模式也需调优 |
| "wrk 最快，所以最好用" | wrk 不支持 Windows，且 Lua 脚本学习成本高 |
| "一个工具测所有场景" | 应该组合使用：bombardier 快速验证 + JMeter 复杂场景 |

## 最佳实践

```bash
# 1. 快速验证（bombardier）
bombardier -c 100 -d 10s http://localhost:8080/api

# 2. 复杂场景（JMeter 非 GUI 模式）
jmeter -n -t scenario.jmx -l result.jtl -e -o report/

# 3. 绕过 HTTP（Jedis 直连）
java -cp ... RedisDirectBenchmark

# 4. 对比分析
# 如果 bombardier > JMeter 15%+，说明 JMeter 可能是瓶颈
```
