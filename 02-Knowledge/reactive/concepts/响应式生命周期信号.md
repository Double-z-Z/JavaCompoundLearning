# 响应式生命周期信号

## 一句话定义

响应式流通过**信号（Signals）**与订阅者通信，理解生命周期是正确使用 `doOn*` 操作符的前提。

## 核心理解

### Reactive Streams 规范定义的4个信号

```java
interface Subscriber<T> {
    void onSubscribe(Subscription s);   // ① 订阅建立
    void onNext(T t);                   // ② 数据发射（0~N次）
    void onError(Throwable t);          // ③ 终止：异常
    void onComplete();                  // ④ 终止：成功
}
```

### 完整的生命周期状态流转

```
Publisher 的状态流转：

   ┌─────────┐    onSubscribe     ┌──────────┐
   │  创建    │ ──────────────▶  │  订阅中   │
   └─────────┘                   └──────────┘
                                      │
                    ┌─────────────────┼─────────────────┐
                    ▼                 ▼                 ▼
              ┌──────────┐      ┌──────────┐      ┌──────────┐
              │  发射数据  │      │  出错了   │      │  正常完成  │
              │ (onNext)  │      │ (onError) │              │
              └──────────┘      └──────────┘      └──────────┘
                    │                 │                 │
                    ▼                 ▼                 ▼
              (可多次调用)       (终止)            (终止)
              
                                   ┌──────┴──────┐
                                   ▼             ▼
                              ┌──────────┐  ┌──────────┐
                              │ Cancel   │  │ (正常结束)│
                              │ 下游取消  │  │ 但无值    │
                              └──────────┘  └──────────┘
```

**关键洞察**：
- 规范只定义了4个信号：`onSubscribe`、`onNext`、`onError`、`onComplete`
- Reactor 扩展了第5种终止信号：**Cancel**（下游主动取消订阅）

### WebFlux 中的四阶段生命周期

在 Spring WebFlux 中，一次 HTTP 请求的处理将 Reactive Streams 信号嵌入到更宏观的四个阶段中：

| 阶段 | 发生时机 | 所在线程 | 关键类 | 信号关联 |
|------|---------|---------|--------|---------|
| **Assembly** | Controller 方法执行期间 | Worker EventLoop | `MonoMap`, `MonoFlatMap`, `MonoCreate` | 无信号，仅创建对象 |
| **Subscription** | 框架组装响应流水线时 | Worker EventLoop | `HttpWebHandlerAdapter`, `DispatcherHandler`, `ResponseBodyResultHandler` | 隐式调用 `subscribe()` |
| **onSubscribe** | `subscribe()` 后从尾到头遍历 | Worker EventLoop | `MonoFlatMap`, `MonoMap`, `DefaultMonoSink` | `onSubscribe(Subscription)` + `request(n)` |
| **Emission** | 最上游数据源产生数据 | EventLoop 或 Scheduler Worker | `DefaultMonoSink`, `FluxReceive`, `MonoSendMany` | `onNext` / `onComplete` / `onError` |

**关键洞察**：
- **Assembly ≠ 执行**：`map()`, `flatMap()`, `filter()` 只是 `new MonoMap<>(上游, 函数)`，零数据流动
- **订阅是隐式的**：WebFlux 框架在 `HttpServerOperations` 层隐式订阅 Controller 返回的 `Mono<Void>`，不是用户代码调用 `.subscribe()`
- **`DefaultMonoSink` 双重身份**：既是 `Subscription`（供下游 request/cancel），也是信号发射器（`sink.success()`）

## doOn* 操作符全家桶

| 操作符 | 监听信号 | 触发时机 | 触发次数 | 适用场景 |
|--------|---------|---------|---------|---------|
| **`doOnSubscribe`** | `onSubscribe` | 订阅时 | 1次 | 打印请求开始、记录 traceId |
| **`doOnNext`** | `onNext` | 每次发射元素 | N次(Flux)/0-1次(Mono) | **日志、监控、副作用** |
| **`doOnSuccess`** | `onComplete` | 成功完成 | 1次(Mono专用) | ✅ **Mono<Void) 场景！** |
| **`doOnComplete`** | `onComplete` | 正常结束 | 1次 | 资源清理、最终日志 |
| **`doOnError`** | `onError` | 异常发生 | 0-1次 | 错误日志、告警 |
| **`doOnTerminate`** | `onComplete` 或 `onError` | 终止（无论成功/失败） | 1次 | 必须执行的清理 |
| **`doFinally`** | `onComplete` 或 `onError` 或 `cancel` | 最终（无论取消/成功/失败） | 1次 | 连接关闭、资源释放 |
| **`doOnCancel`** | `cancel` | 取消订阅 | 0-1次 | 长连接中断处理 |

## 关键陷阱：Mono<Void) 的特殊性

### 问题场景

```java
// compensate() 返回 Mono<Void>
return compensate(successMap.get())
    .doOnNext(v -> log.info("Compensation completed..."))  // ❌ 永远不触发！
    .thenReturn(OrderResult.failure("..."));
```

### 原因分析

**Mono<Void) 的信号序列**：

```java
// 普通 Mono<String>:
onSubscribe → onNext("Hello") → onComplete
                   ↑
             doOnNext ✅ 触发

// Mono<Void>:
onSubscribe → （无 onNext）→ onComplete
                                  ↑
                            doOnNext ❌ 不触发！
                            doOnSuccess ✅ 触发！
```

### 正确写法

```java
// 方案1：使用 doOnSuccess（Mono专用）
return compensate(successMap.get())
    .doOnSuccess(v -> log.info("Compensation completed..."))
    .thenReturn(OrderResult.failure("..."));

// 方案2：使用 doOnTerminate（无论成功失败都执行）
return compensate(successMap.get())
    .doOnTerminate(() -> log.info("Compensation finished..."))
    .thenReturn(OrderResult.failure("..."));

// 方案3：使用 doFinally（包括取消场景）
return compensate(successMap.get())
    .doFinally(signal -> log.info("Compensation finally: {}", signal))
    .thenReturn(OrderResult.failure("..."));
```

### redis-counter-service-webflux 案例

#### 案例1：补偿完成日志（❌ 错误 → ✅ 正确）

```java
// 第82行原始代码（有问题）
return compensate(successMap.get())
    .doOnNext(v -> log.info("Compensation completed for {} items", successMap.get().size()))
    .thenReturn(OrderResult.failure("Partial failure, compensated", successMap.get()));

// 应该改为
return compensate(successMap.get())
    .doOnSuccess(v -> log.info("Compensation completed for {} items", successMap.get().size()))
    .thenReturn(OrderResult.failure("Partial failure, compensated", successMap.get()));
```

#### 案例2：Redis increment 后的日志（✅ 正确）

```java
// 第105-107行
return redisTemplate.opsForValue()
        .increment(key, decrementedQty)
        .doOnNext(newVal -> log.info("Compensated: {} +{} = {}", sku, decrementedQty, newVal));
```

## 选择指南

### 根据需求选择操作符

```
需要做什么？                          用哪个？
─────────────────────────────────────────────────
每次收到数据时打日志                  doOnNext
成功完成后做清理                      doOnSuccess / doOnComplete
无论成功失败都要执行                  doOnTerminate
包括取消也要执行（如关闭连接）         doFinally
处理取消事件（如长连接中断）           doOnCancel
记录错误信息                         doOnError
记录订阅开始（如 traceId）            doOnSubscribe
```

### Mono vs Flux 的信号差异对比

```
Flux<String>:
  onSubscribe → onNext("A") → onNext("B") → onComplete
                     ↑              ↑           ↑
                doOnNext×2     doOnNext×2   doOnComplete×1

Mono<String>:
  onSubscribe → onNext("Hello") → onComplete
                     ↑                  ↑
               doOnNext×1        doOnSuccess×1 / doOnComplete×1

Mono<Void>:
  onSubscribe → （无onNext）→ onComplete
                                  ↑
                            doOnSuccess×1 ✅
                            doOnNext×0 ❌
```

## 常见误区

| 误区 | 正确理解 |
|------|----------|
| "doOnNext 和 doOnSuccess 功能一样" | doOnNext 需要 onNext 信号；doOnSuccess 监听 onComplete |
| "Mono<Void) 会发出 onNext(null)" | ❌ Mono<Void) 不发出任何 onNext，直接 onComplete |
| "doOnTerminate 能捕获 cancel" | ❌ 只能捕获 onComplete 和 onError，不包括 cancel |
| "doFinally 和 doOnTerminate 一样" | doFinally 额外包含 cancel 信号 |
| "所有 doOn 操作符都能改变流的内容" | ❌ 所有 doOn* 都是副作用操作符，不改变流的内容 |

## 最佳实践

### 日志记录的最佳实践

```java
// ✅ 推荐：根据返回类型选择合适的操作符
public Mono<OrderResult> placeOrder(MultiSkuOrderRequest request) {
    return processOrder(request)
        .doOnSubscribe(sub -> log.debug("订单处理开始: {}", request))  // 开始
        .doOnNext(result -> log.debug("中间结果: {}", result))          // 中间步骤
        .doOnSuccess(result -> log.info("订单成功: {}", result))        // 成功
        .doOnError(e -> log.error("订单失败", e))                       // 失败
        .doFinally(signal -> log.debug("订单处理结束, signal={}", signal)); // 最终
}

// ❌ 避免：在 Mono<Void) 上使用 doOnNext
public Mono<Void> compensate(Map<String, Long> decremented) {
    return processCompensation(decremented)
        .doOnNext(v -> log.info("补偿完成"));  // 永远不打印！
}
```

### 资源清理的最佳实践

```java
// ✅ 使用 doFinally 确保资源释放（包括取消场景）
public Flux<StockInfo> streamStockUpdates() {
    return connectionFactory.create()
        .flatMapMany(connection -> 
            connection.subscribe(channel)
                .doFinally(signal -> {
                    if (signal == SignalType.CANCEL) {
                        connection.close();  // 取消时也关闭连接
                    }
                })
        );
}
```
