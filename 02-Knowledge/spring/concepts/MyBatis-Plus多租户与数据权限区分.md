# MyBatis-Plus多租户与数据权限区分

> 一句话：多租户是**租户间完全隔离**，数据权限是**同一份数据分级可见**；两者正交，不可混用。`TenantLineInnerInterceptor` 是 SaaS 场景的单字段等值过滤插件，不适合模拟数据权限。

## 一、核心区别：隔离 vs 可见性

| 维度 | 多租户（Multi-Tenancy） | 数据权限（Data Permission） |
|------|------------------------|---------------------------|
| **核心目标** | **租户间完全隔离** | **同一份数据分级可见** |
| **数据归属** | 数据天然属于某个租户，租户是数据的"所有者" | 数据属于组织/系统，用户只有"访问权" |
| **用户认知** | 用户通常**不知道其他租户存在** | 用户知道数据存在，但**被授权后才能看到** |
| **权限粒度** | 粗粒度：整租户隔离 | 细粒度：行级、列级、部门级、项目级 |
| **变化频率** | 低频：租户结构稳定 | 高频：随角色、项目、组织架构动态变化 |
| **技术特征** | 全局统一的 `tenant_id` 等值过滤 | 动态拼接的 `dept_id IN (...)` 或 `user_id = ?` |

## 二、多租户插件（TenantLineInnerInterceptor）能力边界

| 能力 | 默认行为 | 可扩展性 |
|------|---------|---------|
| 过滤字段 | 单字段（默认 `tenant_id`） | 可重写 `getTenantIdColumn()` 实现多字段切换 |
| 过滤条件 | 等值（`=`） | 可返回 `InExpression` 实现 `IN` 条件 |
| 忽略表 | 支持 | 通过 `ignoreTable()` 配置 |
| 适用场景 | 租户间**完全隔离** | 不适合同一租户内的分级权限 |

**核心问题**：多租户插件是**全局无差别拦截**的，所有 SQL 都会被注入过滤条件，且过滤逻辑与具体业务方法无关。而生产中的数据权限往往**因方法而异**——同一个表，A 接口要求看本部门，B 接口要求看本人，C 接口管理员看全部。

**官方提醒**：MyBatis-Plus 官方明确提醒 **"多租户 ≠ 权限过滤，不要乱用，租户之间是完全隔离的"**。

## 三、从需求场景判断

### 多租户的典型需求信号

1. **"这是 SaaS 产品，服务多个独立客户"**
   - 客户 A 和客户 B 是两家不同的公司，彼此不知道对方也在用这个系统
   - 客户 A 创建的员工编号为 1001，客户 B 也可以创建员工编号 1001，互不冲突

2. **"数据绝对不能跨租户泄漏"**
   - 租户是安全边界，等同于物理隔离数据库的替代方案
   - 即使管理员查询全表，也必须强制带 `tenant_id` 条件

3. **"租户可以自定义配置、甚至独立部署"**
   - 租户有自己的 logo、流程配置、字典数据
   - 极端情况下，大租户需要独立数据库/Schema（多租户架构演进）

**一句话判断**：如果去掉 `tenant_id`，整个数据行对其他租户来说**应该不存在**，那就是多租户。

### 数据权限的典型需求信号

1. **"同一个系统内，不同角色看到不同数据"**
   - 销售总监看全部门业绩，销售只看自己的客户
   - 项目经理看项目成员数据，成员只看分配给自己的任务

2. **"数据需要在组织内流转和共享"**
   - 订单创建者是张三，但财务李四需要审核，物流王五需要发货
   - 同一条数据，不同阶段由不同人处理

3. **"权限是动态授予的，可以临时调整"**
   - 今天 A 部门负责这个项目，明天 B 部门接管，数据权限需要重新分配
   - 用户可能同时拥有"本部门"和"指定项目"两种权限，取并集

**一句话判断**：如果同一条数据**客观存在**，只是某些人**暂时不被允许看到**，那就是数据权限。

## 四、边界场景：集团总部 + 多个子公司

| 场景 | 判定 | 原因 |
|------|------|------|
| 子公司独立核算、独立品牌、互不知晓 | **多租户** | 子公司是"客户"，需要隔离 |
| 子公司是集团内部部门，人员经常交叉调动、数据需要汇总 | **数据权限** | 子公司是"组织单元"，权限是分级可见 |
| 混合：子公司间隔离，但集团总部能看到全部 | **多租户 + 数据权限** | 子公司间用 `tenant_id` 隔离，集团总部用超级管理员角色突破隔离 |

**关键区分点**：子公司之间的人员和数据**是否允许流动**。不允许流动 → 多租户；允许流动 → 数据权限。

## 五、MyBatis-Plus 选型指导

| 你的需求 | 该用什么 |
|---------|---------|
| SaaS 平台，服务多个独立企业客户 | `TenantLineInnerInterceptor`（多租户插件） |
| 企业内部系统，按部门/角色/项目控制数据可见范围 | `DataPermissionInterceptor`（数据权限插件） |
| 两者都要（SaaS + 企业内部 RBAC） | **两者叠加**：先 `tenant_id` 隔离租户，再在租户内用数据权限分级 |

**不要犯的错误**：用多租户插件做数据权限。因为多租户插件是**全局无差别拦截**，所有 SQL 都加 `tenant_id = ?`，而数据权限是**按方法/按角色动态决定**的——同一个表，A 接口看部门数据，B 接口看个人数据，多租户插件无法表达这种动态性。

## 六、快速决策树

```
你的系统是否服务多个独立的外部客户？
    ├─ 是 → 他们是否共享同一套数据库？
    │       ├─ 是 → 多租户（TenantLineInnerInterceptor）
    │       └─ 否 → 独立数据库/Schema，无需租户插件
    └─ 否 → 同一个组织内部，不同角色/部门看不同数据？
            ├─ 是 → 数据权限（DataPermissionInterceptor + 自定义注解）
            └─ 否 → 无需特殊处理
```
