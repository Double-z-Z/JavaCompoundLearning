# 多数据源管理系统行业实践

> 一句话：多数据源是技术实现手段（让一个应用连接多个数据库），分库分表是架构策略（数据如何分布）；大厂实践呈现三阶段演进：应用层路由 → ShardingSphere 分片 → NewSQL 分布式数据库。

## 一、概念分层：技术实现 vs 架构策略

| 维度 | Spring 多数据源配置 | 分库分表策略 |
|------|-------------------|-------------|
| **本质** | 技术实现手段：如何让一个 Spring 应用连接并切换多个数据库 | 架构设计决策：数据如何分布在多个数据库/表中 |
| **关注点** | Bean 装配、事务管理器、路由逻辑、ThreadLocal 上下文 | 数据拆分维度（按用户？按时间？）、一致性、查询模式 |

## 二、哪些行业在生产中使用多数据源？

### 1. 电商与零售（最典型）

**核心痛点**：订单、支付、库存表数据量巨大，读写比严重失衡（通常 9:1 甚至更高）。

**典型场景**：
- 头部电商平台采用 MySQL 支撑订单管理，通过分库分表 + 读写分离提升性能，同时配合 Redis、MongoDB 做冷热数据分层
- 某知名电商平台"优选购"在 2024 年用户突破 5000 万后，采用 ProxySQL 实现 1 主 6 从的读写分离，数据库整体 QPS 从 15000 提升到 45000，主库写入压力降低 70%

### 2. 金融与银行（最严谨）

**核心痛点**：核心交易表日均百万级写入，数据一致性要求极高，且需对接征信、支付渠道等第三方系统。

**典型场景**：
- 银行核心系统按用户 ID 尾号分库（如 0-4 存 user_0 库，5-9 存 user_1 库），交易表按时间分表（trade_2023、trade_2024）
- 多业务系统集成：核心业务库（账户、交易）+ 报表统计库（OLAP 分析）+ 第三方对接库（支付渠道、征信系统）

### 3. SaaS 与多租户服务

**核心痛点**：多个租户共享一套应用，但数据必须完全隔离。

**典型场景**：
- 通过 `TenantLineInnerInterceptor` 实现租户级数据隔离，或结合 DynamicDataSource 按租户动态路由到不同数据库实例
- 当租户数据量增长到一定规模后，从共享库模式迁移到独立库模式

### 4. 工业互联网与物联网

**核心痛点**：海量设备接入，时序数据写入压力极大。

**典型场景**：
- 某工业互联网平台接入 50000 台工业设备，日数据量约 200 亿条，采用 TDengine 时序数据库集群方案，通过数据压缩节省 70% 存储空间

### 5. 社交与内容平台

**核心痛点**：读多写少，热点数据查询集中。

**典型场景**：
- 社交平台"微圈"采用 MySQL Router 读写分离，针对热点数据查询优化，但需处理主从同步延迟导致的脏读问题

## 三、生产环境决策：从单库到多数据源的演进路径

```
单库是否成为瓶颈？
    ├─ 否 → 保持单库，加缓存（Redis）
    └─ 是 → 瓶颈类型是什么？
            ├─ 读多写少，主库 CPU/IO 被读请求打满
            │   └─ 读写分离（1 主 N 从）
            ├─ 单表数据量过大（> 5000 万行），查询变慢
            │   └─ 分库分表（水平拆分）
            ├─ 多业务模块耦合，相互影响
            │   └─ 垂直分库（微服务化，每个服务独立数据库）
            └─ 以上皆有
                └─ 读写分离 + 分库分表 + 分布式数据库（NewSQL）
```

### 关键决策指标

| 指标 | 读写分离 | 分库分表 | 垂直分库 | 分布式数据库（TiDB/OceanBase） |
|------|---------|---------|---------|---------------------------|
| **触发条件** | 读:写 > 5:1，主库读压力大 | 单表 > 5000 万行 | 业务模块差异大，发布相互影响 | 以上皆有，且运维人力充足 |
| **数据一致性** | 最终一致（主从延迟） | 强一致（同分片内） | 强一致（单库内） | 强一致（分布式事务） |
| **改造成本** | 低（配置化） | 中（需改 SQL、分片键设计） | 中（服务拆分） | 高（迁移、学习成本） |
| **典型工具** | ProxySQL、MySQL Router、DynamicDataSource | ShardingSphere-JDBC | 微服务框架 + 多数据源 | TiDB、OceanBase、CockroachDB |

## 四、大厂实践：三阶段演进

### 阶段 1：应用层多数据源（中小规模）

**技术栈**：`AbstractRoutingDataSource` / `DynamicDataSource` + AOP 注解

**实现方式**：
- 基于 Spring 的 `AbstractRoutingDataSource` 实现动态路由
- 使用 ThreadLocal 存储当前线程的数据源标识
- 通过 `@DS` 注解在方法级别切换数据源

**适用场景**：
- 读写分离（90% 的多数据源场景）
- 多业务库集成（如同时访问 MySQL 和 Oracle）
- 第三方临时库对接

```java
@Service
public class AccountService {
    // 写操作：默认主库
    public boolean createAccount(Account account) {
        return accountMapper.insert(account) > 0;
    }
    
    // 读操作：指定从库
    @DS("slave")
    public Account getAccountById(Long id) {
        return accountMapper.selectById(id);
    }
}
```

### 阶段 2：分库分表（大规模数据）

**技术栈**：ShardingSphere-JDBC（首选）+ DynamicDataSource 混合

**为什么选 ShardingSphere**：
- 功能完善：分库分表、读写分离、分布式事务、数据库治理
- 生态活跃：社区文档完善，更新频繁
- 零侵入：以 JDBC 驱动形式嵌入，兼容 MyBatis-Plus、JPA 等 ORM 框架

**大厂实践**：
- 分片策略通常采用用户 ID 哈希取模：`user_id % 2` 分库，`user_id % 4` 分表
- 绑定表（Binding Table）配置：将 `t_order` 和 `t_order_item` 绑定，避免跨分片 Join
- 广播表（Broadcast Table）：小数据量配置表全库同步

### 阶段 3：分布式数据库（超大规模，运维自动化）

**技术栈**：TiDB / OceanBase / CockroachDB

**演进逻辑**：
- 当手动分库分表的运维成本超过收益时，迁移到 NewSQL
- 某大厂通过一套 OceanBase 集群替代了上百套 MySQL 分片，最大单集群数据量超 400TB，使用 OCP 工具统一管理多套集群

**优势**：
- 无感扩容缩容
- 内置冷热存储分离
- 无需应用层处理分片逻辑
- 强一致的分布式事务

**劣势**：
- 学习成本高
- 与 MySQL 生态并非 100% 兼容
- 需要专门的 DBA 团队

## 五、生产环境最佳实践

### 1. 分层设计
- **基础层**：DynamicDataSource 实现数据源快速切换
- **策略层**：自定义路由算法（尾号分库、租户隔离、读写分离）
- **事务层**：根据业务特性选择强一致（XA）或最终一致（Saga/TCC）

### 2. 监控与可观测性
- 每个数据源配置独立监控（Prometheus + Grafana）
- 记录数据源切换日志，便于排查问题
- 主从延迟监控，超过阈值自动切回主库

### 3. 渐进式演进
- 不要一上来就用分库分表，先尝试读写分离 + 缓存
- 分库分表后，避免跨分片 Join，适当字段冗余
- 当手动分片运维成本过高时，评估 NewSQL 迁移

### 4. 事务处理
- 同分片内：使用本地事务
- 跨分片/跨库：使用 ShardingSphere 的分布式事务（XA 或柔性事务）
- 尽量避免分布式事务，通过业务设计将操作收敛到同一分片
