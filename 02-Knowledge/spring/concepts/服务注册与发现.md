# 服务注册与发现（Service Registry & Discovery）

## 一句话定义
微服务架构中，服务实例启动时向注册中心报告地址（注册），客户端从注册中心获取可用实例列表（发现），解决"服务在哪"的动态寻址问题。

## 核心理解

### 为什么需要注册中心？

**传统方式的痛点**：
1. 硬编码 IP → 内网暴露安全风险 + 无法动态调整
2. Nginx 静态配置 → 不支持热部署，无法感知实例变化
3. 手动维护列表 → 扩缩容时人工成本高

**注册中心的本质**：维护一份动态的服务实例地址表

### 核心流程

```
【注册阶段】
服务实例启动 ──▶ 向注册中心发送注册请求（IP + Port + 元数据）
              ──▶ 定期发送心跳（证明自己还活着）

【发现阶段】
客户端 ──▶ 订阅服务列表（首次全量拉取）
      ──▶ 本地缓存列表
      ──▶ 变更时收到推送更新（增量）

【注销阶段】
服务实例停止 ──▶ 主动发送注销请求（优雅关闭）
             或 注册中心超时未收到心跳 → 自动剔除
```

### Push vs Pull 模式对比

| 模式 | 代表 | 优点 | 缺点 |
|------|------|------|------|
| 纯 Pull | Eureka | 简单可靠 | 延迟高（最多30秒） |
| Push + Pull | Nacos | 实时性好 | 复杂度高 |

**Nacos 的混合策略**：
- 订阅时：长轮询/UDP 推送变更通知
- 平常：本地缓存 + 定期刷新
- 类比：[[多级缓存一致性]] 的设计思路

### 无状态服务（Stateless Service）

**核心原则**：Session 不存在服务实例本地，而是存 Redis

```
传统有状态：A实例存了用户Session → 只能路由到A
无状态：Session存Redis → A/B/C任意处理
```

**好处**：
- 水平扩展自由（任意增减实例）
- 高可用（宕机不影响用户体验）
- 负载均衡策略灵活

## 关键关联

- [[Sentinel-核心机制]] - 关联原因：Sentinel 是客户端侧的熔断组件，负责流量控制和健康检测；注册中心负责服务发现。两者职责分离但协同工作。
- [[多级缓存一致性]] - 关联原因：Nacos 的 Push+Pull 混合模式与多级缓存的设计思想一致——变更主动失效 + 定期刷新。
- [[Redis-数据类型与编码]] - 关联原因：分布式 Session 存储依赖 Redis 的高性能简单结构。
- [[Spring配置管理]] - 关联原因：@EnableDiscoveryClient 触发自动配置链路，属于 Spring Boot Starter 机制的典型应用。

## 我的误区与疑问

- ❌ **误区**：浏览器会缓存服务地址 → **纠正**：只有 Java 服务实例才是注册中心的"客户端"，浏览器通过 API Gateway 访问
- ❌ **误区**：注册中心是用户发起的请求入口 → **纠正**：注册中心只服务于集群内部的服务间调用
- ❓ **疑问**：Nacos 的 UDP 推送如何保证可靠性？如果推送丢失怎么办？

## 代码与实践

```yaml
# application.yml - Nacos 配置示例
spring:
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
        namespace: dev
        group: DEFAULT_GROUP
```

```java
// Spring Cloud Alibaba 中 @EnableDiscoveryClient 已可选
// 只要 classpath 下有 nacos-discovery jar 就会自动配置
@SpringBootApplication
public class ProviderApplication {
    public static void main(String[] args) {
        SpringApplication.run(ProviderApplication.class, args);
    }
}
```
