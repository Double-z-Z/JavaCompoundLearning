# 生产环境数据权限实现方案

> 一句话：生产中的数据权限分为行级和列级，Java 后端最常用 MyBatis-Plus `DataPermissionInterceptor` + 自定义注解实现声明式控制；数据库层 RLS 更严格但国内 MySQL 生态较少使用。

## 一、数据权限的两个维度

### 1. 行级权限（Row-Level Security）

最常见的需求，典型控制维度：

| 数据范围 | 说明 | 实现方式 |
|---------|------|---------|
| **全部数据** | 超级管理员 | 跳过过滤 |
| **本部门及子部门** | 部门经理 | `dept_id IN (SELECT id FROM sys_dept WHERE id = ? OR FIND_IN_SET(?, ancestors))` |
| **本部门** | 普通主管 | `dept_id = ?` |
| **本人数据** | 普通员工 | `create_by = ?` 或 `user_id = ?` |
| **自定义部门** | 跨部门项目负责人 | `dept_id IN (SELECT dept_id FROM sys_role_dept WHERE role_id = ?)` |
| **多租户隔离** | SaaS 场景 | `tenant_id = ?` |

这些维度往往**组合出现**：用户可能同时拥有"本部门"和"自定义项目"的权限，需要按**角色取并集**。

### 2. 列级权限（Column-Level Security）

| 场景 | 示例 |
|------|------|
| 敏感字段脱敏 | 普通员工看不到客户手机号、薪资 |
| 成本/售价隔离 | 采购看进价，销售看售价，财务全看 |
| 审计字段隐藏 | 隐藏 `created_by`、`updated_at` |

列级权限通常不在 SQL 拦截层做（改列会影响结果集结构），而是在**序列化/返回层**处理，或结合数据库视图。

## 二、方案 1：SQL 拦截器（MyBatis-Plus `DataPermissionInterceptor`）

Java 后端最常见的方案，RuoYi-Vue-Pro 等主流开源项目采用。

### 核心设计

- 通过 `DataPermissionHandler` 接口动态拼接 SQL 片段
- 结合自定义注解（如 `@DataScope`）标记哪些方法需要过滤
- 根据当前用户的角色，解析出数据范围枚举，拼接对应条件

```java
// 典型实现：按角色数据范围拼接条件
switch (dataScopeEnum) {
    case ALL: return where; // 全部权限，不拼接
    case DEPT: 
        appendSql = deptColumn + " = " + currentDeptId;
        break;
    case DEPT_AND_SUB:
        appendSql = deptColumn + " IN (SELECT id FROM sys_dept WHERE id = " 
                    + currentDeptId + " OR FIND_IN_SET(" + currentDeptId + ", ancestors))";
        break;
    case SELF:
        appendSql = userColumn + " = " + currentUserId;
        break;
}
```

### 优势

- 对业务代码零侵入
- 分页查询的 `COUNT` 语句也能自动应用权限过滤

### 注意点

- **拦截器顺序**：`DataPermissionInterceptor` 必须在分页插件之前
- **复杂 SQL**：嵌套子查询可能解析失败，需配合 `@InterceptorIgnore` 注解排除
- **权限数据缓存**：建议缓存到 Redis 或 ThreadLocal，避免每次查 SQL 都查权限库

## 三、方案 2：数据库层行级安全（RLS）

PostgreSQL、SQL Server、Oracle 等支持原生行级安全策略：

```sql
-- PostgreSQL 示例
CREATE POLICY user_isolation ON orders
FOR SELECT TO app_user
USING (user_id = current_setting('app.current_user_id')::int);
```

### 优势

- 权限策略在数据库层强制执行，应用层无法绕过

### 劣势

- 与 ORM 框架结合复杂
- 迁移成本高
- 国内 MySQL 生态为主，较少使用

## 四、方案 3：应用层手动过滤（不推荐）

```java
list.stream().filter(r -> r.getDeptId().equals(currentDeptId)).collect(...)
```

**致命问题**：分页查询时 `COUNT` 失真，大数据量下内存过滤性能极差。生产环境基本不用。

## 五、生产环境最佳实践

1. **明确区分概念**：多租户是**租户隔离**，数据权限是**分级查看**，两者正交
2. **使用数据权限插件**：基于 `DataPermissionInterceptor` + 自定义注解 + 数据范围枚举，实现声明式控制
3. **统一权限字段**：在需要过滤的表中增加 `dept_id`、`user_id` 等字段，但允许不同方法按不同字段组合过滤
4. **缓存权限上下文**：用户登录后将角色-数据范围映射缓存到 Redis 或 ThreadLocal，避免每次 SQL 拦截都查库
5. **列级权限在返回层处理**：不要试图在 SQL 拦截层删列，而是在 DTO 转换/序列化时根据权限掩码脱敏
