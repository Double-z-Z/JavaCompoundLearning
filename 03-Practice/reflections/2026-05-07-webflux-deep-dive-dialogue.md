### 阶段 3：分类思维（Servlet 和 WebFlux 统称为什么）

**问题**：怎么描述 servlet 和 webflux 他们统称为一类什么东西？

**我的回答**（关键突破）：
1. 它们都是一套 web 请求处理框架
2. 作为框架定义行为模式、工具、生态和使用规范
3. 行为边界：只处理服务端逻辑、管理连接和响应、提供业务层接口

**延伸思考**（Netty vs Web 框架）：
- Netty 要成为 Web 框架需要增加什么？
  - HTTP 编解码器
  - MVC 分层设计和编程规范
  - HTTP 状态管理和连接维护

**顿悟时刻** 💡：
> **MVC 本身和网络模型无关！它是 Web 服务本身的内容架构模式。**

**认知状态**：
- ✅ 建立了抽象分层能力
- ✅ 能区分协议层/框架层/业务层
- ✅ 发现 MVC 是架构模式而非网络模型特性

### 阶段 4：路由选择（函数式 vs 注解式）

**问题**：函数式路由的好处是什么？

**初始困惑**：
- 看起来对 URL 的分层处理没有 Controller 清晰
- 从"基于地址的代码分配"变成了"基于代码的地址分配"

**深度理解后**：
- 核心差异不是位置问题，而是**组合能力**
- 注解式：编译时固定，强耦合
- 函数式：运行时可操作，一等公民

**我的原创洞察** 🌟：

#### 洞察 1：Web 最小组件

> Web 的最小组件应该是编解码 + 路由，因为最简单的 web 就是只含 URL 和简单方法的资源服务。业务逻辑是后来网络发展之后的产物。视图和数据也是 Web 内容丰富之后的产物。

**意义**：建立了 Web 框架的演化视角

---

#### 洞察 2：三层决策模型（核心贡献）🏆

将动态路由场景分为三类：

| 变化频率 | 场景 | 推荐风格 |
|---------|------|---------|
| 高频 | API 网关、多租户 SaaS | 函数式（组合能力） |
| 低频 | 灰度发布、特性开关 | 混合模式（注解 + Filter/AOP） |
| 固定 | 大多数 CRUD API | 注解式（开发效率） |

**关键补充**：
> 场景 2 其实是场景 3 的临时变体，不是内容需求而是特殊需求。

**意义**：提供了实用的架构决策框架

---

#### 洞察 3：插件化结构的本质

> 插件化结构代表这个 Web 服务是可以扩展路由的，甚至改造路由。但这意味着这不是寻常的 Web 服务，因为我作为消费者接触到的 URL 应该都是规范化可读的。而可变路由通常意味着 Web 服务还没有到达最终消费者，或者消费者本身也会对外二次提供 Web 服务。

**例子**：
- 微信小程序平台 → 商家定制服务 → 最终消费者
- 各种平台服务（Shopify、有赞）

**意义**：理解了动态路由的真实使用场景边界

---

### 阶段 5：消费者视角（非人类消费者的 Web 服务）

**问题**：Web 服务不是提供给人的，有哪些例子？

**学习内容**：
- 大多数 Web 服务主要给代码消费（70% 前端 JS / App）
- 机器对机器 (M2M)：支付回调、Webhook、微服务调用
- 基础设施服务：Prometheus metrics、K8s healthz
- AI/Agent 消费：LLM Function Calling、MCP 协议

**我的判断** 💡：

> 大多数场景理论上可以不用 HTTP，它用不上大多数 HTTP 的功能。但是生态友好，维护友好。除非性能瓶颈或满足不了需求，否则 HTTP 成本更低。

**决策树建立**：
```
QPS > 100K? → 考虑 gRPC
延迟 < 1ms? → 考虑共享内存/RDMA
内部微服务且团队成熟? → 可选 gRPC
否则 → HTTP（省心）
```

**应用到自己项目**：
> 计数器可以是前端 JS 调用，也可以作为微服务，只要能用 HTTP 通信就可以。
