# 回滚与补偿的本质区别 — 对话反思

## 对话背景

在讨论秒杀多 SKU 的 Saga 模式时，AI 最初解释回滚和补偿的区别是"中间状态是否对外可见"。用户立即指出这个逻辑不成立：

> "数据库事务也有可能对外中间可见。redis的incr同样也是，这是原子性的问题，不是可见性的问题。所以，两者的区别是原子性吗？"

## 用户的纠正与核心洞察

### 第一击：可见性不是区分标准

用户用反例推翻了我的可见性论证：
- MySQL READ UNCOMMITTED 下，别的事务能读到未提交数据
- Redis INCR 一旦执行，其他客户端立即可见

**结论**：可见性既描述不了回滚，也描述不了补偿。

### 第二击：原子性也不是区分标准

用户追问"区别是不是原子性？"

**正确答案**：不是。回滚是单事务原子性的实现机制（ACID 中的 A），补偿恰恰出现在**原子性无法保证的场景**（分布式环境、CAP 下放弃 ACID）。补偿本身也不具备原子性——C1 执行时可能网络超时、可能重试、可能被并发修改干扰。

### 第三击：真正的区分标准 —— 语义消除的层级

用户引导我重新思考，最终得出的正确结论是：

| 维度 | 回滚（Rollback） | 补偿（Compensating Transaction） |
|------|-----------------|--------------------------------|
| **执行主体** | 数据库引擎 | 业务代码 |
| **作用域** | 单个数据库连接内的同一个事务 | 跨服务、跨网络、跨存储介质 |
| **撤销机制** | 通过 Undo Log / MVCC **物理/逻辑地消除**数据页修改 | 发送另一条业务指令（如 INCR 回补），**数值上抵消** |
| **副作用** | **无**（仿佛从未发生） | **必然存在**（MQ 事件已发出、日志已记录、监控已采集） |
| **并发安全** | 数据库自动保证 | 业务层自己处理 |
| **失败可能** | 几乎无 | **补偿本身可能失败** |

**一句话定性**：
- **回滚**：让一次数据修改在系统语义上"从未发生"
- **补偿**：承认修改已客观发生，再用一次业务操作把数值"填平"，但历史痕迹和副作用永远留在系统里

### 秒杀库存的具体例证

```text
T1 成功：Node1 执行 DECR stock:SKU001 → 99→98
    └── 同时发出 Kafka 事件："SKU001 库存扣减成功"
T2 成功：Node2 执行 DECR stock:SKU002 → 50→49
T3 失败：Node3 执行 DECR stock:SKU003 → 发现只有 0 库存，拒绝

补偿 C1：Node1 执行 INCR stock:SKU001 → 98→99
```

数值回到了 99，但以下痕迹**无法被 INCR 抹除**：
1. Kafka 消息已被订单统计服务消费，销量报表已 +1
2. Prometheus 已采集到 `stock:SKU001 = 98` 的时序数据
3. ELK 永久记录了 `DECR stock:SKU001` 这条操作日志
4. 用户在 C1 执行前刷新页面，已看到"库存 98"

## 思维升级

### 纠正前的错误认知

❌ "回滚和补偿的区别是中间状态有没有对外可见"

### 纠正后的正确认知

✅ "回滚是存储引擎在事务边界内将数据修改物理/逻辑地抹除，仿佛从未发生；补偿是业务代码在分布式环境下用新的业务操作对冲旧操作，数值上抵消但副作用永久残留。"

✅ "前者是'删除历史'，后者是'追加修正'。"

## 给我的工程判断标准

```text
这个问题能否在一个数据库连接的 BEGIN...ROLLBACK 内解决？
├─ 能 → 用数据库事务回滚（简单、强一致、无副作用）
└─ 不能（涉及多个 Redis 节点 / 多个微服务 / 外部系统调用）
   └─ 必须用 Saga + 补偿事务（接受最终一致，额外处理幂等、对账、监控）
```
