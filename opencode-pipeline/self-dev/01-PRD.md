# OpenCode Pipeline Orchestrator — 需求文档 (PRD)

## 1. 项目背景

用户（zhuhengyi321）是一名 Java 后端开发者，正在系统性地评估多 Agent 协作方案。已完成 Hermes 实战验证，发现其核心问题：
1. Developer 与用户的讨论对 Architect 和 Reviewer 不可见，导致架构一致性断裂
2. 用户需要手动控制流程流转，监控 Agent 中断消耗注意力，影响多项目并行效率
3. Claude Code 在 UI 体验、工作空间隔离、配置简洁度上优于 Hermes

用户明确自身角色为**最终项目负责人**，需要掌控进度和方向，同时强调**个人成长（通过复利工程）比 Agent 成长更重要**，需要一个能记录和提炼用户决策/能力/认知的知识 Agent 角色。

## 2. 核心需求

### 2.1 功能需求

| 需求 ID | 需求描述 | 优先级 | 状态 |
|---------|---------|--------|------|
| F-001 | 五阶段工作流编排：架构 → 方向门 → 编码 → 审查 → 合并门 | P0 | 原型中 |
| F-002 | 每个阶段可配置为"交互式"（人与 Agent 对话）或"后端执行"（自动运行） | P0 | 原型中 |
| F-003 | Gate（门）机制：人类审批或程序自动判断，驳回可回退到指定阶段 | P0 | 已实现 |
| F-004 | 多 Agent 顺序执行，支持迭代循环（如编码驳回回退到架构） | P0 | 已实现 |
| F-005 | 实时进度监控：Agent 正在读取/写入/思考的状态可见 | P1 | 部分实现 |
| F-006 | 交互式 Stage 内嵌终端：人类可在 UI 中与 Agent 实时对话 | P1 | 未实现 |
| F-007 | 上下文总线：上游产物（设计文档、代码）自动注入下游 Agent Prompt | P0 | 已实现（路径注入） |
| F-008 | 知识沉淀：每次工作流结束后提取决策日志到 Obsidian | P2 | 未实现 |
| F-009 | 多项目隔离：不同项目独立工作空间，互不污染 | P2 | 未实现 |
| F-010 | Tauri 三 pane 控制塔：左（控制）、中（交互）、右（监控） | P2 | MVP 为 HTML |

### 2.2 非功能需求

| 需求 ID | 需求描述 | 优先级 |
|---------|---------|--------|
| NF-001 | 局域网部署：PVE Fedora 虚拟机 + Windows 笔记本浏览器访问 | P0 |
| NF-002 | 模型无关：支持 DeepSeek / MiniMax / Kimi 等多家模型动态路由 | P0 |
| NF-003 | 数据不出 PVE：代码和密钥留在 Linux 虚拟机，Windows 只做 UI 渲染 | P0 |
| NF-004 | 可自举：原型完善后，用自身工作流迭代开发自己 | P1 |
| NF-005 | 与现有工作流集成：最终产物能导出到 Obsidian 知识库 | P2 |

## 3. 用户画像

- **角色**：Java 后端开发者，个人项目管理者
- **技术栈**：Java / Spring / Linux / PVE / Obsidian
- **工作模式**：远程开发（PVE Fedora），Windows 笔记本做 UI 入口
- **核心痛点**：多 Agent 协作的可见性、可控性、知识沉淀
- **成功标准**：能并行管理多个项目，每个项目有清晰的决策记录和可回溯的审批链

## 4. 术语表

| 术语 | 定义 |
|------|------|
| Sidecar | 独立于 OpenCode 的编排引擎进程，负责状态机和审批队列 |
| Gate | 工作流中的检查点，可以是人类审批或自动程序判断 |
| Stage | 工作流中的一个阶段，如 architect、coder、reviewer |
| Run | 一次完整的工作流实例，有唯一 run-id |
| 交互式模式 | Agent 启动 TUI，人类实时对话介入 |
| 后端模式 | Agent 后台自动执行，人类只监控进度 |
| 上下文总线 | 各阶段产物通过文件系统共享，下游 Agent 读取上游产物 |
